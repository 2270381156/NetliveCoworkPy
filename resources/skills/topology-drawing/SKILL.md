# 网络拓扑绘图

## 先决条件：这个技能依赖两个 IPMC 工具

本技能**不能独立工作**，它靠 IPMC 提供的两个工具画图：

- `topology__draw_topology`
- `topology__export_diagram`

**skill 和 IPMC 是分开发布的，版本不一定配套。** 所以**动手之前先确认这两个工具在不在**
（看你当前可用的工具列表）。

如果缺任何一个，**立刻停下来，不要尝试用别的方式画图**——不要自己写 SVG、不要用
matplotlib/graphviz、不要拿 mermaid 凑。如实告诉用户：

> 当前的 IPMC 版本没有提供拓扑绘图工具（`topology__draw_topology` /
> `topology__export_diagram`），这个技能用不了。请升级 IPMC 到支持拓扑绘图能力的版本。

自己找替代画法会画出一张**看着像但完全没有本技能保证的图**——没有 DRC 检查、没有图例、
没有编码表、没法导出成可编辑的 vsdx/pptx，而用户以为得到的是本技能的产物。宁可不画。

## 随身资料：两份 reference，需要时读

本技能自带两个参考文件，用 `skill_executor__read_file("<相对路径>")` 读（也可以用
`skill_executor__list_files` 看有哪些）：

| 文件 | 什么时候读 |
|---|---|
| `references/change-recipes.md` | **用户提出任何"改样子"的要求时，先读它。** 颜色、图标、字、大小、间距、区域框、图例、端口、连线——按用户的说法查怎么改，以及**哪些当前做不到** |
| `references/icon-catalog.md` | 第一次要给角色配图标时，读一次拿到全部可选 key |

**这是硬要求，不是建议。** 用户说"把图标颜色改一下""图例挪到左边""线太粗"这类话时，
**先读 `change-recipes.md` 再动手**——不要凭印象猜字段名，不要去翻工具参数找样式开关
（工具只有 `preview_path`/`model_path`/`output_path`/`format`/`routing` 五个参数，
一个样式参数都没有）。

`change-recipes.md` 里没有的诉求，就是**当前做不到**：如实告诉用户，说明最接近的替代方案，
让用户选。**绝对不要去编辑渲染产物**（预览 HTML、导出的 SVG/vsdx/pptx）——那些是每次调用
重新生成的，改了下次就没，而且模型和图会对不上。


把网络工程师的自然语言需求转成结构化的拓扑 JSON（`.topo.json`），通过 DRC（Drawing Rule
Check）诊断迭代确保图纸本身画得对，直到没有 error、用户明确满意为止。

**DRC 只查图纸，不查网络设计：** DRC 的 `findings` 只覆盖"这份图纸本身会不会真的画错"——编码表
（`deviceRoles`/`linkTypes`/`connTypes`/`zoneTypes`）里出现的角色/类型是否都有定义、设备 id
有没有重复、label 有没有缺失。**注意**：label 重复（两台设备同名）、编码表条目 legend 文案
为空，都**不**是缺陷——这些是合法的风格选择（人类设计者可能就是想这样），不影响渲染正确性，
不要因为 DRC 没报警就去"顺手"改它们，也不要主动建议用户改。它**不**评判网络工程设计好不好（要不要 HA、上联
够不够冗余、是不是单点故障之类）——这里画的是抽象拓扑，同一种网络结构有很多种同样合法的
画法（HA 对可以是两个独立设备各自接上下游，也可以是一个框代表一组、框本身接上下游），套
一条"必须怎么连"的结构规则去检查，换个画法就文不对题。分数 100 只代表图纸本身干净，**不**
代表网络设计已经满足用户需求——网络设计是否符合用户描述（比如"要双活防火墙""核心要冗余"），
靠你自己对照用户原始需求做判断，不要靠 DRC 分数当替代品，更不要为了刷分去调整跟用户当前
请求无关的网络设计（比如用户只是要加个区域框，就不要主动去改 haPair/链路冗余）。

**核心原则（Authored vs Derived）：**

- 你只写语义：设备（`devices`，每个含 `id`/`role`/`tier`/`label`，可选 `haPair`/`satelliteOf`/`satelliteGap`）、
  链路（`links`，含 `a`/`b`/`type`/`aConn`/`bConn`）、编码表（`encoding`：`deviceRoles`/`linkTypes`/`connTypes`[/`zoneTypes`]）、
  可选的区域分组（`zones`，每条含 `id`/`type`/`label`/`members`）。**zone 是递归的布局容器**，不只是画个框：
  `members` 里既可以是设备 id 也可以是另一个 zone 的 id（嵌套，最多两层显式嵌套，更深会硬报错）；
  `layout`（**只有 `"row"` 行铺 / `"column"` 竖排两种**，缺省 `row`）决定内部成员怎么排；写别的值会被拒（BAD_ARGS）——**环形、放射状、网格这类组网当前表达不了**：用户说"这是个环网/SDH 环/Dragonfly"或"按环形排"时，如实告诉他这是当前模型的表达力缺口，不要用 row/column 硬凑成近似形状交差；`tier` 决定这个 zone
  整体在父容器里排第几行/列；`satelliteOf` 把整个 zone 旁挂到同 tier 兄弟外侧（`satelliteGap`
  调贴靠净空，缺省 90；旁挂只在 `row` 布局里可用，`column` 布局的成员带 `satelliteOf` 会硬报错）；
  `rowGap`/`hGap` 覆盖本 zone 内部的行距/列距净空（不继承——每个 zone 要么自己声明、要么用全局默认）。

- **⚠⚠ 方位（上下左右）不是声明出来的，是 `layout` × `tier` 分布算出来的。**
  **没有任何字段的含义是"这几个东西上下排"。** 用户说"一个在上两个在下""左右对称""服务器
  在上防火墙在下"时，你要把它翻译成 `layout` + `tier`，翻译规则只有一条：

  > **同 `tier` = 并排；不同 `tier` = 沿主轴依次排开。`row` 的主轴是纵向，`column` 的是横向。**

  由此得到三条必须逐条核对的规则（三条都是**沉默失败**：不报错、DRC 满分、图也画得出来）：

  1. **顶层 zone 不写 `tier` → 所有顶层 zone 挤在同一行、左右并排。** 不写时兜底成 `tier: 0`，
     而整图根区域固定是 `row`。要"一个在上、两个在下"，**必须显式写**：
     ```
     zones: [ {id:"DC-A", tier:0, members:[...]},        ← 上面那个
              {id:"DC-B", tier:1, members:[...]},        ← 下面两个，tier 相同 = 并排
              {id:"DC-C", tier:1, members:[...]} ]
     ```
  2. **zone 内设备不写 `tier` → 该 zone 内全部并排一行。** 要"服务器在上、防火墙在下"，
     就得给设备写不同 `tier`（服务器 0、防火墙 1）。`tier` 在**每个 zone 内部各自从头分组**，
     不需要全图连续编号（连续编号也对，效果一样）。
  3. **`column` 里 `tier` 是"第几列"，不是"第几行"。** 想要"一台交换机在上、几台下挂设备
     竖排在下面"，**必须把它们写成同一个 tier**，上下顺序由 `members` 声明顺序决定：
     ```
     devices: [ {id:"SW", tier:0}, {id:"PC1", tier:0}, {id:"PC2", tier:0} ]   ← 全部 tier:0
     zones:   [ {id:"Z", layout:"column", members:["SW","PC1","PC2"]} ]       ← 得到一根竖柱
     ```
     按直觉写成 `SW` tier 0、`PC` tier 1，会得到**并排的两列**（交换机一列、PC 一列），
     zone 明显变宽。这一条工具会给信号：`geometry.columnFanouts` 里出现 `columns > 1`
     就说明写反了。**前两条没有任何信号**，只能靠上面的规则写对，或让用户看预览确认。

  **不要写 `meta.layoutDirection`**（`"TB"`/`"LR"` 之类）。引擎不读这个字段，写了不生效
  也不报错。整图固定自上而下；要横向排布用 `layout: "column"`。
- **⚠ 顶层的左右顺序，由 `devices[]` 数组顺序决定，不是 `zones[]` 数组顺序。**
  一个 zone 的排序位置 = 它所有成员设备里**在 `devices[]` 中最早出现的那个**的下标；
  裸设备用它自己的下标。两者放在同一把尺子上排左右。

  所以要把某台设备摆在两个 zone **中间**（典型场景：两个数据中心左右对称、Internet 在正中），
  必须在 `devices[]` 里**交错声明**——把它写在两组设备之间：
  ```
  devices: [ {id:"A1"...}, {id:"A2"...},        ← DC-A 的设备
             {id:"INT", role:"internet"...},     ← Internet 夹在中间
             {id:"B1"...}, {id:"B2"...} ]        ← DC-B 的设备
  zones:   [ {id:"DCA", members:["A1","A2"]}, {id:"DCB", members:["B1","B2"]} ]
  ```
  按直觉"先写完 A 的设备、再写完 B 的、最后写 Internet"，Internet 会跑到**最右边**；
  写在数组最前面则会跑到**最左边**。调整 `zones[]` 的顺序**没有任何效果**。

  这个错误不报错、DRC 满分、图也画得出来，只是位置不对——又一个沉默失败。
  **而且工具当前不返回布局坐标**，你无法从返回值里验证谁在中间；只能靠这条规则写对，
  或者让用户看预览确认。不要去解析 HTML 里的 SVG 坐标——那是渲染产物，格式会变。
- 用户说"画个框""圈起来""分区""标注一下区域"之类的话，指的就是给一组设备加 `zones`
  （渲染成虚线包围盒 + 标签），不是设备节点本身的 CSS 边框——不要把这类请求当成"渲染样式，
  语义模型管不了"而回绝或绕开；`zones` 正是为此设计的字段。若不确定该圈哪些设备/叫什么名字，
  用 `control__ask_user` 问清楚，问完就在 JSON 里加一条 `zones` 记录，不要只嘴上解释概念。
- **不写坐标字段**（x/y/cx/cy 之类）——坐标由布局引擎派生，写在设备上会被直接忽略。唯一例外是
  zone 的 `position: {dx, dy}`（相对父容器左上角的显式钉住，只有 zone 认这个字段），这是最后手段
  的泄压阀：表达位置意图的优先级永远是 **关系字段（`satelliteOf`/`tier`/嵌套归属）> 数值字段
  （`rowGap`/`hGap`/`satelliteGap`）> `position` 裸坐标**。用了 `position` 的元素，上游结构一变
  就可能不再合适，要主动复查。
- `tier` 是**纯序数**：只决定行/列的先后次序（数字越大越靠"下游"），数值间隔不产生空间效果
  （tier 0 和 tier 5 之间不会留出空行；写 `tier: 0.5` 不会让间距变小——间距用 `rowGap`/`hGap` 表达）。
  同 tier 内谁左谁右由**声明顺序**决定：顶层看 `devices` 数组的下标（zone 取它递归成员里最早出现的
  那台设备的下标，跟裸设备排在同一把尺子上，混排也按声明顺序），zone 内部看该 zone `members`
  数组的顺序；这个顺序稳定、重新布局不会变。
- **禁止把决策写进语义不匹配的字段**：不许用小数 tier 制造间距、不许造空壳 zone 借道控制排序、
  不许把间距诉求编码进设备尺寸。没有合适的字段表达用户的要求时，明确告诉用户这是当前模型的
  表达力缺口，而不是悄悄找个别的字段硬凑——硬凑的值下一个读模型的人（包括未来的你）无法理解。

**工作流程：**

1. 读取或从头构造一份 `.topo.json`（用 `fs__write_file` 写入工作目录）。
   - **默认给每个设备角色配图标。** 给 `encoding.deviceRoles` 里的**每一个**角色挑一个 `icon`
     key，写进 `encoding.deviceRoles[role].icon`。不配图标的图是一堆纯色方框，网络工程师认不出
     哪个是交换机哪个是防火墙——这是成图质量的下限，不是可选的润色。只有两种角色可以不配：
     `decorative: true` 的（"…"省略标记之类，不代表真实网络实体），以及已经用 `glyph`
     （如 Internet 画成云）表达了的。
     - **可选 key 的完整清单在 `references/icon-catalog.md`**，用
       `skill_executor__read_file("references/icon-catalog.md")` 读。第一次要配图标时读一次即可。
     - **按语义判断，不要拿角色名跟 key 做字符串匹配。** 角色名是当前拓扑里临时起的自由文本
       （用户可能说"EOR 交换机""汇聚层交换机""distribution switch"），key 是固定英文短语，
       字面上大概率对不上，但语义上可能是同一类设备。看这个角色**实际是什么设备/概念**，
       不是看它在当前图里叫什么名字。举例："EOR 交换机"实际是汇聚层交换机 → `agg-switch`；
       "distribution switch" → `agg-switch`；"出口路由器"如果语义上是核心/骨干路由器 →
       `core-router`，如果就是普通边界路由器、没有更贴切的 → `generic-router`。
     - **找不到语义上真正贴切的，就不要设 `icon`**——不要为了"总得选一个"而勉强凑一个不准确的。
       不设 `icon` 时这个角色照旧画纯色矩形，是完全正常、可交付的状态，不是缺陷。
   - **图标颜色**：在 `devices[i]` 上加 `iconTheme: "yellow"`（缺省 `"blue"`，不用每台都写）。
     用户说"把这几台的图标标成黄色""区分一下新旧设备/遗留设备"时用它，**逐台设备可设**。
     这是**唯一**的图标配色手段——只有蓝、黄两色，不能指定任意颜色；
     `encoding.deviceRoles[role]` 上的 `fill`/`stroke` **对配了图标的角色是空操作**
     （有图标时方框根本不画），写了不生效也不报错。
     它只对参考页里标了"是设备"的角色生效，Internet/云/管理员这类非设备图标不受影响。
     不设不影响任何 DRC 判定，也不影响布局。细节见 `references/change-recipes.md` 第 1 节。
2. 调用 `topology__draw_topology`，给 `preview_path`（绝对路径，`.html` 结尾，通常跟
   `.topo.json` 同名换后缀）和模型。它做两件事：**把图写成 HTML 让用户在预览面板看见**，同时
   返回诊断给你（0-100 分 + `findings` + `geometry` + `style`）。

   模型有两种给法，**必须且只能给一种**：
   - `topology_json`：直接把模型字典写进工具参数。小图（十来台设备）这样最省事。
   - `model_path`：先把模型落盘成 `.topo.json`，再给绝对路径。

   **设备多的时候必须用 `model_path`。** 工具参数里的模型要你逐字生成出来，受单次输出上限
   约束——几十台设备展开成 JSON 就上万 token，根本传不进去。而生成它的脚本可能只有几十行：
   用 shell 写个脚本把规律性的部分（比如 48 台 leaf、每台两条上联）循环生成出来，落盘，
   再把路径给这里。这样那份大 JSON 从头到尾不经过你的输出。
   改模型也一样——改脚本重新生成，或者写个小脚本改 JSON，都比整份重写划算。
   - **每改一轮就调一次**，别攒到最后。用户看到的图和你读到的诊断出自同一次计算，是同步的；
     你不调，用户就一直看不到你画成什么样。
   - 它**不返回 HTML 内容**，只返回 `path` 和 `bytes`。不要试图读回文件内容再转存。
3. 读 `findings`：每条带 `rule` / `severity`（`error` 比 `warn` 更该优先修）/ `message` / `refs`（涉及的设备/链路 id）。
   针对 `error` 逐条修正后，重新调用 `draw_topology` 复核，直到不再有 `error`、分数进入合理区间。
   - **（第 3.5 步）读 `geometry`**：同一份返回值里的 `geometry` 字段是几何体检
     数据（测量值，不是错误清单），六项：
     - `zoneOverlaps`——互相没有祖先/后代关系的两个 zone，可视化框真的相交（二维求交，带
       `overlapX`/`overlapY`）；
     - `containmentViolations`——成员图形超出所属 zone 框；
     - `rowClearances`——顶层相邻两行**主组**之间的实际净空（`rowGap` 控制的就是这个量）。
       不含旁挂成员，所以这个数干净：负数就是主干内容真的挤到一起了；
     - `satelliteOverflows`——旁挂成员溢出到了别的行**并且真的撞上**（同样是二维求交）。旁挂
       竖跨好几行本身是允许的画法（贴在侧边、不撑高整张图），只有真碰到才会出现在这里。
     - `linkCrossings`——**连线压过了非端点的设备**，每条带 `a`/`b`/`type` 和 `crosses`
       （被压住的设备 id 列表）。最常见的成因是一列设备竖排：交换机到下面那台的连线必然
       穿过上面那台。这个列表非空，图上就是一堆线从设备身上压过去，人一眼就看出不对——
       **但前面四项照样全清、DRC 照样满分**，只有这一项能告诉你。
       修法通常是改结构（把竖排改成横排、或让每台设备各自成组），不是调间距。
     - `columnFanouts`——某个 `layout: "column"` 的 zone 因为成员 tier 不同而**分出了多列**，
       带 `zone`/`columns`（几列）/`byTier`（每列各是谁）。多列本身是合法能力；但如果你本意是
       "上下堆叠"，看到 `columns > 1` 就说明写反了——`column` 里 tier 是"第几列"不是"第几行"，
       把这些成员改成同一个 tier 即可（上下顺序由 `members` 声明顺序决定）。
       这是这类错误**唯一**的线索：DRC 满分、其余几何项全清、图也画得出来，形态却不对。
     通常重叠/越界/负净空/旁挂碰撞都应该处理（调 `tier`/`satelliteGap`/`rowGap` 或调结构），但由
     `position` 钉住导致的除外——那可能是用户故意要的，先确认再动。这些测量不参与 DRC 打分，
     不会影响分数，也不会出现在 `findings` 里。
   - **（第 3.6 步）读 `style`**：同一份返回值里的 `style` 字段是图示层体检，三项：
     - `rolesWithoutIcon`——图里用到、但既没有 `icon` 也没有可渲染 `glyph`、也不是 `decorative`
       的角色。**这个列表非空就说明成图会有一堆纯色方框，回到第 1 步把它们补齐**，别因为
       DRC 已经 100 分就跳过；
     - `unknownIcons`——写了 `icon` 但**图标目录里没有这个 key**，解析不出来、照旧画纯色方框。
       出现在这里说明 key 拼错了或凭印象编了一个，回 `references/icon-catalog.md` 核对；
     - `unrenderedGlyphs`——写了 `glyph` 但引擎不认识那个值（只有 `cloud` 和 `ellipsis` 真能画出
       图形，其余值被静默忽略、照旧画纯色方框）。出现在这里说明你以为自己指定了图形、实际
       是个空操作，改成 `icon` 或换成认识的 `glyph`；
     - `roleColorCollisions`——共用同一组配色的角色。角色数超过调色板长度时必然发生，图例里
       仍有文字区分，所以不一定要改；确实需要区分开时，在 `encoding.deviceRoles[role]` 上
       显式写 `fill`/`stroke`（写了就不会被自动配色覆盖）。**注意 `fill`/`stroke` 只对
       没有 `icon` 的角色有效**——配了图标的角色画的是图片、方框根本不画，写了这两个字段
       是空操作且不报错。带图标的设备只能用 `devices[i].iconTheme` 在蓝/黄之间切换，
       详见 `references/change-recipes.md` 第 1 节。
     跟 `geometry` 一样，这几项都是测量、不打分、不进 `findings`。**DRC 满分不等于图画得好看
     或看得懂**——分数只覆盖"会不会真的画错"，图标和配色它一概不管。
4. 分数不再明显提升、或改动已经满足用户描述的需求时，在总结里给出预览 HTML 的路径、最终分数
   和还剩下的已知问题（如果有）。预览文件在第 2 步每次调用时就已经是最新的了，不需要再渲染一次。
   - 这份 HTML 里嵌了完整的拓扑模型（`window.TOPO`），既是给人看的图、也是存档：下次用户拿着
     它回来接着改时，可以直接从里面取出模型，不必要求用户找出 `.topo.json`。
   - 用户要"导出/存成文件/给我一份图"时，用 `topology__export_diagram`。两种格式**用途不同，
     按用户要什么选**：
     - `format="svg"`——矢量图，用于查看、嵌进文档、发给别人看。**只能看，不能改结构。**
     - `format="vsdx"`——**可在 Visio / 亿图（EdrawMax）里继续编辑**：设备是真正的 Visio 形状，
       连线是粘在设备上的连接器，拖动设备时连线会跟着走。用户说"我要拿去改""给我 Visio 版"
       "要能编辑"时用这个。
     - `format="pptx"`——**塞进汇报材料，用 PowerPoint / LibreOffice Impress 直接改**。
       用户说"放到 PPT 里""汇报要用""做成幻灯片"时用这个。三点要跟用户讲清楚：
       ① 固定 16:9 一页，图等比缩放居中——不按图的大小定页面尺寸，那样的片子塞不进材料；
       ② **不含图例**，颜色/线型的含义没有随文件带出去，汇报时要口头说明，或另外给一份 svg；
       ③ 连线粘在设备的**边中点**上，同一条边上的多条线会汇到一点，不像 svg 里沿边散开。
       拖动设备连线会跟随，但端口位置不如 svg 精确。
     png/pdf 暂未实现，调用会明确报错。它由引擎直接
     把文件写到你给的 `output_path`，**只返回路径和字节数、不返回文件内容**——不要试图
     读回内容再转存，也不要把内容复述进对话。导出完成后把路径告诉用户即可。
     模型同样支持 `topology_json` / `model_path` 二选一。**模型没变就给 `model_path`**——
     刚 `draw` 完又把同一份模型原样传一遍是纯浪费。
   - **视觉细节可以按用户要求调**，全都写进模型（`meta` 或编码表，跟着模型走、下次渲染还在），
     **不是渲染工具的调用参数**。具体怎么改、以及哪些改不了，查
     `skill_executor__read_file("references/change-recipes.md")`——颜色、图标、字、大小间距、
     区域框、图例、端口连线，按用户的说法分节列好了。
     颜色不写就自动分配，通常不用主动配；**字号、字体、背景色不开放**。
   - **走线方式当前只支持 `direct`（两点直线），这是缺省值，通常不用管它。**
     正交折线（`orthogonal`，横平竖直、直角拐弯）的引擎已经在了，但产出还不达标——多条线
     汇聚到同一台设备时会共线重叠，几根线叠在一起分不清，所以暂时关闭。传 `routing="orthogonal"`
     或在模型里写 `meta.routing: "orthogonal"` 都会被明确拒绝（BAD_ARGS）。
     **用户要求"线要横平竖直/走直角"时，如实告诉他这个能力正在修复、当前只能出直线图**，
     不要试图用别的字段绕过去，也不要默默画成直线当作满足了需求。
     **忘了回写会被工具当场点出来**：`draw_topology`/`export_diagram` 的返回值里有 `warnings`
     数组，你传的 `routing` 跟模型 `meta.routing` 不一致时会出现一条 `ROUTING_NOT_PERSISTED`。
     看到它就回去改 `meta.routing`，别只是把图交出去——不然图是直线、模型说自己是正交，
     下次重新渲染会无声地变回去。
   - **`export_diagram` 的 `output_path` 必须是绝对路径**（相对路径会被拒，报 BAD_ARGS）。
     引擎子进程的工作目录是引擎自己的安装目录，不是你的工作目录：写相对路径文件会落到
     安装目录里，工具照样返回成功和字节数，但用户在工作区里根本看不到这个文件。

**关键约束：**

- `encoding` 里出现的设备角色/链路类型/接口类型/区域类型，必须先在对应的 `xxxTypes` 表里有一条
  条目，否则会被判定引用了未定义的编码——条目里的 `legend` 文案本身允许留空，不是必须写。
- `haPair` 是可选的语义标注（声明这两台设备互为冗余对），DRC 不检查它、不会因为没配而报错——
  但如果用户明确要求了 HA/冗余，你仍然应该按需求把 `haPair` 写对（双向互指），这是语义对齐的
  要求，不是为了让 DRC 分数好看。
- 同一层内旁挂的设备（比如单独一台旁挂防火墙）用 `satelliteOf` 声明依附对象，贴靠距离用
  `satelliteGap` 调（缺省 90，量的是两个原始盒之间的净空；两边若都是 zone，各自虚线框还会外扩
  `zonePad`，实际可视留白 = `satelliteGap` − 2×`zonePad`）；同层的左右**排序**直接用声明顺序控制
  （顶层用 `devices` 数组顺序，zone 内用 `members` 顺序）——这个顺序是引擎正式承认的排序依据，
  稳定可靠、重算不变（旁挂解决"贴着谁"，声明顺序解决"谁先谁后"，两件事不同）。
- 想表达"这条链路接在设备的哪个逻辑端口"时，在对应的 `links[i]` 上加 `aPort`/`bPort`
  （自由文本，比如 `"Gi0/0/1"`）——纯逻辑标签，不代表物理端口、没有"一个端口只能接
  一根线"的约束，两条链路引用同一个端口标签是合法声明，不是错误。这个字段不影响布局
  坐标：端口锚点在图上画在设备哪条边、什么位置，永远由"离对端最近"的现有算法决定，
  跟端口标签本身无关。可选字段，不设不影响任何 DRC 判定。
- 用户要求整体调密调疏时：`meta.rowGap`（相邻行净空，缺省 78）/`meta.hGap`（同行相邻元素净空，
  缺省 46）/`meta.zonePad`（zone 虚线框相对成员包围盒的外扩距离，缺省 18）——都是净空(clearance)
  语义，行内内容多高都吃不掉这个留白。
  三条会让你以为"引擎没执行"的坑（展开说明见 `references/change-recipes.md` 第 4 节）：
  **① zone 自己的 `rowGap`/`hGap` 只管它内部成员之间，不管它和兄弟之间**——要拉开 A、B
  两个 zone 得写在它们的**父容器**上；**② 顶层 zone 之间只能用 `meta.hGap`**（根区域隐式、
  没有可写的父容器）；**③ 两个 zone 之间的可视留白 = `hGap` − 2×`zonePad`**，缺省 46−36=10，
  调一点点看不出来。另外字段名拼错（`hgap`/`h_gap`）会被静默忽略——改完没变化时先核对
  拼写和写在了哪一层，再怀疑引擎。
- 图例相关的请求（隐藏、挪位置、只列某几组、图示大小、改文案）见
  `references/change-recipes.md` 第 6 节。有一条要特别记住：**图例内容是从"图里实际用到了
  哪些编码条目"自动派生的，不能逐条挑**——用户要求"图例里单独去掉某一条"时，做不到，
  如实说明。DRC 报告不会出现在渲染出的图上——它只通过 `draw_topology` 的返回值给你，
  没有任何字段能控制"要不要把 DRC 报告画进图里"，因为它压根不属于图纸的一部分。
- 需求含糊时（比如不确定具体要几层、要不要冗余）优先调用 `control__ask_user` 澄清，不要自行猜测
  生成一份可能不符合预期的大改动。
