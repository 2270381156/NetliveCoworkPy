# 写作指南：把领域经验转换成 Skill 指令

本指南教模型如何把访谈笔录转换成高质量的 skill 指令。在开始写输出 skill 的 SKILL.md 之前读取。

---

## 核心原则：知识源头是用户

用户拥有知识。模型的角色是捕捉、结构化、润色——不是补充领域内容。输出 skill 里的每一条指令都应该能追溯到用户说过或确认过的内容。

当用户的指令看起来不完整或有疑问时，追问而不是自己从训练数据里补。一个准确但不完整的 skill 远好过一个完整但不准确的。

---

## 语气与语调

### 祈使句形式

输出 skill 的所有指令必须用祈使句（动词开头，直接指令，无主语）。

**正确（祈使句）：**
```
先检查管辖法律条款。
识别任何异常或单方倾向的条款。
对超出行业惯例的条款做标注。
```

**错误（第二人称）：**
```
你应该先检查管辖法律条款。
你需要识别异常条款。
用户可能会想标注单方倾向的条款。
```

**错误（被动/虚弱）：**
```
管辖法律条款应被检查。
建议识别异常条款。
单方倾向的条款可以被标注。
```

### 为什么祈使句重要

祈使句：
- **更短**——字数少，读取快
- **不模糊**——没有歧义，谁做什么一清二楚
- **可直接执行**——模型不需要翻译就能直接照做

### 专业但不学究

沿用用户的专业术语，但句子保持直接、可执行。

**太学究：**
```
在完成初步文档审查之后，着手对涉及保密义务的合同条款进行全面评估。
```

**太随意：**
```
好了现在看看保密那块，有啥不对劲的说出来。
```

**刚好：**
```
检查保密条款。确认保密范围是否合理，保密期限是否明确界定。
```

## 保留用户的专业用语

用户对工作有精确的词汇。保留它。不要「翻译」成大白话——那会损失含义。

| 用户说 | 保留原样 | 不要替换成 |
|--------|---------|-----------|
| 「做方差分析」 | 「对预算与实际数做方差分析」 | 「把数字对一下」 |
| 「检查有无水肿体征」 | 「检查有无水肿体征（皮下组织积液引起的肿胀）」 | 「看看有没有肿」 |
| 「审查赔偿条款」 | 「审查赔偿条款」 | 「看看谁赔谁那部分」 |
| 「核对试算平衡表」 | 「核对试算平衡表」 | 「看看数字平不平」 |

如果用户用的术语模型可能不熟悉，加一个简短括号说明：「检查有无水肿体征（皮下组织积液引起的肿胀）。」但默认保留用户的原词。

## 把访谈笔录转换成指令

### 模式 1：顺序步骤

当用户描述一个序列（「我先做 A，然后 B，然后 C」）：

**访谈笔录：**
> 「我先快速过一遍整个合同，搞清楚这是什么类型的交易。然后仔细看定义条款，因为整个合同都建立在术语定义的基础上。然后逐条审查，看有没有不寻常的地方。」

**转换成：**
```
## 工作流程

### 第一步：浏览合同确定交易类型
快速通读整份合同。识别合同类型（保密协议、服务协议、采购协议等）和交易基本结构。注意当事方和合同目的。

### 第二步：仔细阅读定义条款
仔细阅读定义条款。合同的每个关键术语都依赖此处的定义。注意任何异常宽泛、狭隘或单方倾向的定义。

### 第三步：逐条审查
按顺序审查每一条实质性条款。对每一条，识别：
- 该条款创设了什么义务或权利
- 对此类合同而言是否属于标准条款
- 是否有任何用语显得异常或单方倾向
```

### 模式 2：条件逻辑

当用户描述判断分支（「如果 X，我做 Y；否则做 Z」）：

**访谈笔录：**
> 「如果合同里有仲裁条款，我会特别留意仲裁地和仲裁规则。如果没有仲裁条款，我就检查管辖法律条款是否指定了对客户不便的法院。」

**转换成：**
```
### 第四步：审查争议解决条款

**如果合同包含仲裁条款：**
- 确定仲裁地（城市和州/省）
- 注明适用的仲裁规则（贸仲、北仲等）
- 判断仲裁地和规则对客户是否合理

**如果合同不包含仲裁条款：**
- 检查管辖法律条款
- 确定哪些法院拥有管辖权
- 标注对客户不便或成本过高的管辖地
```

模式：`**如果 [条件]：**`，后接项目符号列出的动作。条件要具体、可观察。

### 模式 3：质量把关

当用户描述怎么判断做得对不对：

**访谈笔录：**
> 「发给客户之前，我确保覆盖了所有主要风险领域：保密范围、期限与终止、知识产权归属、责任上限、赔偿条款。少了一个，审核就不算完。」

**转换成：**
```
## 质量检查

交付前，逐项验证：

- [ ] 保密：保密义务的范围和期限已识别并评估
- [ ] 期限与终止：合同期限和退出条件已注明
- [ ] 知识产权归属：各方拥有什么权利已明确识别（含已有知识产权和开发中知识产权）
- [ ] 责任上限：任何责任限制已识别，尽可能量化
- [ ] 赔偿：任何赔偿义务已识别，赔偿范围已评估
```

### 模式 4：从反面案例提炼边界

当用户描述过去出过的错：

**访谈笔录：**
> 「我见过有人把每一条都标成"有问题"——客户收到一份 20 页的备忘录，完全不知道什么才是真正要担心的。必须有优先级。只标注真正异常或有风险的地方。」

**转换成：**
```
### 绝对不可违反的规则

- **绝不**把每条条款都标为有问题。必须排优先级——只提出真正异常、单方倾向或对客户有风险的问题。
- **绝不**输出不带优先级排序的审核意见。最重要的问题必须排在最前面。
```

## 如何写示例

### 输入/输出格式

每个示例展示具体的输入和期望的输出。格式简单直接：

```
### 示例 1：标准的双向保密协议

**输入：**
一份 5 页的双向保密协议，甲方为软件创业公司，乙方为潜在投资方。关键条款包括：3 年保密期限、双向不招揽条款、适用加州法律。

**输出：**
## 保密协议审核意见

**文件：** 甲方与乙方之间的双向保密协议
**总体评价：** 整体平衡。签署前有三项值得关注。

### 主要关注点

1. **保密期限（第 3 条）：** 3 年为标准期限，但第 3.2 条将"商业秘密"的保密义务设为永久。请确认仅真正的商业秘密受永久保护。

2. **不招揽条款（第 5 条）：** 条款为双向，公平。但适用范围是"任何员工"而非"参与本次交易的员工"，比标准做法更宽泛。

3. **管辖法律（第 8 条）：** 适用加州法律，管辖地在旧金山。标准和合理。

### 无关注事项

- 保密信息定义（第 1 条）：标准范围
- 材料返还（第 6 条）：合理，30 天期限
- 无知识产权转让或许可：符合保密协议惯例
```

### 好示例的标准

1. **输入真实：** 输入描述像真实用户会有的东西——包含具体细节（公司类型、文件长度、具体条款）
2. **输出完整：** 展示完整交付物，不是片段
3. **具体引用：** 关注点标注了具体条款或段落引用
4. **排序：** 最重要的问题排在最前面
5. **可操作：** 每个关注点解释问题是什么，而不仅是「这里有问题」

### 示例中要避免什么

- 通用占位内容（「某公司」，无任何具体信息）
- 只说「审核完毕——无问题」的输出（没帮助）
- 示例之间太相似（应覆盖不同场景）
- 过于冗长的示例（细节淹没了模式）

## 常见写作错误

### 错误 1：指令模糊

**差：**
```
仔细审核文件并报告任何问题。
```

**为什么差：** 没有定义「仔细」是什么、「问题」是什么、报告什么格式。

**好：**
```
从头到尾阅读文件。对每一条条款，检查：
- 该条款是否为客户创设了义务？
- 义务是否明确界定且范围有限？
- 是否有任何异常宽泛或单方倾向的措辞？
每项关注点标注条款引用和通俗解释。
```

### 错误 2：把说明和理由混在一起

指令只说做什么。理由放括号里，或移到单独的注释。

**差：**
```
你需要检查赔偿条款，因为赔偿真的很重要，如果太宽泛了客户可能会为不是自己干的事承担责任，这很不公平而且可能极其昂贵。所以一定要仔细看，有问题要报告。
```

**好：**
```
检查赔偿条款。注明赔偿范围是否限于客户自身行为，还是扩展到了第三方索赔。标注任何要求客户为对方过失提供赔偿的义务。
（原因：过于宽泛的赔偿条款可能让客户承担重大责任。）
```

### 错误 3：空话和套话

**差：**
```
要仔细。高度关注细节。运用最佳判断。遵循最佳实践。确保高质量输出。
```

**为什么差：** 什么都没说。每个 skill 都可以写这些。零指导价值。

**好：**
不写「要仔细」，在检查清单里列出要检查的具体项。不写「用最佳判断」，把判断标准写出来。每条指令必须是可证伪的——如果模型跟没跟这条指令做，能看出来差别。

### 错误 4：假定模型具备法律/医学/会计专业知识

Skill 应该把领域知识显式化，而非假定模型已经有这些知识。

**差（假定知识）：**
```
检查任何异常条款。
```

**好（显式化知识）：**
```
逐条检查合同条款。与行业标准对照：
- 竞业禁止：应在时间和地域上有限制（通常 1-2 年）
- 不招揽：应仅适用于参与该业务关系的员工
- 保密：期限应明确（通常 2-5 年，非永久）
```

### 错误 5：语气像机器人

指令应该专业，但不过于生硬。

**太像机器人：**
```
执行文件接收程序。解析法律实体标识符。执行条款级分析子程序。将分析结果输出到摘要格式。
```

**太随意：**
```
嘿就随便翻翻这个合同，有啥不对劲的跟我说一声哈。
```

**刚好：**
```
打开文件，识别合同类型。注明当事方和签署日期。然后逐条审查。对每条条款，判断是否属于该类合同的标准条款。
```

## SKILL.md 和 references/ 的分界线

当指令变得又长又详细时，考虑是否应该放到 references/ 中而非 SKILL.md。

**留在 SKILL.md 的：**
- 核心流程（什么步骤，按什么顺序）
- 判断点与条件逻辑
- 质量检查清单
- 1-2 个核心示例
- 关键边界和安全规则

**移到 references/ 的：**
- 详细的参考资料（行业标准、法规定义、医学指南）
- 长示例（超过约 200 字每个的）
- 背景知识——有用但不一定每次都需要
- 边缘情况和少见场景

经验规则：如果某条信息每次跑这个 skill 都必须要用到 → SKILL.md。如果是有时候需要、有时候不需要的细节 → references/，在 SKILL.md 中给出读取指引。

## 给用户看草稿前的自检清单

向用户展示输出 skill 草稿之前，逐条验证：

- [ ] 每条指令使用祈使句（动词开头，没有「你应该」）
- [ ] 用户的专业术语原样保留（未翻译成大白话）
- [ ] 每个步骤具体、可证伪（可以判断是否被执行了）
- [ ] 示例展示了真实、具体的输入和输出
- [ ] 边界明确了什么不要做
- [ ] 质量检查具体，没有空话
- [ ] 语言匹配用户的专业水平和说话风格
- [ ] 输出 skill 中没有任何计算机术语
- [ ] 文档可快速浏览（清晰的标题、短段落、列表）
