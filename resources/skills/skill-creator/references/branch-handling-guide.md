# 分支处理指南

用于梳理逻辑阶段（第 3 步）：当用户的流程描述中出现大量「如果……就……」分支时，如何处理。

## 核心原则

**发现大量分支时，不要直接整理记录下来。** 大量分支是一个信号——说明流程本身还没想清楚，或者内容写错了地方。

## 三问法

按以下顺序判断每一个分支集群：

### 第一问：能不能收敛？

大部分分支是因为用户把「特殊情况」和「主流程」混在一起描述。

**做法：** 引导用户区分主路径和例外。

> "我注意到这个流程里有很多'如果……就……'的情况。我们先理出最常见的情况——就是你 80% 的时间会走的那条路。剩下的特殊情况我们单独处理。"

**结果：**
- 能收敛 → 找出覆盖 80% 场景的主路径写入 SKILL.md，其余当作例外简单处理或忽略
- 不能收敛（分支之间差异太大、没有公共主干）→ 进入第二问

### 第二问：是不是多个 skill？

如果分支之间的差异太大、根本没有公共主干，说明这是两件不同的事。

**做法：** 向用户提出拆分建议。

> "这些分支之间的处理方式差异很大，实际上可能是两种不同的工作。比如 [分支A的场景] 和 [分支B的场景]，它们的步骤、输出、判断标准都不一样。拆成两个独立的 skill 会更清晰，每个 skill 的流程更简洁。你觉得呢？"

**结果：**
- 用户同意拆分 → 分别创建多个 skill
- 用户坚持放在一起 → 进入第三问

### 第三问：是不是应该写成脚本？

如果分支是确定性的路由逻辑（不涉及灵活判断），LLM 执行不可靠，应该写成脚本。

**做法：** 识别确定性路由的特征。

> "这部分逻辑——'如果是 A 类型就做 X，如果是 B 类型就做 Y'——属于规则路由，每次结果应该完全一样。我来写一个自动工具处理这部分，保证不会走错分支。"

**结果：**
- 确定性路由 → 写成 scripts/，在 SKILL.md 中调用脚本
- 原则性灵活判断 → 可以保留在 references/ 中

## 允许保留在 SKILL.md 的分支

**只有在分支很少（≤2 个）且无法通过以上三问消除时**，才允许保留在 SKILL.md 里。

保留时，使用显式格式，不要埋在句子里：

```
根据 [判断条件]：
- 如果 [情况A]：执行 [操作A]
- 如果 [情况B]：执行 [操作B]
```

**错误写法（埋在句子里）：**
> 检查文档类型，如果是 PDF 就用 pdf 工具处理然后提取文本，如果是 Word 就直接读取内容。

**正确写法（显式列出）：**
> 根据文件类型：
> - 如果文件是 PDF：运行 `scripts/extract_pdf_text.py <文件路径>`
> - 如果文件是 Word：直接读取文档内容

## 分支处理决策树

```
发现大量分支
    │
    ├─ 能收敛到主路径 + 例外？
    │   → 是：SKILL.md 只写主路径，例外简单标注
    │
    ├─ 分支之间差异太大，没有公共主干？
    │   → 是：建议拆成多个独立 skill
    │
    └─ 是确定性路由逻辑？
        → 是：写成 scripts/，代码精确路由
        → 否：保留在 references/（原则性灵活判断）
```

## 向用户说明分支处理

在汇总确认时，用业务语言解释处理方式：

**收敛的情况：**
> "你的流程里大部分时候走的是 [主路径描述]。其他特殊情况——比如 [举例]——我们作为例外处理，在 skill 里简单标注一下就行。"

**拆分的情况：**
> "我发现这些场景实际上处理方式完全不同——[场景A] 和 [场景B] 在步骤、判断标准和输出上都不一样。建议拆成两个独立的 skill：一个专门处理 [A]，一个专门处理 [B]。这样每个 skill 都很清晰，不容易出错。"

**写脚本的情况：**
> "[这部分——'根据 [条件] 决定走哪条路'——每次的判断规则是一样的，我来写一个自动工具处理，保证不会出错。"
