# 脚本识别指南

用于写作阶段：判断访谈中收集到的哪些逻辑需要写成脚本，而不是放进 SKILL.md 或 references/。

## 核心判据

**这件事的结果必须精确且每次都一样吗？**

- 是 → 写成脚本。让代码精确执行，保证每次结果一致。
- 否 → 写成 references/ 中的原则指导。让模型理解后灵活运用。

## 8 种必须写脚本的场景

满足以下任一条件，就应该写成脚本：

| # | 场景 | 识别信号 | 示例 |
|---|------|---------|------|
| 1 | **批量处理文件** | 「把文件夹里每个 PDF 都…」「遍历所有 Excel…」 | 批量旋转 PDF、批量提取文本 |
| 2 | **从特定格式解析数据** | 「从日志里提取…」「解析配置文件」「读取报表」 | 解析 Apache 日志、提取 JSON 字段 |
| 3 | **生成固定格式的文档或报告** | 「按照这个模板生成…」「填充表格」 | 用模板生成 Word 报告、填充 Excel |
| 4 | **核对/比较两份数据** | 「对比 A 和 B」「找出差异」「检查是否一致」 | 对比两份配置、检查数据差异 |
| 5 | **统计/汇总/计算** | 「统计数量」「计算总和」「汇总分类」 | 按类别统计金额、计算占比 |
| 6 | **读写结构化数据文件** | 「读取 CSV」「导出 JSON」「处理 Excel」 | CSV 分类、JSON 转换、Excel 汇总 |
| 7 | **需要精确控制的重复逻辑** | 「反复执行直到条件满足」 | 循环检查直到文件生成 |
| 8 | **确定性分支路由** | 「如果是 A 类型就走 X 流程，如果是 B 类型就走 Y 流程」 | 根据文件扩展名选择不同处理方式 |

### 场景 8 特别说明：确定性分支路由

这是最容易被误放进 SKILL.md 的场景。当用户描述中有多个「如果是 X 就做 Y」的硬分支时：

- **不要**写成 SKILL.md 里的条件语句 — LLM 执行 if/else 分支不可靠，可能走错分支
- **不要**写成 references/ 里的分支树 — 同样的不可靠问题
- **应该**写成脚本 — 代码精确路由，每次结果一致

**判断方法：** 这个分支是「原则性的灵活判断」还是「确定性的规则路由」？
- 原则判断（「根据风险程度决定怎么做」）→ references/，模型灵活把握
- 规则路由（「PDF 文件走 A 流程，Word 文件走 B 流程」）→ scripts/，代码精确执行

## 脚本写作规范

- **语言：** Python（最通用，模型可以直接读写）
- **文件命名：** 动词+对象，例如 `parse_log.py`、`generate_report.py`、`classify_expense.py`
- **开头注释（必须）：**
  ```python
  # 功能：[这个脚本做什么]
  # 用法：python scripts/xxx.py <参数1> <参数2>
  # 输出：[输出到哪里，什么格式]
  ```
- **注释用中文**（面向用户时）
- **在 SKILL.md 的对应步骤里写调用方式：** 「运行 `scripts/xxx.py <输入文件> <输出文件>`」
- **不允许硬编码。** 路径、文件名、数值全部从参数或配置传入，不能写死在代码里。发现硬编码必须重写。

## 多个脚本时

创建 `scripts/README.md`，列出所有脚本的功能和调用方式：

```markdown
# Scripts 说明

## parse_input.py
- 功能：解析用户提供的 CSV 文件，提取交易记录
- 用法：python scripts/parse_input.py <输入文件路径> <输出文件路径>
- 输出：结构化的 JSON 数据

## generate_report.py
- 功能：基于分类结果生成汇总报告
- 用法：python scripts/generate_report.py <分类结果JSON> <报告输出路径>
- 输出：Markdown 格式的汇总报告
```

## 向用户说明脚本

用户不需要懂代码，但需要知道脚本在做什么。用这个话术：

> "我注意到你流程里有一部分需要精确处理——[描述场景，如：「每次根据文件类型选择不同的处理方式」]。这部分我来写一个自动工具（脚本），保证每次执行结果都一致。你不需要关心代码，只需要知道这个工具做什么、什么时候运行。"

然后告诉用户三件事：
1. **这个工具做什么**（一句话，用他的业务语言）
2. **什么时候会自动运行**（在流程的哪一步）
3. **如果出问题怎么办**（「告诉我哪里不对，我来修改」）

## 不该写成脚本的情况

以下情况**不要**写成脚本，应该放在 references/ 里：

- 需要根据上下文灵活判断的（「根据客户风险偏好决定…」）
- 标准本身会变化的（「参考最新行业指南…」）
- 涉及主观评价的（「评估代码质量…」）
- 只有 1-2 个简单条件且用户确认不需要精确控制的

**简单记忆：** 需要「灵活判断」→ references/，需要「精确一致」→ scripts/。
