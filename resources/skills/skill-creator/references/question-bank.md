# 问题库：按步骤分类的访谈追问

当第 1-5 步的标准问题问不出清晰答案时，从这里取用扩展追问。也包含按职业定制的切入问题和模糊回答的替代策略。

---

## 第 1 步：定场景

目的：搞清楚 skill 在什么情况下用、怎么触发。

### 主要问题

1. 「你上一次想用我帮忙做这件事是什么时候？当时你正在做什么？是什么让你觉得'我需要帮忙'？」
2. 「你会怎么开口要这个帮助？用你最自然的说法——你日常怎么说就怎么说。」
3. 「有没有特定类型的文件、数据或情况，一出现我就知道'该用这个 skill 了'？」

### 模糊回答时的替代问法

| 用户说 | 试试这样追问 |
|--------|------------|
| 「就是处理合同的时候」 | 「上次你处理的合同是什么？你打开文件第一眼看什么？」 |
| 「就是日常审核工作」 | 「你做得最多的那种审核是什么？上周做了三次的那种？」 |
| 「客户问我问题的时候」 | 「客户问得最多的问题是什么？闭着眼睛都能回答的那个？」 |
| 「各种情况都有」 | 「咱先挑一个——最近一次你做完后觉得'这活真不想再手工干了'的是什么？」 |
| 「我也说不清楚」 | 「换个角度——你开始干活的时候，电脑屏幕上第一个打开的是什么文件？」 |

### 「最近一次具体实例」策略

当一切抽象追问都失效时，彻底放弃抽象，锚定到一个具体实例：

- 「先不说一般情况。就讲一次你实际做这件事的经历。当时是什么情况？客户/病人/客户给你发了什么？你拿到后做了什么？」
- 「能跟我讲讲上周二下午你干了什么活吗？有什么东西送到你手上了？」

锚定到具体实例几乎总是能问出抽象问法问不出的细节。

### 按职业的切入问题

| 职业 | 定制开场问题 |
|------|------------|
| 律师 | 「客户最常发给你审什么类型的文件？合同、诉状、监管文件，还是别的？」 |
| 医生 | 「这是什么类型的接诊场景？初诊、复诊、检查结果解读，还是术前评估？」 |
| 会计师 | 「什么财务文件或报告会触发你开始这项工作？银行对账单、客户表格、税务表单？」 |
| 工程师 | 「什么设计文件、规格书或问题报告会启动这个过程？CAD 图纸？需求文档？故障报告？」 |
| 教师 | 「你通常处理的学生作业或教学材料是什么？论文、习题集、教案、试卷？」 |
| 咨询顾问 | 「客户最常要你交付什么？PPT？书面分析？建议书？」 |
| 房产中介 | 「你最常处理的房源文件或信息是什么？」 |
| HR/招聘 | 「你最常审什么候选人材料？简历、求职信、测评结果？」 |
| 科研人员 | 「你处理的研究产出是什么类型？论文、实验数据、文献、基金申请书？」 |

### 何时可以进入下一步

用户至少描述了一个具体场景，你能：
- 说出触发条件（用户在看什么、做什么时需要帮助）
- 描绘出输入（什么文件、文档、数据进来了）
- 理解上下文（用户在什么情境下）

---

## 第 2 步：立目标

目的：明确做成什么样算好。

### 主要问题

1. 「如果我把这件事做得很完美，结果会是什么样？越具体越好——是一份标注过的文档？一张检查清单？一份分析报告？一份填好的表？」
2. 「如果把这个任务交给新人同事，你会告诉他最终交付物里必须包含什么？」
3. 「你怎么判断做得对还是不对？可接受和不可接受的区别在哪？」

### 模糊回答时的替代问法

| 用户说 | 试试这样追问 |
|--------|------------|
| 「一份好的分析」 | 「咱们先说分析报告里的一个部分——你拿到报告第一眼看什么？什么告诉你这个做得不错？」 |
| 「就是常规报告」 | 「我给你两份报告，一份好一份差。你看什么来判断？」 |
| 「看着办吧」 | 「你以前做过的哪次最满意？能给我看看或者描述一下吗？」 |
| 「看到了我就知道」 | 「行。那我根据你前面说的先猜一下输出长什么样——[具体描述]。差不多吗？」 |

### 「抛草案」策略

如果用户实在说不清输出长什么样，根据已有的信息先抛一个草案：

> 「根据你现在说的，我觉得输出可能是这样的：[一段具体描述，有结构、有内容]——差不多吗？」

给用户一个可以 react 的东西——哪怕猜错了——也比反复问「你到底想要什么」更有效。

### 各职业常见输出格式

| 职业 | 常见输出格式 |
|------|------------|
| 律师 | 标注文件、问题清单、风险摘要、条款对照表 |
| 医生 | 患者摘要、SOAP 笔记、鉴别诊断列表、检查结果概要、转诊信 |
| 会计师 | 分类后的表格、会计分录、差异分析报告、对账汇总 |
| 工程师 | 设计评审意见、规格合规清单、故障分析报告、测试报告 |
| 教师 | 评分表、学生反馈评语、教案、试卷分析 |
| 咨询顾问 | PPT、执行摘要、建议书、SWOT 分析、路线图 |

### 何时可以进入下一步

用户已经：
- 描述了输出格式（文档类型、结构、关键组成部分）
- 给出了至少一个质量标准（怎样算好、怎样算差）
- 确认（或纠正）了你对「完成是什么样」的理解

---

## 第 3 步：理规则

目的：抽取一步一步怎么做的过程和判断逻辑。

### 主要问题

1. 「你自己做这件事的时候是怎么做的？从最开始说起——第一步你做什么、看什么？」
2. 「有没有哪些规则或检查是必须做的？一旦跳过就会出错的那种？」
3. 「有没有碰到不同情况要做不同处理的地方？比如'如果文件里有X，就做Y，否则做Z'。」
4. 「做完之后你检查什么来确认没问题？」

### 模糊回答时的替代问法

| 用户说 | 试试这样追问 |
|--------|------------|
| 「我也说不好，看经验」 | 「有没有见过谁把这事做砸的？他漏了什么？」 |
| 「看具体情况」 | 「咱们先讲最常见的情况。这种情况你怎么做？例外后面再补。」 |
| 「就按常规流程走」 | 「假设你明天休假，同事替你，你有10分钟给他写个清单，上面写什么？」 |
| 「做久了自然会判断」 | 「哪个东西最重要——如果你只能检查一件事，你查什么？」 |

### 「替班清单」策略

这是从做熟了的用户脑中挖出隐性规则最有效的方法：

> 「假设你明天休假，一个同事替你干活。你有 10 分钟给他写个防出错清单。上面写什么？」

这把问题从「解释你的专业知识」（难）变成了「防止你不在的时候出事故」（易）。最容易问出关键路径上的东西。

### 「别人做砸过」策略

反面案例往往比正面规则更容易表达：

> 「有没有见过别人把这事做砸的？他做了什么？漏了什么？后果是什么？」

这能问出：
- 必须检查的东西（那个人漏掉的）
- 判断标准（那个人判断错的）
- 质量标准（为什么那个输出不可接受）

### 抽取条件分支

当用户说「看情况」时，按以下顺序追问：

1. 「看什么情况？」→ 找出条件
2. 「[条件]成立的时候你怎么做？」→ 找出分支 A
3. 「[条件]不成立的时候你怎么做？」→ 找出分支 B
4. 「还有其他可能吗？」→ 找出额外分支

把每个分支写成具体的「如果 [可观察到的条件]，那么 [具体动作]」。

### 大量分支怎么办

用户描述里出现大量「如果A就X，如果B就Y」的分支时，参考 `references/branch-handling-guide.md` 的三问法处理，不要直接全部记录。

### 何时可以进入下一步

用户已经：
- 说出了一个至少 3-4 步的序列
- 给出了至少一个必须遵守的规则
- 描述了至少一个判断分支点

---

## 第 4 步：给示例

目的：收集具体的输入输出案例。

### 主要问题

1. 「能讲一个真实的例子吗——某次你实际经手的工作？什么东西进来了，你产出了什么？我来帮你写格式化的示例，你审就行。」
2. 「你见过经验不够的人做这件事时最容易犯什么错？」

### 模糊回答时的替代问法

| 用户说 | 试试这样追问 |
|--------|------------|
| 「涉及客户隐私，不能给你看」 | 「完全理解。能描述一个改掉真实信息的虚构例子吗？人名金额全换，结构留下就行。」 |
| 「每个案例都不一样」 | 「挑一个最常见的类型。特殊的情况我们可以后面再加第二个示例。」 |
| 「手边没有现成的例子」 | 「哪怕只说说一个典型的输入第一段或第一条通常长什么样，就很有用了。」 |

### 「我来写，你审」策略

不要让用户写示例。这样说：

> 「你就用自己话描述一下——客户发了什么、表格长什么样、文档里写了什么——然后说你做了什么。格式我来整理，整完给你审。」

用户出原材料，我做格式化和整理。

### 保密问题处理

很多专业人士不能分享真实案例。应对方式：

1. 「把人名、日期、金额全改成假的。我只要看结构。」
2. 「用一个完全假设但模式相同的场景。」
3. 「如果连案例类型都不能说，那能描述一下一个典型输入'通常'长什么样吗？」

### 反面案例的价值

用户往往觉得描述失败比描述成功更容易：

- 「最常见的错误是什么？」
- 「一个差的输出长什么样？什么会让你说'这个做得不对'？」
- 「什么边缘情况最容易让人踩坑？」

这些往往能问出第 3 步没问出来的规则和边界。

### 何时可以进入下一步

至少一个正向示例（输入 → 输出），最好还有一个常见错误或反面案例。用户已确认示例真实可信。

---

## 第 5 步：划边界

目的：明确什么不要做、什么时候该拒绝、什么错绝不能犯。

### 主要问题

1. 「这个 skill 不做什么？哪些任务看起来长得像但其实不该用这个 skill 做？」
2. 「什么时候我应该说'这个我做不了'或者'我得先知道更多才能继续'？」
3. 「我如果犯什么错最要命？什么错会让你说'以后再也不能这么干了'？」
4. 「如果用户给的信息不全或不清楚，我应该追问什么？」

### 模糊回答时的替代问法

| 用户说 | 试试这样追问 |
|--------|------------|
| 「用常识判断就好」 | 「我来举一个边界例子——[具体场景]。这个我该管还是不该管？」 |
| 「应该很明显的」 | 「对 AI 来说不一定明显。能给我一个我应该明确拒绝的具体例子吗？」 |
| 「就像专业人士那样做」 | 「不同职业边界不同。在你的领域，我能帮到什么程度，再往下就需要持牌的专业人士了？」 |

### 「最坏情况」策略

> 「假设我完美地照着你的指令执行了——但是很死板，一点灵活性都没有，没有常识判断。最坏会出什么事？」

这让用户说出那些「太显然了所以没想到要说」的高风险约束。

### 各职业边界追问

| 职业 | 追问 |
|------|------|
| 律师 | 「法律信息和法律建议之间的线在哪？什么算越界？」 |
| 医生 | 「总结病情和做诊断之间的线在哪？边界在哪？」 |
| 会计师 | 「分类记账和做税务认定之间的区别是什么？」 |
| 工程师 | 「评审意见和需要注册工程师盖章的设计决定，分界线在哪？」 |
| 教师 | 「给反馈和打分的分界线在哪？什么需要专业判断？」 |

### 何时可以进入下一步

用户已经：
- 说出了至少 2-3 个绝对不能做的事
- 给出了至少一个我应该拒绝或追问更多信息的情况
- 指出了至少一个绝对不能犯的致命错误

---

## 步骤之间的过渡语

用这些过渡语自然衔接：

- **第 1 → 第 2 步：** 「现在我知道什么时候用这个了，咱们聊聊做成什么样算好。」（随后用 `ask_user` 一次问清第 2 步的问题）
- **第 2 → 第 3 步：** 「目标清楚了。接下来我想了解你怎么做的——从起点到成品。」（随后用 `ask_user` 一次问清第 3 步的问题）
- **第 3 → 第 4 步：** 「流程我理解了。为了确认我没理解错，咱们看一个具体例子。」（随后用 `ask_user` 一次问清第 4 步的问题）
- **第 4 → 第 5 步：** 「例子很有用。在动手写之前，咱们再说说边界——哪些事这个 skill 不该碰？」
- **第 5 → 汇总：** 「聊得很清楚了。让我把我们讨论的内容整理一下，你看看对不对。」

---

## 当用户真的卡住时

如果一个步骤用了多种方式追问用户仍然答不上来：

1. **先肯定：** 「这很正常。很多天天做这件事的人反而说不出步骤，因为太熟练了。」
2. **跳过先回来：** 「这个咱们先放一边，后面聊着聊着可能就清晰了。」
3. **抛草案：** 「根据已有的信息，我先猜一下[缺失的部分]——大概是这样吗？差不多就行。」
4. **借鉴类似案例：** 「我帮其他[律师/医生/会计师]做类似 skill 的时候，他们的[场景/目标/规则/边界]通常是[从 domain-patterns.md 参考的模式]。你的情况类似吗？」

绝不施压。一个有缺口的 skill 远好过一个塞满编造内容的 skill。
