# 内容分类规则

用于写作阶段：判断访谈中收集到的每一条信息应该放到 skill 目录结构的哪个位置。

## 7 类分法

| 这句话是什么 | 放哪里 | 面向谁 |
|------------|-------|--------|
| 做什么动作（步骤） | SKILL.md | 模型执行 |
| 为什么这样做 / 按什么标准判断（知识） | references/ | 模型阅读理解 |
| 输出长什么格式（模板） | templates/ | 模型参照格式输出 |
| 计算 / 批量处理 / 确定性路由（代码逻辑） | scripts/ | 程序精确执行 |
| 脚本要读取的数据文件（对照表、词典等） | assets/ | 脚本读取 |
| 好的输出长什么样（参考样本） | examples/ | 模型执行时参考 |
| 输入+期望输出+判断标准（测试用例） | evals/ | 修改后验证 |

## 逐类详解

### 放入 SKILL.md（步骤 — 模型照着走）

**应该放：**
- 「先做 A，然后做 B，最后输出 C」— 流程动作
- 向用户提问的句子 — 需要交互时
- 「参考 references/xxx.md」— 引用知识文件
- 「按 templates/xxx.md 格式输出」— 引用模板
- 「运行 scripts/xxx.py <参数>」— 调用脚本

**判断标准：** 这句话描述的是模型 **要做的动作**吗？是 → SKILL.md

**每步不超过 5 行。** 超过说明细节太多，应移到 references/。

### 移到 references/（知识 — 模型读懂后灵活运用）

**应该放：**
- 行业规则、法规标准、技术规范
- 评分标准、判断好坏的具体指标
- 专业术语定义
- 用户在描述步骤时插入的「因为……」「根据……规范……」
- 原则性的判断指导（不是 if/else 决策树）

**不应该放：**
- 大量 if/else 分支树 — LLM 不擅长可靠执行确定性分支，应写成脚本
- 固定的输出格式 — 应放 templates/
- 对照表、映射表等结构化数据 — 如果脚本需要读取，应放 assets/

**判断标准：** 这句话是模型 **需要知道的背景知识**才能做出正确判断吗？是 → references/

### 移到 templates/（格式 — 模型参照输出）

**应该放：**
- 输出文档的结构框架
- 固定的表格格式
- 标准措辞、固定条款
- 「结果应该包括以下字段……」以及字段的排列方式
- 报告模板、邮件模板、配置文件模板

**判断标准：** 这句话描述的是输出的**长相和结构**吗？是 → templates/

### 移到 scripts/（代码 — 程序精确执行）

**应该放：**
- 批量处理文件
- 数据计算、统计、汇总
- 格式转换（JSON/CSV/Excel/YAML 等）
- 文本解析、正则匹配
- 需要精确、可重复执行的逻辑
- **确定性分支路由**：「如果是 A 类型就调用 X，如果是 B 类型就调用 Y」— LLM 执行这类逻辑不稳定，写脚本才可靠

**详细识别指南见 `references/script-identification-guide.md`。**

**判断标准：** 这件事的**结果必须精确且每次都一样**吗？是 → scripts/

### 移到 assets/（数据 — 脚本读取，不是模型读的）

**应该放：**
- 对照表、映射表（端口→服务名、错误码→含义、国家代码→名称）
- 分类词典、关键词列表
- 图标、logo 等静态资源
- 脚本运行需要的种子数据或配置文件

**判断标准：** 这个文件是**给人（或模型）阅读理解**的，还是**给程序读取处理**的？
- 给人读 → references/
- 给程序读 → assets/

### 移到 examples/（样本 — 给模型参考什么是好输出）

**应该放：**
- 「我希望结果长这样」提供的示例文本
- 典型的完整输入输出对
- 好的案例、反面案例
- 不同场景下的输出差异示例

**与 evals/ 的区别：**
- examples/ 是「参考样本」— 告诉模型 **怎么做**，执行时参考风格
- evals/ 是「考卷」— 检验 skill **有没有做对**，修改后跑一遍验证

### 移到 evals/（测试 — 改完 skill 后验证用）

**应该放：**
- 每个用例包含：给什么输入、期望什么输出、怎么判断对不对
- 覆盖典型场景、边界情况、曾经出过错的场景

**何时需要 evals/（满足任一条件就建）：**
- Skill 逻辑有多个分支，改动后容易悄悄出错
- Skill 会被反复修改和迭代（规则经常更新）
- Skill 的输出有明确的「对/错」判断标准
- 用户反映过某个 case 之前出错过

简单、一次性的 skill 不需要 evals/。

## 向用户呈现分类结果

在写作阶段，将分类结果整理成用户可以一眼看懂的表格，**不需要解释 7 个目录的技术含义**：

```
根据我们的讨论，我计划这样组织这个 skill：

📋 主文件（SKILL.md）
   — 做什么：第1步→第2步→第3步→第4步→输出

📚 参考文档（需要时查阅）
   — [文件名].md：[里面放了什么知识，一句话]

📝 输出模板
   — [文件名].md：[输出的格式框架]

🔧 自动脚本（我来写）
   — [功能].py：[这个脚本做什么，什么时候运行]

📊 数据文件（脚本用到）
   — [文件名].csv：[什么数据]

✅ 测试用例
   — [场景名]：[测试什么情况]
```

用户只需要确认每个部分的内容对不对，不需要关心目录结构。

## 快速判断口诀

> 步骤只写动作，原则知识放 references，格式放 templates，计算和分支逻辑写 scripts，脚本的数据放 assets，好样本放 examples，考卷放 evals。
