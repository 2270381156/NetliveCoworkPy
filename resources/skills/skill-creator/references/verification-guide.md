# 验收与迭代指南

用于第 7 步：skill 文件都建好之后，怎么认真验收它、并根据结果改进。目标不是"跑一下看起来没报错"，而是**像考试一样逐条核对它有没有真的做对**，然后把结果摆给用户看、按反馈改进。

向用户沟通时不要用技术词("断言""评测"之类)——说"测试用例""检查项""通过/不通过"就行。

## 一、准备测试用例

一个用例 = 一份具体输入 + 你期望的结果。至少覆盖：

- **典型场景**：最常见的用法(必备)
- **曾经出错/最致命的场景**：用户在访谈第 5 步说的"绝不能犯的错"——专门设一个用例来防它(必备)
- **信息不全 / 边界场景**：输入残缺、格式异常时，skill 该不该追问或标"待复核"(推荐)

简单的一次性 skill 一个典型用例即可；逻辑有分支、规则会反复改的 skill 多准备几个。用例可以存到 skill 的 `evals/` 目录里，以后改完 skill 再跑一遍就能发现有没有改坏。

## 二、为每个用例写"检查项"

检查项就是一条条**客观、能逐条核对**的判断，写清楚才能一眼看懂在查什么。

- 好的检查项：「结果里把保密期限标成了 3 年」「严重违规的对话没有被判成合格」——对错分明。
- 不好的检查项：「结果写得好」「分析到位」——这种主观的东西不要硬套检查项，留给用户人工判断。
- **针对最致命的错单独写一条检查项**，确保每次都查它。

## 三、逐条核对，能用脚本就用脚本

按 skill 的步骤把每个用例实际跑一遍(有脚本就真的运行)，然后对照检查项逐条判**通过 / 不通过**，并给出**依据**——从输出或运行过程的哪里看出来的。

判定原则：
- **有确凿依据才算通过。** 表面满足不算数——文件名对但内容是空的、是错的，判不通过。
- **能机械核对的检查项，写个小脚本来核对**(比如"数到 7 段""分数算对没有")。脚本比肉眼快、可靠、下次还能用。需要人理解语义的(语气、点评是否贴切)再人工判断。
- **先看没通过的。** 没通过的才是要改的地方。

## 四、顺手审视检查项本身

核对的同时想一下：
- 有没有哪条检查项**"错的输出也能蒙混过关"**？(比如只查了文件存在、没查内容。)那就把它收紧。
- 有没有**重要的结果根本没有检查项在管**？补一条。

一条宽松的检查项通过了，比没有还糟——它会给人"已经没问题了"的错觉。

## 五、把结果摆给用户(大白话)

不开网页、不导报告，直接在对话里说清楚。每个用例讲：
- **输入**：测的是什么
- **产出在哪**：文件路径(必要时把文本结果贴出来让用户判断质量)
- **检查结果**：哪几条通过、哪几条没过，没过的用一句话说清问题

最后给一句整体小结(比如"3 个用例，2 个全过，1 个有 1 项没过")。**先讲没过的**，把用户注意力引到真正要改的地方。然后问："你看这些结果行吗？哪里要改？"

## 六、根据结果和反馈改进，然后重测

改 skill 时记住几条原则：

1. **别为这几个例子过拟合。** skill 是要被用成千上万次的，你和用户只是拿几个例子快速迭代。如果某个问题很顽固，不要堆一堆生硬的"必须/绝不"或针对这个例子的特判——换个说法、换个组织方式，往往更好。
2. **保持精简。** 没在起作用的内容删掉。如果发现 skill 让模型绕远路、做无用功，把导致它的那段拿掉再看看。
3. **多解释"为什么"。** 与其写一堆全大写的命令，不如说清这一步为什么重要——模型理解了才能举一反三。
4. **重复劳动抽成脚本。** 如果每个用例都得现写同一段处理逻辑，就把它写进 `scripts/` 一次，让 skill 以后直接调用。

改完之后**重新跑一遍所有用例**，确认修好了、而且没有把别的弄坏。

## 何时算验收完成

- 用户说满意了，或
- 所有检查项都通过、用户也没有新意见，或
- 继续改已经没有明显进步了

没跑过验收、或还有没过的检查项又没跟用户确认的，不算完成。
