# 领域模式：完整案例

三个端到端的完整案例，展示不同职业如何走完 5 步访谈并产出最终 skill。当用户的职业或任务模式与某个案例相似时，参考本章以加速访谈和构建。

---

## 案例 1：律师 — 合同审核 Skill

### 用户可能会怎么说

> 「我是做小企业法律服务的，每天花大量时间帮客户审保密协议。每份 NDA 审的套路都一样。你能学会帮我做初审吗？」

### 第 1 步：定场景

**我问：** 「上次你审 NDA 是什么情况？你当时在看什么？」

**用户说：** 「客户给我发了一份 PDF 的 NDA，对方是一个潜在供应商。客户想知道能不能签。这类活我一周接 5-10 个。」

**我追问：** 「你打开 PDF 第一眼看什么？」

**用户说：** 「先看当事方是谁，NDA 是双向还是单向的。这个直接决定了后面怎么审。」

**结果：** 场景明确——为小企业客户审核第三方 NDA。触发词：「帮我审这份NDA」「帮我看下这个保密协议」「这个能签吗」「过一遍这个协议」。

### 第 2 步：立目标

**我问：** 「如果我把这件事做得很完美，输出什么样？」

**用户说：** 「客户会收到一页纸的摘要，列 3-5 个他们真正需要担心的点。不是 20 页的法律意见书——他们不看的。客户需要知道：能不能签，不能签的话哪些条款必须改。」

**我追问：** 「好的审核和差的审核区别在哪？」

**用户说：** 「差的审核什么都标'有问题'，把客户吓死。好的审核会排优先级——告诉客户什么是真正异常的、有风险的，什么是标准的、不用管的。」

**结果：** 输出是一页通俗易懂的摘要，含优先排序后的关注点、条款引用，以及清晰的「可签/需修改/不要签」总体评价。

### 第 3 步：理规则

**我问：** 「从头到尾告诉我你怎么审的。先做什么，再做什么？」

**用户说：** 「先定类型——双向还是单向。这个决定一切。然后查：保密范围（定义多宽？）、保密期限（多久？）、排除项（什么不算保密信息？）、有没有隐藏的竞业或不招揽条款。然后看过场条款——管辖法、管辖地、救济措施。最后问自己：这份 NDA 有没有 dealbreaker？」

**我追问：** 「什么算 dealbreaker？」

**用户说：** 「永久保密期限。NDA 里藏着竞业禁止。允许对方把客户的保密信息随便转让的条款。这些是绝对不能接受的。」

**结果：** 流程结构化：(1) 识别 NDA 类型，(2) 审查保密范围/期限/排除项，(3) 检查隐藏的限制性条款，(4) 审查过场条款，(5) 整体风险评估并做 dealbreaker 筛查。

### 第 4 步：给示例

**我问：** 「能讲一个你最近审的实际例子吗？」

**用户描述** 了一份双向 NDA，5 年保密期限，标准范围，但有一个异常的不招揽条款——客户 2 年内不得招聘供应商的任何员工。用户标注了这个条款过于宽泛，建议谈判修改。

**我整理成** 示例 1。还起草了一个反面示例：单向 NDA，所有义务都在客户身上，对方没有任何义务——展示当 NDA 不平衡时分析如何变化。

**我问：** 「你见过经验不足的律师审 NDA 时最容易犯什么错？」

**用户说：** 「不看排除项。他们只关注什么算保密信息，漏掉了'我方已经知道的信息'或'公开可得的信息'这些排除项。这些排除项是保护客户的。」

**结果：** 一个正向示例（双向 NDA，标准条款有一个关注点），一个反面示例（单向 NDA 极度不平衡），一个常见错误已记录。

### 第 5 步：划边界

**我问：** 「这个 skill 不该做什么？」

**用户说：** 「不提供法律意见。不说'这个没问题，签吧'。始终说'这是你需要和律师讨论的关注点'。另外，这个 skill 只管商业 NDA——不管劳动合同、不管房地产、不管并购。」

**我追问：** 「什么时候我应该说'这需要律师亲自看'？」

**用户说：** 「NDA 引用了另一份没提供的文件。交易结构异常复杂。NDA 适用的是不熟悉的外国法。这些情况就说'这需要律师审核'。」

**结果：** 清晰边界：不提供法律意见、仅限商业 NDA、复杂/涉外情况推给律师。

### 产出的 SKILL.md（精简版）

```markdown
---
name: nda-first-pass-review
description: This skill should be used when the user asks to "审这份NDA", "帮我看下这个保密协议", "这个能签吗", "过一遍这个合同". 为小企业客户做商业保密协议的初审，输出一页纸优先排序的通俗摘要。
---

# NDA 初审

## 用途

为小企业客户审核商业保密协议。用通俗语言识别和排序关注点。输出一页纸的、客户能直接用的摘要。

## 工作流程

### 第一步：识别 NDA 类型
判断是双向 NDA（双方共享保密信息）还是单向 NDA（仅一方共享）。这决定了哪一方承担哪些义务。

### 第二步：审查保密条款
检查保密信息定义的范围。检查保密期限。检查排除项——什么不被视为保密信息。

### 第三步：检查隐藏的限制性条款
查找竞业禁止、不招揽、不绕开条款。这些在 NDA 中出现需要特别关注。

### 第四步：审查过场条款
检查管辖法、管辖地、转让和救济条款。标注对客户造成实际不便的条款。

### 第五步：整体评估
对每个关注点定级：
- Dealbreaker：不改不签
- 需谈判：应讨论并可能修改
- 提示：异常但视情况可接受
```

## 案例 2：医生 — 接诊前患者摘要 Skill

### 用户可能会怎么说

> 「我是全科医生。每次看病人前要花 10 分钟翻他们的登记表和之前的病历来做准备。你能帮我总结关键信息，让我带了解进诊室吗？」

### 第 1 步：定场景

**我问：** 「上次你看病人前准备，看了什么东西？」

**用户说：** 「打开了患者的病历——今天的登记表、护士量的生命体征、我 6 个月前写的上次就诊记录。我需要知道：有什么变化、上次定的行动计划是什么、今天来的主要原因是什么。」

**结果：** 场景：通过整合登记表 + 生命体征 + 历史病历来做接诊前准备。触发词：「帮我总结这个患者」「准备一下下午 2 点的病人」「帮我把这个患者的情况过一遍」。

### 第 2 步：立目标

**用户说：** 「半页纸的摘要，60 秒能看完。主诉、相关病史、相比上次的变化、我需要跟进什么。不是全部病历——只提取和这次就诊相关的。」

**结果：** 结构化摘要：主诉、生命体征（异常项标出）、与上次就诊的变化、上次就诊确定的待办事项、用药情况（变更标出）。

### 第 3 步：理规则

**用户的流程：**
1. 先看主诉——「今天为什么来？」
2. 查生命体征——标出不在正常范围的
3. 回顾上次就诊记录——当时的计划是什么、该发生什么？
4. 对比今天的登记表和上次就诊——有什么变化？新症状？已解决的问题？
5. 查用药——有变化吗、需要续方吗？
6. 标注今天需要跟进什么

**判断分支：** 「如果生命体征异常，我需要知道超了多少，以及上次这个指标是不是也异常。一次高血压读数和持续走高是完全不同的。」

### 第 4 步：给示例

根据医生描述整理了一个患者案例：55 岁，高血压+糖尿病，常规复诊。今天血压偏高（145/90），上次正常（128/82）。用药：赖诺普利 10mg。上次就诊计划：增加运动，6 个月后复诊。

还写了一个反面示例：多慢性病患者，摘要绝不能把急症问题（胸痛）淹没在慢性病历史里。

### 第 5 步：划边界

- 不做诊断、不建议治疗方案
- 不解读检查结果——只标出异常值
- 不处理儿科和产科患者（不同的正常值范围、不同的流程）
- 数据不全或矛盾时，追问而不是假设

### 产出的 SKILL.md（精简版）

```markdown
---
name: patient-intake-summary
description: This skill should be used when the user asks to "总结这个患者", "准备一下下个病人", "帮我把这个患者情况过一遍", "进诊室前给我看点重点". 将登记表、生命体征和历史病历整合成结构化的单页摘要。

将患者登记表、生命体征和既往就诊记录整合成简洁的接诊前摘要。60 秒可读完，只呈现医生进诊室前需要知道的信息。
```

## 案例 3：会计师 — 费用分类 Skill

### 用户可能会怎么说

> 「我给小企业做代账。每个月收到一份费用的表格，我得把每笔交易按税务口径分类。规则是固定的但很费时间。你能学会做初分吗？」

### 第 1 步：定场景

**用户说：** 「客户每月把信用卡账单发我一个 CSV 或 Excel。每行是一笔交易。我得给每笔交易分配一个税务分类——餐饮、差旅、办公用品、等等。有些一眼能看出来，有些需要判断。」

**结果：** 场景：把交易表格里的业务费用按税务口径分类。触发词：「帮我分下这些费用」「把这些交易归类」「按税务口径分一下」「帮我做下代账初分」。

### 第 2 步：立目标

**用户说：** 「我要原来那个表格加一列分类。再单独一个汇总页——每个分类的合计，还有我自己需要看的有疑问的交易列表。」

**结果：** 两部分输出：(1) 原始数据 + 分类列，(2) 含分类汇总和问题交易清单的汇总页。

### 第 3 步：理规则

**用户的分类规则：**
1. 商户名含餐厅或食品相关词 → 「餐饮与招待」（50% 抵扣）
2. 商户是航空公司、酒店、网约车 → 「差旅费」
3. 商户是文具店或描述含「办公用品」→ 「办公用品」
4. 交易在大型商超（亚马逊、沃尔玛、Costco）→ 标为有疑问（可能是办公用品，也可能是私人消费）
5. 金额超过 ¥500 → 无论分类，标为需复核
6. 以上都不匹配 → 「其他业务支出」，标为需复核

### 第 4 步：给示例

一个 50 行表格的示例：营销顾问的月度消费。商户含航空公司、文具店、亚马逊（3 笔）、餐厅（5 笔）、Adobe（软件订阅）、WeWork（办公室租金）。输出展示正确分类，亚马逊的交易全部标为有疑问，¥15,000 的 WeWork 因金额超标。

### 第 5 步：划边界

- 不做最终税务认定——所有分类是给会计师复核的建议
- 不处理个人消费——如果交易看起来是私人的，标注出来
- 不处理中国以外的税务管辖区
- 表格里没有商户名称列或描述列时，要求用户提供格式正确的文件

### 产出的 SKILL.md（精简版）

```markdown
---
name: expense-categorization
description: This skill should be used when the user asks to "分类这些费用", "归类这些交易", "按税务口径整理这个表格", "帮我把这些费用分下类", 或提供需要税务分类的业务交易 CSV/Excel 文件时使用。
---

## 用途

对 CSV 或 Excel 中的业务费用交易按税务口径分类。执行一致的分类规则，将有疑问和大额交易标出供会计师复核。
```

## 三个案例的共同模式

这些模式在不同职业中反复出现，可以指导你的访谈：

1. **用户都有一个清晰的顺序** ——他们按特定顺序做事是有原因的。把那个顺序找出来。

2. **总有「底线」** ——一旦碰到，什么都变了。律师的底线是单方条款。医生的底线是异常体征。会计师的底线是含混不清的消费。问：「什么会让你停下来，说'这个得特别处理'？」

3. **输出格式高度职业化** ——律师要条款引用。医生要体征趋势。会计师要分类列。别把通用格式强加于人，提取用户真正在用的格式。

4. **边界关乎执业责任** ——每个职业都有「无资质不做」的事。律师不给法律意见。医生不做诊断。会计师不做最终税务认定。Skill 必须反映这些执业边界。

5. **用户最难说清的是第 3 步（规则）** ——他们的判断已经自动化了。用反面案例（「给我讲一次别人做砸的经历」）来挖出他们自己说不清的规则。

6. **一个好例子胜过十段抽象描述** ——用户卡住时，要一个具体的真实案例。规则会自然地从案例里浮现出来。
