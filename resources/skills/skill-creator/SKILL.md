# 技能创建器

帮助任何人——尤其是不懂编程的人——把脑子里的工作流程或专业知识变成完整、可用的 skill 文件。覆盖从「我有个想法」到「skill 在真实案例上验收通过」的完整过程。

## 本 Skill 做什么

引导用户完成两个阶段：

**阶段一：访谈（第 1-5 步）** 通过结构化提问，把用户脑中的隐性知识掏出来。什么场景触发？做成什么样算好？一步一步怎么做？有没有现成的例子？边界在哪里？

**阶段二：构建、验收与迭代（第 6-8 步）** 把访谈结果变成完整的 skill 目录，每条信息分到正确的文件类型，识别该写成脚本的逻辑，创建全部文件。然后**像考试一样逐条核对它有没有真的做对**，把结果摆给用户、按反馈改进，直到验收通过。最后可选地自查这个 skill 的"触发说明"准不准（靠自己判断，不依赖任何工具）。

用户负责：分享知识、确认决策、看测试结果提反馈。我负责：问对问题、处理所有技术细节、写所有代码、认真验收并迭代到通过。

## 什么情况下不用走完整流程

- 用户只是简单问一句「skill 是什么 / 怎么用」→ 直接回答，不要启动完整的创建流程。
- 用户本身技术能力强、已经把流程描述写得很清楚、只想快速生成 → 可以跳过详细访谈（第 1-5 步），直接从汇总确认 + 构建阶段开始。
- 用户是要【重构一个已有 skill】（结构性大改：步骤全重排、references 整体重组、定位重设）→ 先完整读现有的 SKILL.md 和 references 作为"现状素材"，不必从头访谈；据此重新做内容分类、重排结构、重建文件，向用户确认新结构后动手，然后照常走验收（第 7 步）和结构校验（第 6e 步）。（只是局部修复/微调不属于这里——那用 skill-edit。）

## 核心沟通原则

在整个过程中始终遵守以下规则：

1. **不说计算机术语。** 禁止使用「JSON」「YAML」「schema」「eval」「benchmark」「frontmatter」「subagent」「progressive disclosure」「package」等词。用普通人能听懂的说法替代：「顶部的描述信息」「测试用例」「指令文件」「辅助文档」。

2. **任何一次向用户提问，都必须调用 `ask_user` 工具——绝不在普通回复里用文字问。** 这条贯穿全程、无一例外:访谈第 1-5 步、模糊回答的追问、步骤之间的补充追问、汇总确认、第 7 步要反馈、第 8 步确认考题——**每一次**都走 ask_user(最容易出错的是第一次之后就忘了用工具——后面每一次同样必须用)。把当前要问的问题一次性、编好号放进 ask_user 里,让用户一轮答全,不要挤牙膏、不要一个一个问。
   ⚠️ **自检**:如果你正准备在普通回复里写出一个问句(出现"？"、或在征求用户意见/确认),立刻停下,改用 ask_user。

3. **用用户自己的专业语言。** 用户是律师说「尽职调查」，就用「尽职调查」回应。用户是医生说「鉴别诊断」，就保留这个词。不要把人家的专业术语翻译成大白话。

4. **所有文件操作都对用户透明。** 不要让用户建目录、编辑文件、写格式代码。我全部自己搞定。用户只负责审阅和确认。

5. **绝不假定用户懂技术。** 不要让用户按某种格式写东西。不要预设用户知道文件结构和命名规范。凡涉及技术操作，默默地做，不解释。

6. **不要只列清单——直接创建。** 到了生成文件的阶段，用工具把每个文件写出来。用户收到的是一个完整可用的 skill 目录，不是一份待办清单。

## 阶段一：访谈（第 1-5 步）

按顺序引导用户走完这五步。每一步的模式是：
- **每一步都必须用 `ask_user`**（不只第一步）把这一步的主要问题（2-4 个）一次性问清楚，让用户一轮答全
- 如果回答模糊，用该步的「模糊回答处理」策略再追问（追问同样用 `ask_user`，一次问清楚）
- 该步完成后，用过渡语自然衔接到下一步
- 如果多种方式追问后用户仍然卡住，先跳过，后面再回来补

---

### 第 1 步：定场景

**目的：** 搞清楚 skill 在什么情况下用、怎么触发、上下文是什么。

**主要问题（用 `ask_user` 一次性提出，不要打成文字）：**

1. 「你上一次想用我帮忙做这件事是什么时候？当时你正在做什么？是什么让你觉得'我需要帮忙'？」

2. 「你会怎么开口要这个帮助？用你最自然的说法就行——比如'帮我看看这份合同'而不是'请执行合同审核流程'。」

3. 「有没有特定类型的文件、数据或情况，一出现我就知道该用这个 skill？」

**模糊回答处理：** 如果用户说「就是处理合同的时候」这类笼统描述，追问最近的一个具体实例。「上次处理是什么时候？你打开文件第一眼在看什么？」把对话锚定到一个具体案例上，而不是追问抽象定义。

**何时可以进入下一步：** 用户至少描述了一个具体场景，触发情境、输入类型、上下文都清楚了。

---

### 第 2 步：立目标

**目的：** 明确输出什么、做成什么样算成功。

**主要问题（用 `ask_user` 一次性提出，不要打成文字）：**

1. 「如果我把这件事做得很完美，结果会是什么样？越具体越好——是一份标注过的文档？一张检查清单？一份分析报告？还是一份填好的表格？」

2. 「如果把这个任务交给一个新人同事，你会告诉他最终交付物里必须包含什么？」

3. 「你怎么判断做得对还是不对？可接受和不可接受的区别在哪里？」

**模糊回答处理：** 如果用户说「一份好的分析」或「完整的审核」，缩小范围。「咱们先说其中一个部分——你看结果的时候第一眼检查什么？什么东西告诉你这个做得不错？」如果用户仍然说不清，直接抛出一个草案：「根据目前聊的，输出是不是大概长这样——[具体描述]？差不多吗？」

**何时可以进入下一步：** 输出格式（文档类型、结构、关键组成部分）和至少一个具体的质量标准已经清晰。

---

### 第 3 步：理规则

**目的：** 抽取一步一步怎么做、哪里有判断分支。

**主要问题（用 `ask_user` 一次性提出，不要打成文字）：**

1. 「你自己做这件事的时候是怎么做的？从最开始说起——第一步你做什么、看什么？」

2. 「有没有哪些规则或检查是必须做的？一旦跳过就会出错的那种？」

3. 「有没有碰到不同情况要做不同处理的地方？比如'如果文件里有X，就做Y，否则做Z'。」

4. 「做完之后你检查什么来确认没问题？」

**模糊回答处理：** 很多用户的判断已经自动化了，说不太清楚。如果用户说「我也说不好，凭经验」，用「替班清单」技巧：「假设你明天休假，一个同事替你干活，你有10分钟给他写个清单，上面写什么？」如果还不行，用反面案例：「有没有见过别人把这事做砸的？他漏了什么？」

**有大量分支怎么办：** 如果用户描述里有大量「如果A就做X，如果B就做Y」，不要直接全记录。用 `references/branch-handling-guide.md` 里的三问法：
1. 能不能收敛到一个主路径（80%情况）+ 少量例外？
2. 分支之间差异太大，是不是该拆成多个 skill？
3. 路由逻辑是不是该写成脚本而不是指令？

**何时可以进入下一步：** 用户说出了一个至少 3-4 步的序列，至少一个必须遵守的规则，至少一个判断分支点。如果有大量分支，已经确定了处理策略。

---

### 第 4 步：给示例

**目的：** 收集具体的输入输出案例。

**主要问题（用 `ask_user` 一次性提出，不要打成文字）：**

1. 「能给我讲一个真实的例子吗——某次你实际经手的工作？什么东西进来了，你产出了什么？我来帮你整理成格式化的示例。」

2. 「你见过经验不够的人做这件事时最容易犯什么错？」

**模糊回答处理：** 不要让用户自己去写示例。这样说：「你就用自己的话描述一下输入——客户发了什么、表格长什么样、文档里有什么——然后说你做了什么。格式我来整理。」如果有保密顾虑：「人名、日期、金额这些全都可以改掉，我只需要看结构。」

**何时可以进入下一步：** 至少一个正向示例（输入 → 输出），最好还抓到了一个常见错误或反面案例。

---

### 第 5 步：划边界

**目的：** 明确什么不要做、什么时候该拒绝、什么错绝不能犯。

**主要问题（用 `ask_user` 一次性提出，不要打成文字）：**

1. 「这个 skill 不做什么？哪些任务看起来长得像但应该用别的 skill 或者根本不该用 AI 做？」

2. 「什么时候我应该说'这个我帮不了'或者'我需要更多信息才能继续'？」

3. 「我如果犯什么错最要命？什么错会让你说'以后再也不能这么干了'？」

4. 「如果用户给的信息不全或不清楚，我应该追问什么？」

**模糊回答处理：** 如果用户说「用常识判断就行」，抛出一个具体的边界情况来试探：「我来试一个——如果是[某个特殊情况]，我该不该管？」对于有执业资质要求的专业人士，直接问：「我能帮到什么程度，再往下就需要持证的专业人士了？这条线在哪？」

**何时可以进入下一步：** 用户至少说出了 2-3 个绝对不能做的事，至少一个我应该拒绝或追问的情况，至少一个绝不能犯的致命错误。

---

### 汇总确认（阶段一和阶段二之间的桥梁）

五个访谈步骤全部完成后，在生成任何文件之前，把逻辑主线和内容分配计划合并为一条消息，让用户一次确认。

```
根据我们的讨论，我的理解是这样的：

📋 **流程：**
1. [触发条件/起点]
2. [步骤 2]
3. [步骤 3]
4. [步骤 4]
5. [输出结果]

📦 **内容分配计划：**
- 主文件：步骤部分包含什么
- 参考文档：[文件名].md — 放什么知识
- 输出模板：[文件名].md — 放什么格式
- 自动工具（我来写）：[文件名].py — 做什么用
- 测试用例：测试什么场景

❓ **不确定的地方：** [还需要澄清的问题]

你看这个理解对吗？确认后我开始生成所有文件。
```

**把上面这份理解发给用户后，用 `ask_user` 征求确认（无误 / 需要改哪里）；等用户确认后再进入第 6 步。** 确认之前不生成任何文件。

---

## 阶段二：构建、验收与迭代（第 6-8 步）

### 第 6 步：内容分类与文件生成

用户确认汇总后，创建完整的 skill 目录。

#### 6a：内容分类

阅读 `references/content-triage-rules.md`。把访谈中的每一条信息按 7 类分法归类：

| 内容类型 | 放到 | 示例 |
|---------|------|------|
| 一步一步的动作 | SKILL.md | 「先检查管辖法律条款」 |
| 领域知识/判断标准 | references/ | 行业规则、评分标准、术语定义 |
| 输出格式/结构 | templates/ | 报告框架、表格格式、标准措辞 |
| 确定性逻辑/计算 | scripts/ | 批量处理、格式转换、分支路由 |
| 脚本读取的数据 | assets/ | 对照表、关键词列表、配置文件 |
| 参考样本 | examples/ | 好输出长什么样的案例 |
| 测试用例 | evals/ | 输入→期望输出→通过/不通过条件 |

#### 6b：脚本识别

阅读 `references/script-identification-guide.md`。对访谈中每一条逻辑规则，用核心判据判断：

> **这件事的结果必须精确且每次都一样吗？**
> - 是 → 写成脚本（Python）。在 `scripts/` 里创建文件。
> - 否 → 写成原则指导放在 `references/` 里。

特别关注**确定性分支路由**——「文件类型是 A 就用方法 X，是 B 就用方法 Y」。这是最容易放错位置的——必须写成脚本，不能写成 SKILL.md 里的条件指令。

写脚本时：
- 用 Python，注释用中文
- 文件头必须写：功能、用法、输出
- 绝不硬编码路径、文件名、具体数值——全部从参数传入
- 多个脚本时创建 `scripts/README.md`

#### 6c：创建所有文件

用 `templates/skill-md-template.md` 作为 SKILL.md 的骨架。把模板里的每个 `[FILL: ...]` 占位符替换为访谈结果和内容分类后的内容。

**⚠️ 交互型 skill 分两处处理（别混）：** 如果这个 skill 在执行时需要**向用户提问、和用户交互**（从访谈第 3/5 步能看出它要反问用户、要用户确认、要用户补信息）：
- **`description` 末尾**加一句「使用此 skill 时创建一个 interactive 类型的任务」——这是给 harness 在建任务时读的（决定任务类型），必须放 description，也是 description 里唯一允许出现的"非纯触发说明"。
- **「需要向用户提问时用 `ask_user` 工具提问，别把问题干巴巴写在普通回复里」这条属于运行时行为，写进生成 skill 的正文**（相关步骤或「核心原则」里），**不要塞进 description**。

创建分配计划里的**每一个**文件——SKILL.md、所有 references/、所有 templates/、所有 scripts/、所有 assets/、所有 examples/、所有 evals/。

**不要只列文件清单。用 Write/Bash 工具把每个文件都创建出来。**

#### 6d：引用完整性检查

所有文件创建完后，逐一验证每个文件在流程中确实被调用：

- references/ 里的每个文件在 SKILL.md 中有对应的「参考 references/xxx.md」读取指令
- scripts/ 里的每个脚本在 SKILL.md 里有对应的「运行 scripts/xxx.py」执行步骤
- templates/ 里的每个模板在 SKILL.md 里有对应的「按 templates/xxx.md 格式输出」
- SKILL.md「参考资料」节列出的每个文件确实存在
- 没有孤儿文件——没有被任何地方引用的文件，要么补上引用，要么删除

#### 6e：结构校验（跑脚本兜底，防写乱）

文件建好后，对**新建的那个 skill 目录**跑一遍结构校验脚本，把所有 `FAIL` 修掉、`WARN` 逐条核实：
```bash
python scripts/check_skill.py <新建的skill目录>
```
它机械检查：新 skill 的 frontmatter 是否**只有 `name` + `description`**（没塞多余字段）、`name` 是否全小写连字符且与文件夹同名、description 有没有夹带步骤/代码/标题、`---` 围栏是否完好、正文是否还在、有没有多余的 `skill.yaml`、引用的文件是否都存在。这一步专门兜住"元数据写臃肿、结构写乱"这类错——技术细节自己处理，跑出问题就默默修好，不用拿脚本输出去烦用户。

---

### 第 7 步：验收测试与迭代

交付前不止"跑一下看看能不能动"，而是**像考试一样逐条核对它有没有真的做对**，把结果摆给用户看，再按反馈改进。详细方法见 `references/verification-guide.md`。整个过程在对话里完成，不用网页、不导报告。

#### 7a：准备测试用例

用第 4 步收集的示例，再补上两类必备用例：
- **最致命的那个场景**——用户在第 5 步说的"绝不能犯的错"，专门设一个用例来防它
- **信息不全 / 边界场景**——输入残缺或异常时，skill 该追问还是标"待复核"

把用例存进 skill 的 `evals/` 目录，以后改完再跑一遍就能发现有没有改坏。

#### 7b：为每个用例写检查项

给每个用例列几条**客观、能逐条核对**的检查项（「严重违规的对话没被判成合格」这种对错分明的），并**专门为最致命的错写一条**。主观质量（语气、点评是否贴切）留给用户人工判断，不硬套检查项。

#### 7c：逐条核对（能用脚本就用脚本）

按 skill 的步骤把每个用例实际跑一遍（有脚本就真的运行），逐条判**通过/不通过**并给出**依据**。能机械核对的检查项（数数量、算分数）写个小脚本核对，更可靠、可复用；要理解语义的再人工判断。有确凿依据才算通过——文件名对但内容空/错，判不通过。

#### 7d：把结果摆给用户

在对话里逐个用例说清楚：测的是什么、产出在哪（必要时贴出文本）、哪几条检查通过、哪几条没过（没过的一句话说清问题）。给一句整体小结，**先讲没过的**，然后**用 `ask_user`** 问用户："这些结果行吗？哪里要改？"

#### 7e：改进并重测

按用户反馈和没过的检查项改 skill（原则见 `references/verification-guide.md`：别为这几个例子过拟合、保持精简、解释为什么、重复逻辑抽成脚本）。改完**重新跑一遍所有用例**，确认修好且没弄坏别的。直到用户满意、或所有检查项通过、或继续改没有明显进步为止。

#### 7f：报告结果

验收通过后，告诉用户：

> 「所有文件已经创建好了，我用[测试案例]跑了一遍，跑通了——[简要说明做了什么、产出了什么]。下面是每个文件的说明：」

然后用通俗的语言列出目录结构：

```
✅ **你的 skill 已就绪。** 创建了以下文件：

📋 [skill名]/SKILL.md — 主流程：第1步→第2步→第3步→输出
📚 references/[文件名].md — [什么知识，什么时候查阅]
📝 templates/[文件名].md — [什么格式模板，什么时候用]
🔧 scripts/[文件名].py — [做什么，运行方式：python scripts/xxx.py <输入>]
📊 assets/[文件名].csv — [什么数据，哪个脚本用到]
📋 examples/[文件名].md — [什么示例]
✅ evals/[文件名].md — [测试什么场景]

**以后要改东西的话：**
- 改步骤顺序？→ 改 SKILL.md
- 改规则或标准？→ 改 references/
- 改输出格式？→ 改 templates/
- 改自动工具？→ 告诉我要怎么改
- 改完想验证没出错？→ 跑 evals/ 里的测试

**试试看：**[用通俗语言告诉用户怎么试用]
```

---

### 第 8 步（可选）：自查"什么时候会用到它"

skill 顶部那段描述，决定了它以后会不会在该用的时候被想起来用。做完可以自查这段描述准不准。**这一步不需要任何外部工具或命令行，靠自己的判断就能做，哪个运行环境都行。**

1. **拟一批"考题"**：写 10-20 条用户可能说的话，一半是"这种情况该用到这个 skill"，一半是"这种情况长得像但其实不该用"。写得像真人随口说的（带具体文件名、背景、口语、错别字都行），重点放在容易判错的边界例子上。用 `ask_user` 把这批考题分成"该用/不该用"两组列给用户，让他确认或增删。

2. **逐条自判**：对每一条，只看 skill 的**名字 + 描述**（先别看正文，模拟"还没决定要不要用它"的状态），问自己：「用户这么说的话，我会不会想起来用这个 skill？」把每条的判断记下来。

3. **找出不一致并改描述**：
   - 该触发却判"不会用" → 描述太窄或漏了说法，把缺的触发场景/关键词补进去。
   - 不该触发却判"会用" → 描述太宽或有歧义，收窄措辞，必要时加一句"不适用于……"的排除。

4. **改完再自判一遍**，直到所有考题都判对；把改前/改后的描述给用户看。

> 说明：这是靠自己的判断做的轻量自查，不如在真实运行环境里实测严格，但**不依赖任何特定产品或命令行**。如果你的运行环境恰好能把这个 skill 装进去真实触发测试，那样更准；不能的话，这个自查也足以排掉明显的描述问题。

## 反模式：什么不要做

以下规则是我在执行本 skill 时的自我约束。违反任何一条都会损害用户的体验。

1. **不说计算机术语。** 禁止使用 JSON、YAML、schema、eval、benchmark、frontmatter、subagent、metadata、progressive disclosure、package 等词。确需提及技术概念时，只用通俗描述。

2. **不用纯文字提问，不挤牙膏。** 任何一次提问都必须用 `ask_user` 工具（不只第一次，每一次都要），把该步问题一次问清楚、编好号、让用户一轮答全；绝不在普通回复里用文字问，也不要一个一个挤。

3. **不假定用户懂技术。** 不要让用户建目录、编辑文件、写格式化文本。所有文件操作透明处理。

4. **不跳过早确认就写文件。** 在完成访谈（第 1-5 步）并得到用户对汇总的确认之前，不开始生成文件。过早生成浪费精力，产出的 skill 也容易跑偏。

5. **不追问用户没有的细节。** 两种方式追问后用户仍然说不清，就用现有的内容写个草稿让用户反馈。草稿比追问更容易暴露缺失。

6. **不只列清单不创建。** 到了生成阶段，用工具把每个文件写出来。绝不列个文件清单说「这些是我准备创建的」。

7. **不跳过验收。** 交付前一定按第 7 步做验收：准备测试用例、逐条核对检查项、把结果摆给用户、按反馈迭代。没跑过验收、或还有没过的检查项又没跟用户确认的，不算完成。能机械核对的检查项要写脚本核对，别只靠肉眼。

8. **输出的 skill 不用第二人称。** 访谈时自然说「你」，但生成的 skill 文件必须用动词开头的祈使句。写的时候自动转换，不用跟用户解释这条规则。

9. **不强扭用户的流程。** 7 步框架是用来引导对话和构建的，但输出的 skill 应该反映用户自己的思维方式。有些流程是线性的，有些不是。

10. **输出的 skill 不写空话套话。** 每条指令必须具体、可验证。「要仔细」不是指令。「检查保密条款的范围、期限和排除项」是指令。

11. **不替用户补内容。** 我的角色是捕捉和整理用户的知识，不是替用户补齐专业内容。如果觉得哪里不完整或可疑，问用户，而不是自己从训练数据里补充。一个不完整但准确的 skill 远好过一个完整但错误的。

12. **不留孤儿文件。** skill 目录里的每个文件都必须在 SKILL.md 中有对应的引用指令——什么时候用、怎么用。没被引用的文件，要么补上引用，要么删掉。
