# 内容分类规则

用于第四步：判断用户描述里的每句话应该放到哪里。

## 判断方法

| 这句话是什么 | 放哪里 |
|------------|-------|
| 做什么动作 | SKILL.md |
| 为什么这样做 / 按什么标准判断 | references/ |
| 输出长什么格式 | templates/ |
| 计算 / 批量处理逻辑 | scripts/ |
| 脚本要读取的数据文件 | assets/ |
| 好的输出长什么样（给Claude参考） | examples/ |
| 输入+期望输出+判断标准（测试用） | evals/ |

## 详细分类规则

### 放入 SKILL.md（步骤）
- 「先做X，然后做Y，最后输出Z」
- 向用户提问的句子
- 「参考 references/xxx.md」「运行 scripts/xxx.py」

### 移到 references/（知识——Claude读懂后灵活运用）
- 行业规则、法规标准、技术规范
- 评分标准、判断好坏的具体指标（写成原则，不写成 if/else 树）
- 专业术语定义
- 用户在步骤里插入的「因为……」「根据……规范……」

**references/ 里不该出现的东西：**
- 大量 if/else 分支树——这会变成提示词喂给 LLM，而 LLM 不擅长可靠地执行确定性分支逻辑
- 如果发现自己在 references 里写分支树，应该改成脚本

### 移到 templates/（格式）
- 输出文档的结构框架
- 固定的表格格式
- 标准措辞、固定条款
- 「结果应该包括以下字段……」

### 移到 scripts/（代码逻辑）
- 批量处理文件
- 数据计算、统计、汇总
- 格式转换（JSON/CSV/Excel/YAML等）
- 文本解析、正则匹配
- 需要精确、可重复执行的逻辑
- **确定性分支路由**：「如果是A类型就调用X，如果是B类型就调用Y」——这类逻辑写进提示词 LLM 会执行不稳定，写成脚本才可靠

### 移到 assets/（数据文件——脚本读取的，不是Claude读的）
- 对照表、映射表（端口→服务名、错误码→含义、国家代码→名称）
- 分类词典、关键词列表
- 图标、logo等静态资源
- 脚本运行需要的种子数据
- **判断方式**：这个文件是「给人理解的说明」还是「给程序读取的数据」？是数据就放 assets/

### 移到 examples/（参考样本——给Claude看，知道好输出是什么样）
- 「我希望结果长这样」提供的示例文本
- 典型的完整输入输出对
- 好的案例、反面案例

### 移到 evals/（验收测试——改skill后用来检验有没有退化）
- 每个用例包含：给什么输入、期望什么输出、怎么判断对不对
- 覆盖典型场景、边界情况、容易出错的场景
- **和 examples/ 的区别**：examples 是给Claude参考用的，evals 是改完skill之后跑一遍验证用的

## assets/ 和 references/ 的核心区别

```
references/  ← Claude 读，理解后用来做判断
assets/      ← 脚本读，程序用来做处理
```

例子：「端口号和服务名的对应关系」
- 如果 Claude 需要在回答里解释「80端口是HTTP」→ 放 references/
- 如果脚本需要遍历一万条日志并把端口号转换成服务名 → 放 assets/（CSV文件）

## 快速判断口诀

> 步骤只写动作，原则知识放references，格式放templates，计算和分支逻辑写脚本，脚本的数据放assets，好样本放examples，考卷放evals。

## references 和 scripts 的核心分工

```
references  ← 原则性知识，LLM 读懂后灵活运用（允许模糊）
scripts     ← 确定性逻辑，代码精确执行（不允许模糊）
```

判断要不要写成脚本的问题：**这件事执行结果必须精确且可重复吗？** 是 → 脚本。否 → references。
