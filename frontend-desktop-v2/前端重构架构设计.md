> 已综合两轮外部审视意见修订(删 zustand、移出虚拟化、补两张安全网、反转迁移顺序、精简分层;并修正 shared/ 边界、hooks 归属、golden-master 可操作性、Step 0 拆分、文档编号)。

## 0. 目标与硬约束

**目标**
- 在**不改技术选型**的前提下,重构 `frontend-desktop`,消除上帝组件、样式三套打架、逻辑/副作用纠缠等结构性问题。
- 让"配色 / 边距 / 字号"能在**单一来源**处统一调整。
- 让核心逻辑(SSE 事件翻译)可脱离浏览器单测,从结构上根除 live/replay 不对称类 bug。

**硬约束**
- **功能严格不丢**:除 §5.3 白名单内的 2 个 bug 修复外,行为与旧版逐项一致。
- **技术选型不变**:React 19 + TypeScript + Vite + Tailwind v4 + `@tanstack/react-query` + react-markdown/remark-gfm + pdfjs-dist + docx-preview + 自研 pptx 解析 + Electron。
  - ⚠️ **不引入 zustand**:经核实旧前端既未在 `package.json` 声明、`src/` 也零引用 zustand。当前客户端状态就是 `App.tsx` 的 `useState + localStorage`。本次**不新增全局状态库**。
  - 不引入路由库(桌面端视图少,沿用手写视图切换,仅收口集中)。
- **两个 bug 要修**(已确认),并进"行为对照白名单"(§5.3)。

## 2. 目标架构:3 桶分层 + 单向依赖

```
src/
  app/       应用装配:providers、视图切换(收口现有 App.tsx 手写导航,不引路由库)、
             布局骨架、错误边界、main.tsx(含 signalReady 白屏看门狗,见 §6)
  features/  按功能切片,每片自带:UI(容器+展示) + 该片数据 hooks(§3.2) + 该片测试 + 必要时局部状态
             chat / sessions / llm-settings / skills / workspace+preview
             ※ 领域逻辑归属其 feature。例:SSE 纯 reducer 放 features/chat(§3.4,经核实仅 chat 消费 SSE)
  shared/    纯通用积木(不含任何后端领域知识):
             ui(原子件)· tokens(接入 Tailwind @theme)· i18n · lib(纯工具)
             · api(仅 http 客户端 + query-key 工厂,§3.2)· electron(桥)· types(跨切面通用类型)
```

**铁律一 — 单向依赖**:`app → features → shared`,**不许反向**;同层之间尽量不互相依赖。

**铁律二 — shared/ 不得含领域**行为**知识**:`shared/` 内任何模块**不得包含**"知道后端有哪 21+ 种 SSE 事件、知道这些事件怎么处理"的**逻辑**。这类行为一律归到拥有它的 feature(见 §3.4)。否则会把当年"什么都堆进 components/"换成"什么都堆进 shared/",原罪换马甲。

> **边界澄清(避免与 `shared/types` 冲突)**:铁律二只约束**含行为的逻辑模块**(reducer、事件处理函数等)。**纯类型声明例外** —— `shared/types` 可放 API 数据契约的 TS `interface/type`(无运行时行为),它们是"结构描述"而非"业务规则"。`types/index.ts` 现有类型的归宿:
> - **跨多 feature 的数据契约 → `shared/types`**:`Session`/`SessionStatus`/`TERMINAL_STATUSES`/`LLMProvider`/`RegisterLLMRequest`/`WorkspaceEntry`/`WorkspaceListing`/`AuthUser`(`TERMINAL_STATUSES` 虽是运行时常量,但属"哪些状态是终态"的数据事实,非行为,可留 shared)。
> - **只属某一 feature 的 UI 模型类型 → 随该 feature**:chat 的 SSE 派生类型 `ChatItem`/`ChatMessage`/`ChatToolCall`/`ChatWaitingInput`/`ChatObserverMessage`… → `features/chat`。
> - **纯客户端草稿态 `PendingSession` → `app/`**(或 chat feature)。
> 这样"这个 type 放哪"在第一天就有确定答案,不留开放问题。

> 这两条铁律是"分步、可机器校验"的根本;§5.2 用 ESLint 把它们变成可自动检查的门禁。
>
> 刻意只用 3 桶,**不搞 entities/platform 五层 FSD** —— 对单用户、约 1.1 万行的桌面应用,过度分层是另一种过度设计。

## 3. 关键设计决策

### 3.1 样式:Tailwind 为唯一写法,令牌为唯一来源(对应病 #2)
- 把旧 `index.css` 的 CSS 变量(`--bg1/--blue/--t1/--r/...`)接进 Tailwind v4 的 `@theme`,使 `var(--blue)` ≡ `bg-blue` 为同一值。
- **全项目禁止**:裸十六进制(`#2563eb`)、内联 `style={{padding:'11px...'}}`。统一改配色/边距 → 只改令牌一处。
- 此步是最高 ROI / 最低风险,但也是最大的机械 diff → **必须由视觉基线把关**(§4.2)。
- **已知 follow-up(半透明色尚未 token 化)**:迁移代码里若干半透明色(如 `bg-[rgba(37,99,235,0.09)]` = `--blue-dim`、模型芯片的蓝/绿/红 alpha 边框背景)目前用**精确 rgba 任意值**写死,**故意如此**——保证视觉 diff 像素级一致(换成 `bg-blue/9` 这类 Tailwind 透明度修饰会走 color-mix/oklab,可能产生像素漂移、令基线失败)。lint 合规(只禁裸 hex)。**待需要全局统一调这些半透明色时**,再把它们(`--blue-dim`/`--blue-glow` 及常用 alpha)加进 `@theme` 成 token、批量替换并重跑视觉基线。首次出现在 `features/llm-settings`(Step 2)。

### 3.2 服务端状态:query-key 工厂(shared)+ 数据 hooks(feature)(对应病 #4)
**裁定:采用方案 A。**
- `shared/api/` **只放两样**:底层 http 客户端 + `queryKeys.ts`(集中所有 React Query key)。**shared/api 不放任何具体资源 hook**(那些"知道会话/LLM"的东西是领域知识,违反铁律二)。
- 各 feature 自己写数据 hooks:`features/sessions/api/useSessions()`、`features/llm-settings/api/useLLMAccounts()` 等,内部用 `queryKeys` + http 客户端封装 `useQuery/useMutation`,并就地定清 invalidate 关系。
- **组件不再直接 `useQuery/useMutation`**,只调本 feature 的数据 hook。
- 这是病 #4 的正解,**与状态库无关,一行 zustand 都不需要**。
- **跨切面缓存失效统一走 `queryKeys`**:某 feature 的 mutation 需让别的 feature 的缓存失效时(典型:chat 发消息 / 会话结束 → 失效 sessions 列表),**只 import `shared/api/queryKeys`**、用 `queryKeys.sessions()` 做 invalidate,**绝不 import 对方 feature**。`queryKeys` 是纯字符串数组、无领域行为,`features→shared` 方向合法,从而既能跨切面协调、又不破"同层不互相依赖"。

### 3.3 客户端状态:维持最小化,暂不引入全局 store
- 现有顶层状态(selectedId / centerView / pendingSession / workspaceOpen 等)继续用 `app/` 顶层 `useState`,prop 下传一两层即可。
- **暂不引入 zustand 或任何全局状态库**;若 chat 迁完后 prop drilling 确实痛,再单独评估(届时优先 React Context,仍不一定需要外部库)。

### 3.4 SSE:纯 reducer + 薄 hook,放 features/chat(对应病 #3)
- **位置裁定:放 `features/chat/`,不放 shared/。** 经核实 `useSessionSSE` 只被 `App.tsx:112` 调用并下传给 ChatPanel,`SessionList` 等**不消费 SSE**;SSE 事件翻译是 chat 领域逻辑,按铁律二归 chat feature。
- **两条输入路径必须先归一(实现关键,勿低估)**:旧码 live 是逐帧 SSE、replay 是 `session_update.history` 经 `evtToItem` 转成对象,**两种格式不同**。新设计定义一个 **`InternalEvent` 联合类型**:live 适配器把 SSE 帧、replay 适配器把 history 项**各自先转成 `InternalEvent`**,reducer **只认 `InternalEvent`**。这样"live/replay 共用一套规则"才是真的,golden-master 也只需覆盖这一种格式。不先想清这一步,Step 3 写 reducer 会被格式分叉卡住。
- `features/chat/sse/sseReducer.ts`:`(state, event: InternalEvent) => state` **纯函数**,**可脱离浏览器单测**;live 与 replay 喂同一 `InternalEvent` → 对称性 bug 从结构上消除。
- `features/chat/sse/useEventStream.ts`:只管 EventSource 连接、重连、看门狗等副作用,把事件喂给 reducer。
- 组件只消费 reducer 输出。配套 §4.1 golden-master 做客观回归。
- **`ChatItem` 系列类型设计为无 UI 状态字段 + `Readonly<>`**:类型定义里不放 `isExpanded`/`isCollapsed` 等 UI 交互字段;所有 reducer 输出类型包 `Readonly<>` 或用 `as const`。效果:若有人试图在 reducer 里加展开/折叠状态,必须先改类型定义(留痕),且 `state.items[0].isExpanded = true` 是编译错误——UI 交互状态被类型系统推向 component 本地 `useState`,而非 reducer。

### 3.5 适配层:Electron 与后端协议各包一层(对应病 #6)
- `shared/electron/bridge.ts` 收口所有 `window.electronAPI.*`(含 §6 的 signalReady)。注意:bridge 只做"通道"封装,不含会话/事件等领域概念,符合铁律二。
- **必须保留可选链降级语义(行为约束,非实现细节)**:现有代码到处用 `window.electronAPI?.x?.()` 做"有/无 Electron"的安全降级——浏览器调试(无 `window.electronAPI`)下不崩,且 `App.tsx:65` 的 `hasElectron = !!window.electronAPI?.getSession` 据此**跳过登录门直接进界面**。bridge 每个导出函数内部都要保留这个降级,例:
  ```ts
  export const isElectron = !!window.electronAPI?.getSession
  export const signalReady = () => { try { window.electronAPI?.signalReady?.() } catch {} }
  ```
  非 Electron 环境安全退化为 no-op、不抛异常。否则会断掉**浏览器调试路径**——而 §4.2 视觉基线与 §5.1 测试都依赖这条 mock/浏览器路径,一断则两张网同时失效。**不要**写成裸 `window.electronAPI.method()`。
- 后端 SSE 事件名 / 字段等**领域协议**集中在 `features/chat`(随 reducer),不放 shared。

### 3.6 上帝组件拆解(以 ChatPanel 示范,余者同法)
```
features/chat/
  ChatPanel.tsx        仅布局编排(容器,目标 ~100 行)
  useChatSession.ts    聚合 SSE + 各 mutation,对外给干净 state/actions
  sse/                 sseReducer.ts(纯) + useEventStream.ts(副作用) + __fixtures__/(§4.1)
  api/                 该片数据 hooks(send/answer/interrupt/resume/bashMode…)
  components/
    MessageList.tsx     消息列表(滚动/自动贴底;⚠️ 不含虚拟化,见 §7)
    MessageItem/        用户气泡 / AI 气泡 / 工具调用 / HITL / 任务摘要 …(各一文件)
    Composer.tsx        输入框 + 粘贴图片 + 发送(修"首条消息丢图"的前端侧;后端通路见 §1 注)
```

> ⚠️ **迁移 chat 时必须纳入的上游变更(2026-06 已同步进 v2 的旧文件,迁移时一并带过来,别迁丢)**:
> - **LLMErrorModal 改为"只关闭"**:props 现在只有 `{message, onClose}`——**去掉了 `resuming`/`onResume` 与「恢复运行」按钮**(去 `Spinner` 导入)。定位从"检查配置后恢复"变成"建议上报会话供开发者排查",`llmError.body` 文案重写(zh+en,§i18n)。迁移后的弹窗组件按此实现,**别把 resume 入口加回来**。

### 3.8 Feature 桶文件(barrel index.ts)— 封死内部结构

每个 feature 只通过 `index.ts` 对外暴露公共 API,内部文件对外不可见:

```ts
// features/chat/index.ts — 只导出外部确实需要的
export { ChatPanel } from './ChatPanel'
export type { ChatSession } from './useChatSession'
// sseReducer、ToolCallItem 等内部实现不导出
```

**效果(编译时强制,非 ESLint 软规则)**:外部若写 `import { sseReducer } from '@/features/chat/sse/sseReducer'`,配合 TypeScript `paths` 别名 + `eslint-plugin-boundaries` 的 `allow-only-index` 规则,直接报错——**内部结构对外完全不透明**,feature 内部重构不影响外部,外部也无法绕进内部耦合。

适用范围:每个 feature 目录(`chat/`、`sessions/`、`llm-settings/`、`skills/`、`workspace+preview/`)都建 `index.ts`。`shared/` 子目录视具体情况选择是否加桶文件。

### 3.7 两处具体归属裁定(ModelPickerButton / useOnboarding)

> 这两个组件横跨多处使用,易引发"放哪"的纠结。经核实源码,结论如下(注:它们并不构成审视所担心的"死锁/跨切面",premise 与代码不符):

- **`ModelPickerButton`(被 ChatPanel 与 NewSessionDialog 共用)**:经核实它**已是哑组件** —— 只接收 `providers: LLMProvider[]` 等 props、内部**不做** `useQuery`(`ui/ModelPickerButton.tsx:7-21`),取数在调用方。**因此不存在死锁**:**原样移到 `shared/ui/ModelPickerButton`**(仅依赖 `shared/types` 的 `LLMProvider` 纯类型与 `shared/i18n`,符合铁律二),两个调用方各用本 feature 的数据 hook 取 `providers` 喂进去即可,**无需重写**。两个 feature 都能 import shared,天然不构成跨 feature 依赖。
- **`useOnboarding`(driver.js 引导)**:经核实它**不是**跨切面领域逻辑 —— `useFirstVisitTour(tour, steps, opts)` 是**通用的"每页一次"引导驱动**,只读 localStorage 标志、import 仅 driver.js + i18n,**不感知任何 feature 状态**;被 `App`/`LLMSettingsPage`/`SkillsPage`(**非** SessionList)各自传入自己的步骤调用。归属:**通用引擎 `useFirstVisitTour` + `tourSeen/markTourSeen` → `shared/lib`**;**各页步骤定义(`mainTourSteps`/`llmTourSteps`/`skillsTourSteps`)→ 随各自的 app/feature**。

## 4. 两张安全网(动手前先架好)

### 4.1 SSE 事件流 golden-master(最高优先级)
新纯 reducer 的客观回归基线。要素必须落清,否则 golden-master 沦为空话:

- **fixture 来源(纯前端采集,不用 `/export`)**:⚠️ 后端 `GET /sessions/{id}/export` 返回的是**会话 SQLite 二进制文件**(`media_type="application/octet-stream"`,供"上报会话"用,`api/sessions.py:289-295`),**不是** JSON 事件序列,**不能**拿来采集 fixture;后端也没有"返回 JSON 事件序列"的接口。可行做法两条配合:
  - **① (主)dev dump 钩子**:⚠️ Step 0c 在 Step 3 之前跑,**此时新文件 `features/chat/sse/useEventStream` 还不存在**,所以钩子要加在**旧 `frontend-desktop/src/hooks/useSessionSSE.ts`** 里:dev 模式下每收到一帧原始 SSE 就 append 进数组、会话结束序列化落 fixture;**采完六类场景后移除**。这正是 golden-master 的正确姿势——**先从现有(旧)系统捕获行为基线**,再用它验证新实现。捕获的原始帧既是旧 `handle()` 的输入、也是新 live 适配器的输入,覆盖 **live** 全场景。
  - **② (补)history 载荷**:直接取 `session_update` 事件里的 `history` 字段(已是 JSON,作 **replay** fixture);但它只含可持久化事件类型(旧码 `_HISTORY_TYPES`,流式 delta 不在内),仅覆盖 replay 路径。
  - 两者**配合**才能覆盖下面六类场景。落位 `features/chat/sse/__fixtures__/*.json`。
- **必须覆盖的场景(最少)**:① 正常文字对话 ② 工具调用(普通 + 控制工具/任务摘要)③ observer 轮次(actor+observer 推理都在)④ HITL 等待/审批 ⑤ 失败 + retry ⑥ 中断 / 恢复(history 回放)。
- **幂等(关键)**:断言前先**归一化易变字段** —— 时间戳置固定值、随机/会话 id 重写为稳定序号(沿用旧代码 replay 把 id 改写为 `h${index}` 的做法,`useSessionSSE.ts:184`),否则快照天天 diff、golden-master 失效。
- **断言对象**:对 `reducer(initialState, events)` 的**最终 UI 模型**(及关键中间态)做快照断言;live 与 replay 喂同一 fixture 必须得到一致结果(对称性回归)。
- **谁来跑**:fixture **采集是半自动**(需后端 + 真实会话 + 导出,可由人/agent 驱动一次);采集完成后,reducer 的快照测试**全自动**(纯函数,无需后端/浏览器),纳入每片验收。

### 4.2 视觉基线(像素 diff,带护栏)
