# 全自动模式安全设计：准入 + 隔离 + 回退

**日期**：2026-08-07（实现进度更新 2026-08-11）
**状态**：app 侧实现完成（准入 + rewind + 低完整性边界模块 + 模式持久化 + 接线，内核零改动），待 Windows 真机联调（§8 阶段 1 的 1.3/1.5）
**范围**：让 agent 在「全自动模式」下无人值守连续执行 shell / 代码。唯一目标——**阻止改动工作区外的东西**（工作区外可读、不可写）。OS 隔离以 Windows 为目标平台。

---

## 1. 目标（收敛后）

用户开启全自动模式时，会话已选好一个**工作区**。此后大模型：

- ✅ 工作区内**随便增删改查**；
- ✅ 工作区外可**读**；
- ❌ 工作区外**不可写 / 不可改**；
- Python / node 用**全应用共享的那套环境**，这套**照常可写**（`pip` / `npm` 该装就装），**不做限制**。

> 一句话：**只拦"往工作区外写"，其余全放行。**

**硬约束：不影响现有功能。** 本方案只新增第三个模式 `strict-auto`，三层（准入 / 边界 / rewind）**全部只在该模式生效**，对现有 semiauto / manual 两模式零改动（详见 §4.4）。

**明确不做**（不在目标内，别把方案想复杂）：数据防外泄、防有意提权攻击、防"故意绕过检测"、防共享环境被投毒。对手是"agent 手滑乱改用户其它文件 / 系统"，不是"agent 被操纵去攻击宿主"。

**为什么不能只靠"看命令"拦**：命令词能拦住 `rm C:\Users\...`，但一旦允许执行 Python，`os.remove(运行时算出的路径)` 就看不穿了（代码图灵完备，语义等价写法无穷）。所以必须：
- **OS 层强制**——让"写工作区外"在系统层直接失败，不靠猜命令意图；
- **rewind 兜底**——工作区内删错改错，能一键回滚。

## 2. 三层防护

```
        模型：连续执行工具（全自动，不逐条确认）
                        │
        ┌───────────────▼──────────────────────────────┐
        │ ① 准入层 · strict-auto = 纯完整性（现有 auth 扩档）│  不看命令文本
        │   全自动下一律放行（含网络）；边界全交给完整性②    │  → 无命令级判断
        └───────────────┬──────────────────────────────┘
                        │ 放行（文件/系统/网络操作全部下放到边界层/环境）
        ┌───────────────▼──────────────────────────────┐
        │ ② 边界层 · OS 写入边界（新增 low_integrity）      │  内核强制 · 运行中每次访问
        │   只有 {工作区 + 共享环境} 可写，其余只读；读不限  │  → 把漏网的写关在工作区内
        └───────────────┬──────────────────────────────┘
                        │ 破坏（若有）被限定在工作区内
        ┌───────────────▼──────────────────────────────┐
        │ ③ 恢复层 · rewind（新增 checkpoint）           │  事后 · 可回滚
        │   工作区文件回滚到任一检查点                     │  → 把工作区内的破坏撤销
        └───────────────────────────────────────────────┘
```

| 层 | 干什么 | 强制力 | 覆盖 |
|---|---|---|---|
| **① 准入** | 全自动下**不做任何命令级判断**（网络限制亦已移除） | — 全放行 | 无 |
| **② 边界** | 工作区外的写在 OS 层失败、读放行 | ✅ 内核强制 | 整棵进程树 · 代码里算出的路径 · 越界读写的读写区分 |
| **③ rewind** | 工作区内的破坏可回滚 | — | 工作区**文件**（不含系统副作用） |

**为什么这么分**：全自动的边界**只靠②（完整性）**——它能强制、能区分读写、能覆盖脚本算出的路径，是唯一可靠的强制点。①在全自动里退化成「什么都不判、全放行」（避免与②重复、且避免误杀合法读）；③兜②之后残留在工作区内的破坏。**② 在（Windows）才敢开全自动**；② 不在（Mac）则退化为无文件边界，仅 ③ rewind 兜工作区内。

## 3. 威胁模型

**要防（手滑事故）**：误删 / 误改工作区外的用户文件、别的项目；脚本改系统配置 / 注册表 / 计划任务 / 开机项；脚本调关机；资源耗尽（fork bomb / 死循环）。

**不防**：数据外泄（读 + 外发）、有意提权攻击、故意绕过检测（如把系统命令藏进 `powershell -c`）、共享环境被投毒。

**验收**：工作区外的写失败（无论来自 python / cmd / powershell / 任意层子进程），而工作区内操作、读取、共享环境装包都无感知通过。

> 必须在产品里明说这条边界——不能让用户从"有全自动模式"推断出上面那些"不防"的也被防住了。

## 4. 层① 准入层：全自动 = 纯完整性（不看命令文本）

**定位**：在现有 `auth`（`bash_policy.classify` 的 `ALLOW` / `CONFIRM` / `DENY` + `BashReviewModeStore` 的 per-session 模式）上**新增 `strict-auto` 档**。但和 semiauto/manual 根本不同：**strict-auto 的准入层几乎什么都不做**——全自动的安全边界是 OS 完整性②，不是命令文本判断。

**核心原则：path 判断 / 危险动词判断，是「要人把关」的 semiauto/manual 才用的信号，不该进全自动。**
- 全自动没人确认，命令危不危险**不靠猜命令词**，靠运行时 OS 完整性强制：Low 进程读 Medium 可以、写 Medium 被系统拒。越界与否、动没动系统，都是 OS 说了算。
- 若在全自动里仍做 path 判断，坏处有二：① 与 OS 层**重复**；② 更糟——把「读工作区外」（`ls ..`、`cat ../x`）这类**完整性本就允许的合法读误杀**（path 判断分不清读写，一律按越界拦）。方向反了。

**所以 strict-auto 准入层规则只有一条：一律放行**（`return allowed=True`），不看命令文本。连命令里明写的越界、系统操作、网络都不在此判断——全部交给运行时的完整性②或环境本身。

| 命令类别 | 全自动准入 | 谁来兜 |
|---|---|---|
| 工作区内文件增删改 | 放行 | 完整性②（Low 写 Low，通过）；删错了 rewind③ |
| 工作区外**写**（rm/mv/`echo>`、脚本算路径） | 放行 | 完整性②在 OS 层拒（Windows）；**Mac 无完整性→真生效**（诚实降级） |
| 工作区外**读**（`ls`/`cat ..`） | 放行 | 完整性②允许（Low 读 Medium）——正是设计要的「工作区外可读」 |
| 系统/权限（chmod/reg/sc/sudo/icacls…） | 放行 | 完整性②：Windows 上写 HKLM/建服务/改 ACL 都要 Medium+，Low 干不了→被拒；Mac 无 |
| 网络（curl/wget/ssh…） | 放行 | 网络限制已移除（见下「网络策略」）——允许模型联网；内网环境本就限制对外访问 |

> **网络策略（独立于三层，全模式生效）**：原先 `classify` 对 curl/wget/ssh 等**全模式硬 DENY**（内网策略）现已**移除**——semiauto / manual / strict-auto 三模式都允许联网命令（manual 下仍逐条确认）。这是一次**与本设计正交的产品决定**，不属于「三层只在 strict-auto 生效」的范畴，故单列于此。

> **执行层致命红线（永远硬拦，含 strict-auto）**：准入层"一律放行"指的是【准入层不判】；但**执行层**（`shell`/`low_shell` 起进程前）保留一份极小的固定黑名单 `FATAL_ONLY_BLACKLIST = {format, mkfs, dd, shutdown, reboot, halt, poweroff}`，**任何模式、任何平台都硬拦**（命中即 `COMMAND_BLACKLISTED`、不执行）。理由：这 7 个是**抹盘 / 毁文件系统 / 关机**级操作，完全在"工作区边界"模型之外、不可逆、rewind 救不回、对 agent 干活无正当用途；且完整性网盖不全（关机类 Low 未必挡得住，Mac/非低完整性更没有网）。它不是启发式 path/动词判断（那些会误杀、已删），而是"任何情况下都不该发生"的红线，零误杀。**所以精确表述是：strict-auto = 准入层一律放行 + 执行层保留这 7 个致命命令的硬黑名单兜底。** 描述给模型看的黑名单也对齐成这一份（见 §10 工具描述对齐）。

### 平台差异（必须对用户讲明）
- **Windows**：完整性在 → 越界写被 OS 拒、读放行、系统写多被拦。全自动名副其实。
- **Mac/Linux（dev）**：无完整性 → 全自动的**文件边界真的没有**，越界写会真生效。前端切全自动时弹降级 toast 明示「仅 rewind 兜底，无 OS 边界」。故 Mac 全自动只适合开发/测试，不托管真实风险任务。

### 为什么不做命令文本审查（连「命令里明写 rm C:\」也不在准入层拦）
刻意的：避免半吊子文本判断（既漏——`powershell -c "..."` 藏得进；又误杀——`ls ..` 这类读被拦）。把边界收敛到**单一强制点（OS 完整性）**，逻辑更干净、无读写误判。代价是 Mac 上没有这个强制点——已在平台差异里明示。数据外泄、有意提权、共享环境投毒等仍不防（§3/§9）。

### 4.4 与现有两个模式的关系（硬约束：不影响现有功能）

现有 per-session 两模式（`bash_authorizer.py`）：
- **semiauto**（半自动，旧名 `auto`）：`ALLOW` 直接放行、`CONFIRM` 弹确认；
- **manual**（人工审核）：连 `ALLOW` 也强制确认（什么都过一遍）。

**本方案三层全部只在新增的 `strict-auto` 档生效，对 semiauto / manual 零影响：**

| 层 | 实现约束 | 对 semiauto / manual 的影响 |
|---|---|---|
| ① 准入 | **不改 `classify()`**。strict-auto 只是 authorizer 里**新增的一个分支**（一律 `return allowed=True`，不看命令文本）；semiauto / manual 走原分支不变 | **零**——`rm` 在 semiauto/manual 里照旧 `CONFIRM`（网络策略的移除是另一回事，全模式生效，见 §4） |
| ② 边界 | Low 令牌**只在 `strict-auto` 会话**套用；semiauto / manual 仍用普通（Medium）令牌启动子进程（和今天一样，写哪都行、由确认把关） | **零**——否则 manual 批准的"写工作区外"会在 OS 层失败，等于改了 manual 行为 |
| ③ rewind | 被动快照，不改变任何命令的执行语义，只多"可回滚"能力 | **零**（执行语义不变；被动订阅 EventBus，实际全模式都在拍，与模式无关） |

**实现红线**：
```python
# bash_authorizer.authorize 里，在原逻辑【之前】加分支：
d = classify(command, workspace)          # classify 现已无 DENY 分支（网络策略移除后只剩 ALLOW/CONFIRM）
mode = self.mode_store.get(agent.session_id)
if mode == "strict-auto":
    return AuthorizationDecision(allowed=True)   # 纯完整性：不看命令文本，边界交给 OS②
manual = mode == "manual"
# ……原逻辑一字不改……
```
新增内容仅为：`mode_store` 多一个取值 `strict-auto`、前端模式选择器多一项、authorizer 多一个分支、low_integrity 仅对 strict-auto 会话启用。**全叠加式，不触碰任何现有代码路径。**

### 4.5 模式持久化（跨重启保留）

模式（旧名 `auto` 已改名 `semiauto` 消歧义）不再是纯内存，落盘到 `<data>/bash_review_modes.json`：
```json
{ "default": "<新会话默认>", "sessions": { "<session_id>": "<mode>" } }
```
- **每会话记住自己的模式**，跨重启/更新保留；`default` = 用户**最近一次选择** → 新会话默认沿用（原子写 tmp+rename、坏文件回落默认不崩、`path=None` 退回纯内存）。
- **存量会话**（升级前没落过盘）在 `sessions` 查无记录 → 自动回落 `default`，不报错。
- **strict-auto 会话重启后要重激活低完整性**：模式从盘恢复了，但 provider 的低完整性登记表是内存的、重启即丢。故 `apply_mode_low_integrity(session_id, mode)` 在**三处**调用统一同步——① 用户切模式；② 会话创建登记工作区后；③ resume/重启重新登记工作区后。否则会"显示自动模式但实际没边界"。
- 关键节点有日志（回滚 / 模式切换 / 低完整性激活耗时 / GC / 致命黑名单拦截），便于无人值守时回溯。

## 5. 层② OS 工作区隔离（边界层）——真正的强制

核心：**启动 agent 的 python / shell 子进程时，把它的进程令牌降到"低完整性级别（Low）"**。Windows 规则"低完整性进程写不了更高完整性的对象"会让它写不出工作区外，而系统里几乎所有东西默认都是 Medium——于是只需把 {工作区 + 共享环境} 标成 Low，进程就"只能写这几处、别处一律被 OS 拒、读不受限"。**此机制已在目标 Windows 上实测通过（见 §5.6）。**

> 起初设计的是"受限令牌 + `WRITE_RESTRICTED`"（语义更漂亮：每会话一个专用 SID、天然隔离会话、不改用户文件夹）。但 spike 实测：该令牌下 **Python 启动即失败（`0xC0000142`）**——限制 SID 使进程访问不到启动所需的内核对象（窗口站/桌面已补授权仍不够，还差 BaseNamedObjects/ALPC 等），要填齐是 Chromium 级工作量。**逐项排查确认罪魁是"限制 SID/WRITE_RESTRICTED"，删特权、禁 Admin 均无碍。** 故 MVP 改用 Low 完整性级别；受限令牌路子的取舍见 §5.8。

### 5.1 令牌与访问检查（前置）

每个进程持有 **Access Token（访问令牌 = 权限工牌）**：记录身份 SID、所属组、特权、**完整性级别**（Untrusted/Low/Medium/High…）。进程动一个对象时，Windows 先比**完整性级别**（低的不能写高的），再比该对象的权限表（ACL）。普通进程是 Medium，能写宿主能写的任何地方——这就是现在 agent 的 python 想删哪删哪的根因。

### 5.2 机制：Low 完整性级别（MVP，已实测）

- **把子进程令牌降到 Low**：复制当前令牌为 primary，`SetTokenInformation(TokenIntegrityLevel = Low)`。
- **把可写目录标成 Low**：对 {工作区 + 共享环境 + 缓存} 执行 `icacls <dir> /setintegritylevel (OI)(CI)L`。新建文件自动继承 Low。
  > ⚠️ **必须递归标记已有文件**（`/T`）：工作区里用户**已存在的文件是 Medium，Low 进程改不了**（低不能写高）。不递归标记的话，agent 只能新建、**改不了旧文件**。代价：大工作区递归标记有耗时；改动了用户现有文件的完整性（可逆，用户自己的 Medium 程序仍可读写这些文件、无感）。**此场景 spike 已验（§5.6：`/T` 后 `modify_existing=OK`）。**
- **重定向 `TEMP`/`TMP` + `PYTHONPYCACHEPREFIX`** 到一个 Low 目录（Low 进程写不了默认 Medium 的 `%TEMP%`）。

效果（spike 实测）：

| 操作 | 结果 |
|---|---|
| **读**任何位置（系统库、别的项目、用户文件） | Low 可读 Medium → 可读 |
| **写** 工作区 / 共享环境 / 缓存（已标 Low） | Low 写 Low → 通过 |
| **写** 其它任何位置（`C:\`、桌面、别的项目、系统、产品自身，默认 Medium） | Low 写 Medium → **OS 拒** |

**新建文件自动是 Low**（Low 进程创建的对象自动带 Low 标记）→ 无需逐文件操作，新文件天然可写、且仍在边界内。

### 5.3 可写集（收敛版：三个目录 + 两组重定向）

低完整性进程能写的就这几处，其余全部保持 Medium（不动）→ 自动只读。**不枚举"要禁什么"，只列"要放行的"。**
```
{ 会话工作区（递归 /T，含已有文件） }        ← 模型的正经产出。会话专属，绑定会话时标。
{ 全应用共享 venv 根 }                        ← 装包成品。打包态=fs_shared_venv_python 的 venv；
                                               启动时标一次（跨会话共享，不每会话重标）。
{ 一个 low_temp/（所有会话共用，像系统 %TEMP%） }  ← 草稿 + 缓存。启动时标一次。
```
> **venv 分两态（已核对代码）**：
> - **打包态**（`fs_shared_venv_python` 有值）：`bash_auto_venv=False`，**不建每工作区 .venv**——python 由 `_run.py` 头插进 `os.environ` PATH 的**全应用共享 venv** 统一提供，`pip install` 装进该共享 venv。故**共享 venv 根**必须在可写集、标 Low（`label_global_writable_dirs` 启动时标）。
> - **dev 态**（`fs_shared_venv_python=None`）：`bash_auto_venv=True`，每工作区自建 `.venv`（在工作区内，随工作区一起标 Low + `low_shell` 兜底 `label_low(.venv)`）；此时无"共享 venv"这一项（`LowIntegrityLayout.shared_env=None`）。
>
> **谁标什么**：共享 venv + `low_temp` 跨会话共享 → **启动时标一次**；工作区会话专属 → **会话激活时标**（`icacls /T` 只跑在工作区上，避免每次切模式重标大 venv）。

**程序写盘有两大去处，各用一组环境变量重定向到那个 `low_temp/` Low 目录**——这样不用逐个追 pip/npm/matplotlib 等工具：

| 去处 | 重定向的环境变量 | 覆盖 |
|---|---|---|
| ① 草稿（临时） | `TEMP` / `TMP` / `PYTHONPYCACHEPREFIX` | pip 构建、`tempfile`、编译器、各种 CLI 的中间文件 |
| ② 持久（缓存/配置，在家目录/AppData） | `USERPROFILE` / `APPDATA` / `LOCALAPPDATA` / `HOME` | pip/npm 缓存、`~/.cache/*`、matplotlib、huggingface、git 配置…… 全落进来 |

> **为什么两组都要**：光重定向 temp 只盖住"草稿"那一半；pip 缓存、npm 缓存等**持久数据在家目录/AppData、不在 temp**——不重定向"家"，这一半全漏。**给低完整性一个"假家"（指向 Low 目录）是收掉长尾的大杠杆**：所有"往自己家/AppData 写缓存"的程序都透明落进 Low 区，无需知道有哪些程序。
> **副作用**：假家意味着程序读配置也读假家 → 读不到用户真实 `~/.gitconfig` / 身份 token；对 agent 脚本通常无所谓甚至更好（隔离），个别真需要的再单独放行读或预置。

**长尾靠实测收敛，不靠想全**：两组重定向后仍可能有极少数工具用非常规/硬编码绝对路径。这是**兼容性**问题、不是安全漏洞——没想到的路径**默认安全地被拒、只让某工具报 access denied**，不会击穿。用**依赖清单 + 真实负载冒烟测试**（跑真实 `pip/npm install` + 典型 skill）暴露，暴露一个补一个（再加一个重定向或列入排除）。**有界、可收敛。**

### 5.4 Job Object（资源与行为，可选但便宜）

与完整性级别正交，一并加：进程数上限（防 fork bomb）、内存 / CPU 上限、`KILL_ON_JOB_CLOSE`（会话结束 / 崩溃不留孤儿）、UI 限制禁 `EXITWINDOWS`（防脚本调关机）。启动顺序须 `CREATE_SUSPENDED → AssignProcessToJobObject → ResumeThread`，防进程在纳入 job 前 fork。spike 已验证 Low + Job 正常。

### 5.5 组合配方（Low 完整性级别，MVP）

> **⚠️ Office/COM 要走 broker（2026-08-25）**：DCOM 用**调用方的完整性级别**启动进程外 COM 服务器，Low 会话里 `Dispatch('Excel.Application')` 出来的 `EXCEL.EXE` 自己也是 Low（实测 `S-1-16-4096`）；它由 RPCSS 启动、拿不到 §5.3 重定向过的 `TEMP`，连自己的临时文件都写不了，`Workbooks.Add()` 就会失败，报错还伪装成「内存或磁盘空间不足」。同机 Medium 对照组同样操作成功，确证是完整性级别所致。进程内 COM、`Shell.Application`、WMI/RPC 均正常，**只有需要落临时文件的 Office 这类服务器不行**。也试过让 Excel 在 Low 下跑起来：把 `%TEMP%` 标 Low 之后**仍然失败**，再往下就得开放 HKCU 的 Office 键和 `%APPDATA%\Microsoft\Excel`，而那里的 XLSTART 是「用户下次开 Excel 就自动执行」的目录，等于留后门，故放弃这条路。
>
> **最终方案见 `office_broker/`**：COM 由边界外的 Medium broker 进程代持，通过带 Low 完整性标签的命名管道驱动。**agent 侧完全无感知**——投进 PYTHONPATH 的 `sitecustomize.py` 在解释器启动时把 `win32com.client` 换成代理的影子模块，`import win32com.client; Dispatch("Excel.Application")` 这种平常写法原样可用，`constants` 也照常（值从 broker 侧的类型库取）。只有会话里真有 broker（`NLC_OFFICE_PIPE` 在）时才接管，半自动/人工模式下拿到的仍是真的 win32com。
>
> **孤儿 Office 的收尸**：Office 由 RPCSS 启动，**不是 broker 的子进程**，Job 的 `KILL_ON_JOB_CLOSE` 管不到（Job 成员资格只随子进程继承）。故 broker 在 Dispatch 前后做进程快照，把「这次新出现的 PID」记进 `low_temp/office_pids.txt`：正常退出时自己 Quit，被强杀时由 `manager.stop_broker` 照着这个文件收尸（并校验映像名，因为 PID 会被复用）。反过来，**没有新 PID 就说明连上了用户自己开着的 Office**（Excel 是单实例应用），那种一律不 Quit 也不杀，否则会把用户未保存的文档一起关掉。
>
> **⚠️ broker 自己也得跟着 host 一起死（2026-08-25 修）**：冻结态下 broker 的启动命令是 `[sys.executable, "--office-broker"]`，`sys.executable` 就是 **app 自己的 exe**——所以一个活着的 broker 在系统看来就是一个正在运行的 IPMaster-Cowork，它锁着安装目录里的 exe 和 DLL，装新版时 NSIS 报「无法停止 IPMaster-Cowork」。而 Windows 的子进程**不会**因为父进程没了就退出：后端被 `SIGTERM`（Node 在 Windows 上就是 TerminateProcess）或 taskkill 掉之后，broker 原地留下，accept 循环还在等下一个客户端，永远等不到。Electron 的 `stopBackend` 只在后端 5 秒没退时才 `taskkill /T` 整棵树，正常退出根本走不到那条分支；父子关系还得父进程活着才查得到，等后端死了再补 `/T` 也没用。三层修法：① host 侧建一个只带 `KILL_ON_JOB_CLOSE` 的 Job（不带 make_job 那套 UI 限制，那是给 Low agent 子进程的，套到 broker 上只会给 COM 添麻烦），每个 broker 起来就纳入——句柄随后端进程消失而关闭，**正常退出/被强杀/崩溃全都算**，这是唯一一条在后端来不及跑代码时也成立的路径；② broker 带 `--parent-pid`，看门狗线程按 PID **加出生时间**（PID 会复用）每 3 秒查一次，父进程没了就自己收摊，兜 Job 建不起来的情况；③ FastAPI 的 lifespan teardown 里 `stop_all()`，正常关闭走这条，顺带把 Office 也收了。另外后端启动时 `reap_orphan_brokers()` 扫一遍上次遗留的——只杀**父进程已经不在**的（父进程还活着说明另一个 host 正在用），装了旧版本的机器靠这条自愈。
>
> **快照记账有三个坑，放开全家桶之后逐个踩出来了**（2026-08-25，映像名与判定统一收在 `office_broker/procs.py`，两侧共用一份）：① **拍一张快照不够**——实测 Publisher 的 `Dispatch` 已经返回、COM 也能调了，`MSPUB.EXE` 才出现在进程表里，得轮询到看见为止（一看见就返回，所以正常情况根本等不满；等太久反而会把用户这期间自己打开的 Office 误记成我们的）。② **取常量也会拉进程**——`op_const` 里的 `gencache.EnsureDispatch` 会再起一个（实测 Visio：取一次常量就多一个 `VISIO.EXE`），必须和 `Dispatch` 走同一套记账。③ **Office 会拉自己的子进程**——实测自动化起的 `MSPUB.EXE` 还会再拉一个 `MSPUB.EXE` 子进程，只收账本里那个就会漏；故收摊前先把账本里进程的 Office 子孙并进来，且**必须在杀父进程之前取**，父进程一没父子关系就查不到了。broker 被强杀那条路径同理，`_reap_orphan_office` 自己现查一次子孙。这三条都不用「把会话期间新出现的 Office 全杀掉」那种启发式，因为那会误杀用户自己开的。
>
> **Word 的默认文件位置**要写成 `Options.SetDefaultFilePath(0, path)`；参数化属性在晚绑定下写成 `Options.DefaultFilePath(0, path)` 是 TypeError，被 try 吞掉后等于从没设过。边界改由 `office_broker/policy.py` 的闸门守：ProgID 白名单 + 危险成员封禁（Run/VBE/RegisterXLL/AddIns/Shell/SendKeys）+ **参数级**路径校验（绝对路径必须在工作区内、`..` 穿越直接拒、已知带路径成员的相对路径锚回工作区），再加 broker 起 Office 时设 `AutomationSecurity=ForceDisable` 与默认文件位置=工作区。闸门按参数而不是按成员做，是因为 Office 对象模型太大，枚举「哪些方法带路径」必漏，漏一个成员名就等于漏一个越界写的洞。
>
> **白名单覆盖整个 Office 家族（2026-08-25 扩）**：Excel/Word/PowerPoint/Outlook/Access/Publisher/Visio（含 `Visio.InvisibleApp`）/Project/OneNote，前缀按 `.` 整段匹配，`Excel.ApplicationEvil` 这种不放行；非 Office 的 COM（`WScript.Shell`、`Scripting.FileSystemObject`、MSXML）仍然一律拒——这条通道存在的理由是 Office，放开就等于给了任意执行。扩容时三处必须同步改，漏一处就是一个洞或一个孤儿进程：① 危险成员表要补各家自己的「执行代码」入口（Visio `ExecuteLine`/`Addons`、Access-Project `DoCmd.RunMacro`）；② 映像名表（broker 自收 + host 兜底收各一份）要补 `outlook.exe`/`msaccess.exe`/`mspub.exe`/`visio.exe`/`winproj.exe`/`onenote.exe`，`test_office_images_cover_every_allowed_progid` 会盯着这两张表和白名单对齐；③ 后缀表要补 `.vsdx/.mpp/.pub/.one/.accdb/.msg` 等，否则 `SaveAs("x.vsdx")` 不被当成路径、锚不回工作区。防弹框各家语义也不同：Visio 没有 `DisplayAlerts`，用 `AlertResponse = 1`(IDOK)；Access 用 `DoCmd.SetWarnings False`；Outlook/OneNote 两样都没有。默认文件位置：Visio 是 `DrawingsPath`，Access 是 `SetOption("Default Database Directory", …)`。
>
> **常量要跨 app 找**：客户端桩只记得最近一次 Dispatch 的 ProgID，先开 Word 再问 `xlUp` 就会问错类型库。broker 侧记下本会话 Dispatch 过的所有 ProgID，取不到就把它们逐个 `EnsureDispatch` 再取（`win32com.client.constants` 本来就是所有已加载类型库的合并命名空间）。
>
> **弹模态框的 app 会把 broker 卡住**：broker 是单线程串行 STA，某个调用弹出对象模型关不掉的模态框（实测：本机 Outlook 没有可用邮件配置文件，`Dispatch` 成功但会弹「新建配置文件」向导）就会一直阻塞，直到会话结束 `stop_broker` 收摊。这与不走 broker 时的行为一致（那边是 agent 进程自己被卡、由 exec 的空闲超时兜底），差别只在 broker 是会话级共享的，卡住之后这个会话后续的 Office 调用都得等。OneNote 在本机是另一种情况：ProgID 在册但类型库没注册，调用直接报「库没有注册」——这类环境问题原样透传给 agent，不由闸门包装。


> **⚠️ 标 Low 会连带降级 exe（2026-08-25 修）**：Windows 新进程的完整性级别 = `min(令牌 IL, 主映像文件 IL)`。`icacls (OI)(CI)L /T` 会把目录里的 `.exe` 一并标成 Low，于是那些 exe **无论被谁启动**（半自动/人工模式下的 Medium 后端、乃至用户自己在系统终端里）都会跑成 Low 进程；而非 strict-auto 路径不做 §5.3 的 env 重定向，子进程带着真实 `%TEMP%` 以 Low 运行，`pip install` 报 `No usable temporary directory`、pywin32 建 `gen_py` 报 WinError 5。修法是标完立刻把 `.exe` 还原成 M：目录仍是 Low（Low 进程照写），而 strict-auto 靠的是 Low **令牌**（令牌更低时以令牌为准），边界不受影响。受影响的四处都要还原：共享 venv、工作区、本地 skill 目录、云端 skill 物化根。


**谁做**：全部由**后端 app 的 `low_integrity/` 模块**执行（不是引擎、不是模型）。工作区在 **strict-auto 会话绑定工作区时**标记；共享 venv / low_temp 在**首次进 strict-auto 时**标一次（原为启动时无条件标，理由见本节开头的 exe 降级说明）。**不撤回工作区标记**——用户会一直用这个会话对话、反复执行，撤了下条命令又得重标；且 Low 标记对用户无感（用户自己的 Medium 程序仍可读写该目录）。
```
① 复制当前进程令牌为 primary（DuplicateTokenEx）
② SetTokenInformation(TokenIntegrityLevel = Low)
③ icacls：给 {工作区(含已有文件 /T) + 共享 venv + low_temp} 标 (OI)(CI)L（工作区=会话激活时；共享 venv+low_temp=首次进 strict-auto 时标一次）
③b icacls：把上述目录里的 .exe 还原成 M（`windows.restore_executables_medium`，理由见下）
④ env：TEMP/TMP/PYTHONPYCACHEPREFIX + USERPROFILE/APPDATA/LOCALAPPDATA/HOME → low_temp（§5.3 两组重定向）
⑤ （可选）建 Job + §5.4 限制
⑥ 启动：CreateProcessAsUser(Low 令牌, …, CREATE_SUSPENDED) → AssignProcessToJobObject → ResumeThread
```

### 5.6 本项目落地要处理的两点

**① 注入点（已探明，方案确定并落地——内核零改动）**：子进程由内核 `_script_runner.py:spawn_contained` 用 `create_subprocess_shell` 创建，写死、不能传令牌。但**内核的 `FilesystemToolsProvider` 本就设计给 host 继承**（分发走实例字典 `self._invokers`，`_build_invokers()` 可覆盖；app 已有 `BashExecAliasFilesystemProvider` 子类）。最终方案：
- **在 app 的 provider 子类里覆盖 `_build_invokers` 包装 `shell` 处理器**（`make_shell_invoker`）——**dispatch 层零改动**；非低完整性会话原样委托内核 invoker（已实测零行为差异），低完整性会话才进 Low 路径。
- launcher（`low_integrity/windows.py:spawn_low`）用 `CreateProcessAsUser`(Low 令牌) + 自建管道 + 读线程 → `asyncio.StreamReader`；
- **最终选「零改内核」**：不给内核加 `launcher` 参数，而是 app 侧 `low_integrity/low_runner.py` **自带一小段 run-with-liveness**——存活采样/杀树/结果结构等纯原语**全部 import 复用内核**（`_script_runner`/`_encoding`），只重写「起进程」那步换成 Low 启动器，与默认路径逐行对齐。代价：复刻了 shell 的一小段编排（`low_runner`+`low_shell` 约两段 ~40 行），且耦合内核私有模块（升级重命名有静默破风险，可接受）。
- **不需要额外 exe。** ❌ 直接改 vendored 文件不行（升级被覆盖）——这里是"子类继承 + 自带 runner"，vendored 内核一字未动（`git status` 干净）。

**② 环境验证 spike（已跑，全部通过）**：脚本 `dev/probe/win_restricted_token_spike.py`，在**一台真实企业机**上实测：
- ✅ **Low IL 机制通过**：Low 令牌启动，写工作区 / 共享环境 OK、**写工作区外被 OS 拒**、读工作区外 OK；Low + Job 同样通过。
- ✅ **所有解释器一致**：python / **cmd** / **powershell** / **node** 均——能启动、写工作区内通过、**写工作区外被拒**（`--test-interp`）。PowerShell 在企业执行策略下 `-Command` 正常跑，未被拦。
- ✅ **改工作区里已有文件**：递归标 Low（`/T`）后，Low 进程能改工作区里预先存在的 Medium 文件（`modify_existing=OK`）。
- ✅ **企业环境**：EDR / 组策略 / PowerShell 执行策略均未拦令牌降权、进程创建与脚本执行。保留：这是**该组织的策略**，其它客户的 EDR / AppLocker / WDAC 可能更严，不保证每台放行。
- ✅ **纯 Python launcher 实时流式**（脚本 `dev/probe/win_low_launcher_stream_spike.py`）：`CreateProcessAsUser`(Low) + 自建管道 + 读线程 → `asyncio.StreamReader`，子进程每秒一行、父进程收到时间戳 `[0.5,1.5,2.5]` **依次到=实时流**，且写工作区内 OK、写工作区外 DENIED、pid/退出码可取。**证明 launcher 能接进内核 `run_with_liveness`，无需额外 exe。**
- ❌ **受限令牌（restrict SID + WRITE_RESTRICTED）启动失败 `0xC0000142`**；逐项排查（V1–V4）确认罪魁是限制 SID，删特权 / 禁 Admin 无碍 → 故不用它（§5.8）。
- 仅剩：随包 python-runtime（当前用普通 3.12 验证，预计一致，正式接入时 `--python` 再确认一次）。

### 5.7 作用域：所有解释器共用同一套（python / cmd / powershell / node）

降权加在**进程**上，不是加在 Python 上。任何从 Low 令牌启动的进程及其整棵子进程树都是 Low（子进程继承完整性级别 + job）。**准入层只看到被提交的那一行命令，边界层覆盖整棵进程树**——这正是"解释器包装盲区"的根本解法：不是看穿它，而是让内层跑不出边界。**因此 python / cmd / powershell / node 共用同一套令牌 / job / 标记，"写不出工作区外"对它们一视同仁，不额外增加工作量。**

> **"约束一视同仁"是原理保证；"能否在 Low 下正常启动"要逐个验。** 已实测：Python ✅。预判：cmd 几乎必然可（极轻量）、node 大概率可（运行时同类）、**PowerShell 是风险点**——它启动要加载 profile / 模块、写模块分析缓存到 Medium 位置、还有执行策略，Low 下易卡，可能需 `-NoProfile -NonInteractive` + 缓存重定向，兼容差则列入排除清单走人工模式。spike 已加 `--test-interp` 逐个验 cmd/powershell/node，正式接入前跑一遍。

### 5.8 Low IL 的两个限制（实测选定后如实记录）

选 Low IL 换来了"能跑 + 简单"，但相比受限令牌，牺牲两点。在**防手滑 + 本地单用户**模型下均可接受，须在产品/文档写明：

1. **会话之间可互写**：Low 是单一等级，并发的多个 strict-auto 会话工作区都标 Low → A 会话进程理论上能写 B 会话工作区。**风险低**——A 的 agent 只拿到自己会话的工作区路径，不会凭空拼出 B 的路径；主动去写别的会话属"攻击"、不在防范围。
2. **要给用户选的工作区打 Low 标记**：侵入性小（用户自己的 Medium 程序仍可写该目录，无感）。**不在会话结束时撤回**（§5.5：用户会持续对话反复执行，撤了下条又得重标；Low 标记对用户无感）。

**若将来"每会话强隔离 / 不碰用户文件夹"成硬需求**：回到受限令牌路子，代价是啃 `0xC0000142`——用 Process Monitor 定位并授权全部启动内核对象（BaseNamedObjects/ALPC 等，Chromium 级工作量），或改用 AppContainer（但其默认连读都 deny，与"工作区外可读"冲突，需额外放开读）。均为独立课题。

### 5.9 两条写路径（低完整性边界只覆盖一条，另一条已有准入层堵好）

agent 改文件有**两条独立路径**，边界层只管其中一条：

| 写路径 | 谁执行 | 完整性 | 越界写怎么挡 |
|---|---|---|---|
| **shell / 代码执行**（`bash_exec` / 脚本） | **Low 子进程** | Low | ② 低完整性边界（本章）——覆盖整棵进程树、代码算出的路径 |
| **`write_file` / `edit_file` 工具** | **引擎（后端 Medium）直接 I/O**，不经子进程 | Medium | ① 准入层 `fs_write_authorizer.py`——已在非 manual 模式**硬拒工作区外写** |

**互补、无缺口，且两条路径的准入策略【刻意不对称】**：
- **shell / 代码**：有「读写歧义 + 脚本算路径」盲区，且**有完整性网**（Low 子进程）→ strict-auto 准入**纯完整性、不看命令文本**（§4）。path 判断在这里既多余又会误杀合法读（`ls ..`），故删掉。
- **write_file / edit_file**：拿到的就是字面 `path` 参数、**总是写**、无脚本盲区，但**没有完整性网**（Medium 引擎直接 I/O，能写任何地方）→ 准入层**必须**按 path 硬拒越界，否则 Windows 上也照样写穿。故 strict-auto 下这条**保持**非 manual 即 DENY（现有 `fs_write_authorizer` 就是，见 [`auth/fs_write_authorizer.py`](../src/netlivecowork/auth/fs_write_authorizer.py)）——这里 path 判断是干净的、不误杀（写工具本就没有「读」的语义）。

> 一句话记忆：**「有网的路径（shell）交给网、不判文本；没网的路径（write_file）自己按 path 判」**。两者都指向同一目标「工作区外不可写」，只是各用最合适、无副作用的手段。

## 6. 层③ rewind（恢复层）

**目标**：工作区文件可回滚到任一检查点，撤销 agent 的破坏性改动。

**机制 · 自研内容寻址存储（无 git 依赖）**：存储目录放**工作区外**（`<NLC_DATA_DIR>/checkpoints/<session>/`），`.git` 之类不出现在工作区、不被 agent 的通配操作误纳入。结构：
- **blobs/**：文件内容按 `sha256` 命名、`zlib` 压缩存一份；同内容天然**去重**，跨检查点共享。
- **manifests/**：每个检查点一份「路径 → sha256」清单。
- **index.json**：`next_seq` + 各检查点元信息（回合号、时间戳、清单名）。
- **stat_cache.json**：`(mtime,size) → sha` 缓存，**增量快照**只对变过的文件重算哈希，没变的直接查表，快。

  快照 = 扫工作区 → 增量算 sha、写新 blob、落 manifest、更 index。回滚 = 按目标 manifest 把工作区文件逐个还原（写回 / 删除多出来的），再截断该回合之后的对话事件。

**为什么自研而非 git**：只依赖标准库（无需系统装 git）、逻辑透明可控、增量 + 压缩 + 去重、二进制可、跨平台。（早期设计过「影子 git」，后改为此方案去掉外部依赖。）

**与对话时间线对齐**（接现有事件溯源）：用 **turn（每会话用户消息序号，`turn_seq`）** 对齐两条时间线——"回退到第 N 回合" = 文件回到那时 + 对话截到那时。每条用户消息带 `turn_seq`，快照按 turn 幂等建一次；回滚成功持久化一条 `rewind_record` 事件（历史重放也带，标记不丢）。接近 Claude Code 的 rewind 体验。

**边界与代价**：只在回合之间的静止点拍；`node_modules` / venv / `__pycache__` / 大二进制**排除** + 单文件大小上限（`NLC_REWIND_MAX_FILE_MB`），防快照爆炸；每会话保留最近 N 个（`NLC_REWIND_KEEP`），超出 **gc**（连带清理不再被任何 manifest 引用的孤儿 blob）。开关/参数统一由 env 单一来源（见 config.py）。

**前端**：仿 Claude Code——每条用户消息 hover 出现回退图标，点击弹 modal 二次确认（可多次回退）；回滚**只动工作区文件、不改对话历史**；结果走右下角 toast，消息下方内联显示持久化的回滚记录。

**限制（对用户讲明）**：只回滚**工作区文件**；工作区外改动、网络请求、外部 DB、关机等**副作用回不来**。**闭环依赖边界层②**——只有边界把破坏关进工作区，rewind 才能保证"所有破坏都可撤"。

## 7. 三层协同：全自动模式为什么这时才敢开

```
agent 连续执行（全自动）
  ① 准入：全自动下不拦任何命令（含网络）；文件/系统一律放行，不看命令文本
  ② 边界：任何写工作区外（命令 or 脚本算出的路径）→ OS 拒绝；读工作区外 → 放行（强制层）
     → 破坏被限定在工作区内，且合法读不被误杀
  ③ rewind：工作区内的破坏 → 回滚撤销
     → 全自动无人值守，且可恢复 —— 风险可接受
```

**边界齐全时（Windows）**：边界层②（工作区外写被 OS 拒）+ rewind③（工作区内可撤）都在 → 全自动名副其实，风险可接受。

**边界缺失时（Mac/Linux dev、无完整性）——降级，仍可用，不硬拒**：当前实现**允许**用户开全自动，但**显式告知降级**（前端弹 toast：「本平台无 OS 工作区隔离，越界写不再被系统层拦截，仅 rewind 兜底」）。理由：全自动主要在 Windows 打包态用；dev/Mac 是开发测试环境，硬拦反而挡开发。用户被明确告知"没有文件边界"后自行担责——这与产品"防手滑、不防攻击"的定位一致。**执行层的致命红线（§4，format/关机等 7 个）在任何平台仍硬拦**，所以就算 Mac 降级，最灾难的操作也进不来。

> **To B 可选加固**：若某客户要求"边界不可用即禁止开全自动"，留一个配置开关把降级改成硬拒（当前默认是降级+告知，非硬拒）。见 §8 阶段 3。

## 9. 未覆盖 / 边界（产品里说明）

- **不防数据外泄**：Low 令牌只限写（低完整性不能写高，读不受限）；"读用户文件 + 外发"不覆盖。
- **不防有意提权攻击**：用户态方案挡不住内核漏洞；把系统操作藏进 `powershell -c` 之类也不特殊处理——全自动**本就不看命令文本**，全靠完整性②在运行时拦其写操作（写 Medium/HKLM 被拒）。属"不防故意绕过"，与手滑无关。
- **rewind 不撤副作用**：网络 / 外部 DB / 关机等，只撤工作区文件。
- **仅 Windows 有文件边界**：OS 隔离仅目标平台；mac / linux（dev）**无完整性→全自动无文件边界**（仅 rewind 跨平台兜工作区内），越界写会真生效，故 Mac 全自动只作开发/测试用，前端弹降级 toast 明示。
- **开发 / 验证限制**：OS 隔离代码只能在此侧写、**须在 Windows 实测**。
