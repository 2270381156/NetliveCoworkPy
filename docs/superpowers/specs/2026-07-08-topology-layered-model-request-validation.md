# 分层模型验证：~100 条调图请求的路由测试

配套 `2026-07-08-topology-layered-authoring-model-design.md`。目的：验证"用户的自然语言请求应该能被清晰路由到某一层"这条设计原则是否站得住——不是挑容易分类的例子，刻意包含了本对话中真实出现过的请求、以及一批边界模糊/歧义的例子，用来暴露分层模型的缺口，而不是证明它"看起来都对"。

来源：前 3 条来自本次及此前对话中真实出现过的请求（对齐、圈区域、图标语义匹配歧义），其余为覆盖各层的补充样本。

## 结果分析

逐条核对后的准确计数（100 条不重不漏）：

| 分类 | 数量 | 条目 |
|---|---|---|
| 清晰落在单一层（含个别附带字段缺口备注，但归属本身无歧义） | **80** | 其余全部未单独列出的条目 |
| 天然需要跨两层协作，且两层归属都明确（不是歧义）——集中在"加新设备/新组"类请求，天然需要"先①声明再②选皮肤" | **4** | #19 #21 #23 #33 |
| 真正歧义、agent 必须反问才能确定层级，不能自己猜 | **5** | #85 #90 #91 #96 #97 |
| 请求本身指向的能力/字段当前完全不存在（暴露真实 schema/引擎缺口，不是分层选错） | **4** | #24 链路方向、#52 zone 嵌套、#67 同 tier 换行、#80 链路汇聚符号 |
| 根本不在"编辑图内容"这个范畴内（元指令/动作请求/设计判断/导出格式） | **6** | #83 #89 导出格式、#92 重新生成、#93 版本对比、#94 设计好坏判断、#95 检查请求 |
| 单条宏观请求，需要 agent 自己拆解成多条①-⑥层动作 | **1** | #100 |
| **合计** | **100** | |

（另有 #5/#20/#37/#59 四条在表格备注里提到"暴露字段/覆盖面缺口"，但这四条的**层级归属本身是清楚的**——只是该层目前少一个字段/一种资产，不影响路由判断，因此计入"清晰落在单一层"，不重复计入缺口那一类。）

**两组此前没意识到的层边界**，是这次验证真正有价值的产出：

- **③"要不要圈"和④"圈出来的区域之间怎么摆"是两件事**（#47/#50 vs #41-46）——此前设计文档把"zones 的一切"都归进③，这次发现"区域框本身的样式"其实是②（`zoneTypes[type].fill/stroke`），"两个已存在的区域框之间怎么排布"其实是④，只有"要不要给这组设备画个框"才是③。
- **⑥"全局渲染参数"和②"某个编码类型的样式属性"经常用同一句话表达，无法从字面直接判断范围**（#85 线条粗细、#90 配色主题）——不是分层模型错了，是自然语言本身有歧义（"线条细一点"到底指全局还是某个 linkType），这正好印证 `SOUL.md` 已有的"需求含糊时优先 `control__ask_user`"原则在④⑥边界同样适用，不需要新机制。

**结论**：6 层模型对"编辑图内容"这类请求覆盖率 80%（单层清晰命中）+ 4%（多层协作但不歧义）= 84% 无需任何澄清即可正确路由；真正的歧义只有 5%，且都指向"该反问、不该猜"这条已有原则，不需要新设计；6% 的请求从根上就不是"编辑图"（是操作/判断/导出类），不该也不需要被这个模型覆盖；4% 暴露了字段/引擎能力的真实缺口，值得记录但跟"分层是否合理"是两件事。**核心结论：分层本身是合理、可路由的，不需要因为这次验证推倒重来。**
