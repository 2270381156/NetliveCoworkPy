# 拓扑图分层作者模型与检查体系设计

## 背景

图标库功能（`2026-07-07-topology-icon-library-design.md`）完成后，用户希望重新讨论拓扑图整体架构：目标不只是"怎么表达画图"，而是让 `topology-agent` 具备"在用户指导下自主画图、检查、改进"的能力——类比 Claude 生成/修改 HTML 的方式，**主要靠语言层面（形式化数据结构 + 结构化检查）解决，不依赖 agent 去"看"渲染出来的图片**。这是贯穿本文档的核心约束，多次讨论中都据此纠偏。

本文档整理这次讨论确定的分层模型、每个具体概念的归属、检查（Check）体系的边界原则，以及这些决定对 `topology-agent` 的 SOUL.md/ROLE.md/技能/工具的影响。**本文档是设计讨论的结果，尚未拆解成实现计划**——多处标注了仍需进一步设计的开放问题，不代表可以直接照此实现。

## 六层模型

从纯语义到纯像素，六层：

| # | 层 | 一句话 |
|---|---|---|
| ① | 逻辑拓扑 | 节点和关系本身：设备/角色/型号/名称/设备对/组/连接/连接类型 |
| ② | 图示 | 用什么视觉符号表达①层的元素 |
| ③ | Layer（图层合成） | 画布本身固定的渲染层结构：有几层、谁在上谁在下、层间是否透明——**不是画区域框**（那是"zone"，一个跨①②④⑥的独立概念，见下） |
| ④ | 布局 | 元素排布在画布哪里、如何对齐 |
| ⑤ | 走线 | 连线怎么画 |
| ⑥ | 渲染 | 最终 SVG/像素输出 |

分层设计的三条原则（讨论中确认）：

1. **层间映射明确、单向**：上一层的内容（+可选的本层作者化提示）派生出下一层的内容，不应该跳层依赖。
2. **除⑥外，每层都应该是"可见"的、可被 agent 反思修改的**——不是说 agent 要读原始坐标像素，而是每层都该有形式化的数据结构表达，agent 能读取、判断、修改这份结构化数据，而不是盲写①层 JSON 之后祈祷下游层"看起来对"。
3. **用户的自然语言请求应该能被清晰路由到某一层**——这是检验分层是否"清晰、全面"的试金石：如果一个常见请求（比如"把这两台设备对齐"）没有清晰的归属层，说明分层本身还有缺口。

这不是凭空发明的模型——它跟现有代码的隐含结构基本吻合：`role`/`type` 是字符串 key 查表到②层的 `encoding`；`topo.js` 的 `computeLayout()` 是④层；hand 引擎的 anchor 分布/elk 引擎的 libavoid 避障路由是⑤层；`render.js`/`index.html` 的 `drawNodes()`/`drawEdges()` 是⑥层。`render()` 里 `drawZones() → drawEdges() → drawNodes() → drawPorts()` 的固定调用顺序，就是③层这次讨论确认下来的"固定渲染栈"的雏形——代码里早就有这个顺序，只是从没被当成一个独立的、该被明确管理的概念。这次讨论的价值是把这些边界显式化、检查其完整性，而不是重新发明。

## 各概念的层归属（逐一确认）

| 概念 | 归属层 | 现状/结论 |
|---|---|---|
| 设备/链路基础语义（id/role/tier/label/haPair） | ① | 已有，不变 |
| zones（区域） | **不是③**，跨①②④⑥ | 此前两次表述都需要修正：先是"仅限物理区域"（错，逻辑/功能性分组如"EOR+下挂 TOR+服务器"同样是 zone），后来又把 zone 本身当成"③层"（也错）。zone 其实是一个跟"设备"一样、横跨多层的独立概念：成员+类型声明在①，视觉样式（边框实线/虚线、颜色）是②的编码（对应现有 `zoneTypes` 表），包围盒派生在④（不变），画出来是⑥。③在这里唯一管的是：zone 这类元素整体画在渲染栈的哪一层（见下方"Layer（图层合成）"一节，结论是最底层）。zone 跟"设备组/配对"的区别不在物理/逻辑，而在**成员是否合并成一个图标**——zone 不合并，compound icon 合并 |
| 图例面板 | **内置 zone**，跨①②④⑥（同 zone） | **修正**：不只是"用 zone 的画法"，必须真正参与④层布局——图例是整图的一部分，画布整体包围盒要把图例占的空间纳入进去，**不能是浮动在内容之上的 HTML 覆盖层**（现有实现就是这个问题：`#legend` 是 `position:absolute` 的 div，完全不参与坐标计算，宽一点的图就会盖住内容——已经在实际案例里复现过，见下方"案例验证"）。**要不要有图例、摆哪条边、包含哪些分类，都是④层的作者化提示字段**（`meta.showLegend`/`meta.legendPosition`/`meta.legendGroups`，跟 `meta.layoutDirection` 同类），不是④层算法自动算出来的，也不是渲染调用参数——这三点讨论中修正过两轮，详见下方"图例面板的完整分层表达"开头的弯路记录。要不要画边框是②层的样式选择（跟 `zoneTypes` 一样可选），不是必须的。见下方"Layer（图层合成）" |
| DRC 诊断信息（findings） | **不进入渲染的任何一层** | **修正**：最初误把它跟图例面板并列成"内置 zone"，讨论中被纠正——DRC 报告根本不是图纸的一部分，不需要视觉呈现。它只是 `observe_topology`（这个 spike 里对应 `cli.js observe`）的返回值，agent 拿到结构化 findings 后自己判断怎么处理、要不要告诉用户，不需要、也不应该画进渲染结果。现有 `render.js`/`index.html` 里的 `buildDRC()`/`#drc` 面板是这次讨论之前遗留的开发调试便利，要删除 |
| 设备组/配对（"组"，如 HA 对、pool） | ①声明 + ②渲染 | **暂缓**，见文末"复合图标（暂缓）"一节——先把其他架构落地，这个概念不纳入本轮范围 |
| 图标选择（icon key） | ② | 已有，`topology-icon-picker` 技能 |
| 复合图标（compound icon） | ② | **暂缓**，见文末 |
| iconTheme（蓝/黄配色） | **决策在②，字段位置在①**（`devices[i].iconTheme`） | 已正确实现，无需改动。字段挂在设备实例上是因为需要 per-instance 粒度（同角色的不同实例可能要不同配色），不代表这是①层的概念判断 |
| 端口（port） | ①，纯逻辑标签 | 新概念，见下方 |
| 图标大小 | ④，不是② | 决定的是布局占位空间（跟今天的 `deviceRoles[role].w/h` 一样），不是纯视觉选择。**agent 需要能检测"图标是否超出所属 zone"**——这是一条检查需求，不只是派生值。**新发现（案例验证中挖出）**：`w`/`h` 目前是两个独立作者化的数字，同时决定"占地大小"和"长宽比"——一旦某个角色设了 `icon`，长宽比这部分不该继续独立作者化，应该跟着图标的原生比例走（图标 SVG 自己的 viewBox 长宽比），否则 `preserveAspectRatio="xMidYMid meet"` 会在非约束维度上留出空白，导致那个方向的连接端口视觉上"悬空"，看起来没连到设备上——这是一类系统性 bug，不是个例。占地大小（比如只保留一个 `h` 或缩放系数）仍然合理保留作者化用于视觉层级；长宽比设了 `icon` 之后就不该是自由变量。详见下方"案例验证" |
| 文字内容（label/legend 文案） | ① | 已有，不变 |
| 文字大小、文字位置 | ④，**不是⑥** | 需要架构调整：目前 `labelSize`/`roleSize`/`iconHref ? 下方 : 居中` 这些判断写死在 `render.js`/`index.html` 的 `drawNodes()`（⑥层），本次讨论认为这些应该是布局阶段（`topo.js` 的 `computeLayout()`）的派生输出，⑥层只管拿现成的几何值组装 SVG，不再自己做任何取舍 |
| 端口连线的锚点几何位置 | ④，全派生 | 现有算法（`sideToward()` + 按对端坐标排序 + 沿边均匀分布）已经天然实现"端口锚点离对端最近"，端口标签的声明不影响这个算法，不需要改 |
| 走线路径本身（hand 简单锚点 / elk 避障路由） | ⑤ | 已有，全派生，本次讨论没有发现表达力缺口 |
| 全网状连接下的视觉对齐（core-agg 全网状，想让特定 agg 出现在特定 core 下方） | ④，**独立未决问题** | 确认这不是设备组/配对问题（agg 之间不是同一个逻辑设备的冗余实例），是纯定位问题。方向上需要一个类似 `pairHint`/`alignWith` 的④层作者化字段，具体形状本次未设计 |

## 端口（port）

- 纯逻辑概念，**不代表物理端口**，没有"一个端口只能接一根线"的约束——如果①层显式声明一个逻辑端口接了两条链路，下游层应该服从这个声明，不视为错误、不做任何校验。
- **没有设备级的端口清单**——不需要在 device 上预先声明所有端口。只有链路端点上一个可选的自由文本标签（`aPort`/`bPort`），纯粹给 agent/用户自己做语义区分用（比如想表达"这两条链路虽然连的是同一台设备，但逻辑上是两个不同的连接点"）。
- 不影响布局坐标——现有的"按对端位置排序、沿边均匀分布"算法已经天然实现"端口锚点离对端最近"，不需要为端口标签加任何额外的布局逻辑。
- **没有对应的 DRC 检查**——两条链路引用同一个端口标签不是错误，是合法声明，DRC 不该管。
- 只有两种画法：链路只引用设备（现状，默认），或链路引用设备+端口标签（新增可选字段）。

## Layer（图层合成，③）

这是本次讨论里被纠正最多次的概念，最终结论：③跟"zone/区域"完全无关，是画布本身固定的渲染层结构——传统画图工具（Illustrator/Visio 那种）用的是用户可以任意创建、任意重排的通用图层系统，**这里明确不要那种复杂度**：agent 和用户都不需要、也不应该去操心"图层管理"，我们只需要一套**固定的、预先定义好**的渲染栈。

**固定渲染栈（从底到顶）：**

1. **Zone 层** — 用户声明的区域框（见上）
2. **连线层** — links/edges
3. **设备层** — 设备图标/框（复合图标暂缓，未来加入时也走这一层，不需要新层）
4. **端口标记层** — connType 锚点标记（圆点/方块），画在设备之上
5. **文字层** — 设备 label/角色 legend 文字，独立于设备层的一次绘制，保证文字不会被任何其他元素（尤其是端口标记）遮住
6. **内置 Zone 层** — 图例面板，顶层，保证图例始终可读（DRC 诊断报告不进渲染，见下方"图例面板的完整分层表达"）

这不是全新设计——第 1-4 层的顺序，现有 `render()` 函数（`drawZones() → drawEdges() → drawNodes() → drawPorts()`）已经在这么做了，只是从没被当成一个独立概念管理过。真正的变化是第 5 层（文字从"设备绘制的一部分"拆成独立一步）和第 6 层（图例面板从"HTML 覆盖层特例"改造成"内置 zone"，纳入同一套渲染机制；DRC 诊断面板直接从渲染结果里删除，不属于这层）。

**关于内置 Zone 层的重要澄清**：这里说的"顶层"只是画的先后顺序（保证不被别的元素盖住），**不是让图例悬浮在主图内容之上**——图例本身的位置和占地必须像任何其他元素一样，参与④层的布局计算：布局引擎在主图的某条边（上/下/左/右）之外预留出图例需要的空间，画布整体包围盒因此扩大，图例被摆在这块预留空间里，跟主图内容互不重叠。"画在最顶层"只是防御性的绘制顺序保证，真正解决"会不会盖住内容"这个问题的，是④层真的给它分配了独立空间，而不是让它继续用 `position:absolute` 浮在已有内容上面（这是现有实现的真实状况，也是问题的根源）。

**不是这一层的职责**：agent 不能新增图层、不能重排这个栈、不能声明某个 zone"这次要画在最上面"——这套栈是渲染器的固定实现细节，不是 authored 内容。跟"颜色靠哈希调色板派生，不需要 agent 操心"是同一类信任边界。

## 图例面板的完整分层表达（DRC 报告不进渲染）

"内置 zone"解决了图例该不该占独立空间的问题，但图例作为一个跟设备/zone 一样的一等公民，该在**每一层**怎么表达，需要逐层说清楚，不能只停在④层布局这一点上。**这一节只覆盖图例面板**——上一节表格已经修正过：DRC 诊断报告经讨论确认不是图纸的一部分，完全不做视觉呈现，只作为 `observe_topology` 的返回值交给 agent，不需要④层占位、不需要⑥层绘制，原来设想的"DRC 面板也要参与④层布局"整个作废，`render.js`/`index.html` 里的 `buildDRC()`/`#drc` 直接删除。

本节的结论经过好几轮修正才收敛，记录一下走过的弯路，避免以后重蹈：最初把"摆哪条边""要不要显示"都设想成 `render_html` 调用时的参数（跟选 hand/elk 引擎归一类）；用户指出摆边不该是④层自动选算法、该是用户/agent 驱动的选择后，第一次修正只挪对了"谁来决定"，没挪对"这个决定该记在哪一层"——把"会真正改变④层派生结果的字段"和"纯粹的⑥层展示开关"混成了一类。按分层框架重新过一遍才理清：**凡是会改变④层派生出的坐标/包围盒结果的字段，都是④层的作者化提示，跟 `meta.layoutDirection` 同类；只有真正不改变④层任何计算结果、单纯决定"画不画"的，才是⑥层的展示开关。** 图例的"摆哪条边""包含哪些分类"显然会改变④层算出来的包围盒/坐标，是④层字段；"要不要有图例这块区域"一开始想当然地归成⑥（类比"计算了但选择不画"），但这站不住——不存在"算出了图例布局、但这次选择不画"这种中间态，"没有图例"就是一个结构性事实（跟 zone"没声明就不存在"是一回事），不是"算了但藏起来"，所以**这三个字段最终全部归④，`render_html` 侧不需要任何图例相关的参数**。

**①层：不是独立作者化的 JSON 块，是显式的派生数据结构**——图例的内容（哪些角色/链路类型/接口类型/区域类型出现、对应的图例文案）100% 可以从现有数据 derive 出来（`usedEncodings(model)` 扫一遍实际引用了什么，再去各 `xxxTypes` 表查 `legend` 字段），不需要任何新的作者化字段，agent 不用写、也不该写。这跟 zone 不一样：zone 的成员归属是真实的、无法从别处推出来的作者化事实，图例的内容是纯投影。现在的问题不是"缺一层①层表达"，是这份派生结果被闷在 `buildLegend()` 函数内部、只有渲染时才算一次，agent 读不到——需要把它变成一个显式、独立、可读取的派生数据结构。

**③层的一个额外发现：图例分组不是一套独立发明的分类，是 L3 固定渲染栈的投影**——L3 固定渲染栈（Zone 层/连线层/设备层/端口标记层/文字层/内置 Zone 层）里，除了文字层和图例自己所在的内置 Zone 层，其余四层正好一一对应四张编码表（Zone 层↔`zoneTypes`、连线层↔`linkTypes`、设备层↔`deviceRoles`、端口标记层↔`connTypes`）——这也正好是图例现有的四个分组。两者的分类依据是同一件事："这张编码表对应哪一类可视元素"，L3 定的是画的时候谁在谁上面，图例分组定的是归类的时候按什么 token 类型分。所以 `legendGroups` 不需要另造一套分类词汇表，直接复用这四张编码表的名字即可。**呈现顺序不强制跟 L3 画布顺序一致**——默认顺序沿用现有实现已经在用的"设备→链路→接口类型→区域"，用户可以通过调整 `legendGroups` 数组的顺序自由改变。

**④层：三个作者化提示字段（都在 `meta` 下，跟 `layoutDirection` 同类），加上两套内部排布算法**：

- **`meta.showLegend`**（布尔，缺省 `true`）——要不要有这块图例区域。为 `false` 时④层不产生任何图例几何数据，不占用整体包围盒的任何空间，等同于"这张图没有图例"；不是"算了但选择不画"。
- **`meta.legendPosition`**（`top`/`bottom`/`left`/`right`，缺省 `bottom`）——图例区域摆哪条边。
- **`meta.legendGroups`**（有序数组，缺省 `["deviceRoles", "linkTypes", "connTypes", "zoneTypes"]`，即现状顺序）——一个字段同时管"包含哪些分类"（数组成员）和"呈现顺序"（数组顺序），不需要额外的排序字段。
- **外部包围盒**：位置、宽高用主图的世界坐标系表达（在 `legendPosition` 指定的那条边之外预留空间，画布整体包围盒相应扩大），拿去跟主图内容做包含/重叠检查——这是图例真正"参与④层"的意义所在。
- **内部排布：按 `legendPosition` 分两套算法**——
  - **左/右摆放（竖列）**：标题在上、条目纵向一行一个，按 `legendGroups` 顺序堆叠所有分组，就是今天已有的样子。摆在侧边时天然该是竖的。
  - **上/下摆放（横向流式换行）**：标题在每组左侧、所有组的标题左缘对齐成一个固定宽度的"标题列"；条目从标题列右侧起横着排，排满主图宽度（宽度预算 = 主图 bbox 宽度）就换到下一行；换组强制另起一行。跨行时标题只出现在该组第一行（顶部对齐，不重复、不垂直居中）。没有 DOM 量不了真实文字宽度，按字符数估算条目宽度（CJK≈1 字宽、ASCII≈0.55 字宽），精度够用。摆在上/下时天然该是横的、矮胖的，跟侧边的竖列是两种形态。
  - 两套算法产出同一套"分组→标题+条目行"的数据结构（每个条目带自己的 x/y 世界坐标），⑥层的 `drawLegend` 不区分方向、直接读坐标画，不需要为两套排布各写一份渲染。
- 图例内部的行高、图标大小、文字大小、分组间距，用一套独立于设备间距常量（`ROW_GAP`/`H_GAP`）的世界单位常量（数值上沿用现有 CSS 的行高/字号比例换算）——图例是 `#world` 里的真实 SVG 内容，跟设备/zone 用同一个坐标系画，用户交互缩放主图时图例跟着一起放大缩小（讨论中明确选择的行为：图例是真正的一等公民，缩放表现应该跟设备/zone 完全一致，不搞"HUD 常驻不缩放"的特例，类比 PPT/Visio 里整个画布缩放时标注元素也跟着一起缩放）。

**已记录、暂不展开的后续优化**：上/下摆放的横向流式换行里，每个分组是"标题 + 条目横着流、排满换行"。更聪明的做法是把条目数悬殊的大组（比如"设备"8 条）主动拆成多个定长子列，子列（不分属于哪个组）再按宽度预算统一横向装箱——比单纯的流式换行更紧凑、更整齐。这个需要一个动态决定"拆几列""怎么装箱"的算法，讨论中明确决定先不展开设计，v1 就用上面的流式换行，这条作为已知的后续改进方向记录下来。

**⑥层：`showLegend` 已经不是⑥层的字段**（归④，见上）——⑥层此时只是单纯地把④层算好的 `layout.legend`（如果存在）画成 SVG；`layout.legend` 不存在（`showLegend:false`）时⑥层自然什么也不画，不需要单独判断。

**图例相关的一切都在 `.topo.json` 模型里，`render_html` 不需要任何图例相关的调用参数**——这跟"DRC 不进渲染"是同一轮讨论修正的结论，但原因不同：DRC 是因为它压根不该视觉呈现；图例是因为"摆哪、放哪些、要不要有"全都会实际改变④层派生结果，跟 `layoutDirection` 一样该被记在模型里、可复现、agent 可读可改，不是一个转瞬即逝的渲染选择。

## 案例验证：一次具体的数据中心组网图诊断

用一个典型 Spine-Leaf 数据中心拓扑（19 台设备、26 条链路、2 个 zone，覆盖 `haPair`/`satelliteOf`/`trunk`/`zones`/`aPort`/图标 等本文档讨论过的几乎所有机制）实际画出来、逐条排查观察到的问题，用来验证这次讨论定的原则站不站得住，也顺带挖出了几个新问题。

### 验证成功的部分

- **"agent 靠语言层面判断，不靠视觉"这条核心约束基本站住了**：观察到的 5 个问题里，4 个（图例图标不匹配、服务器文字压 zone 边框线、leaf 侧端口标记漏了 `bConn`、FW-FW 的 HA 链路被 BR 的方框挡住）全部靠读 JSON 模型、`computeLayout()` 的坐标数值、以及 `render.js` 源码诊断清楚，全程没有用截图。唯一需要视觉确认的是第 5 个问题（图标留白导致端口"悬空"）——但即使这一个，根因也是能从两组数字（图标 SVG 自己的 `viewBox` 长宽比 vs 设备方框的长宽比）直接推出来的，视觉只是确认了精确的表现形式（约束维度贴合、非约束维度留白），不是靠视觉才能发现问题存在。
- **"检查暴露数据、agent 决定怎么修，修法可能不在原来那一层"这条原则被验证了两次，且都很有说服力**：
  - FW-FW 被 BR 挡住：写了一段约 15 行的线段-矩形相交检测，直接从 `computeLayout()` 的坐标数据算出结构化 finding（形如 `{link: "FW1-FW2", blockedBy: "BR1"}`）。看到这条 finding 之后，正确的修法根本不在⑤走线层（不是"让引擎绕开障碍画折线"），而是①层建模本身错了——FW 不该用 `satelliteOf` 挂在 BR 旁边当旁挂设备，该是 Internet→BR→FW→Spine 这条数据流上独立的一层（典型数据中心的边界安全层本来就该是这样）。如果渲染器自己悄悄用折线绕开障碍，这个建模错误会被永久掩盖——图看起来"没问题"但语义是错的。这是本次案例里最有说服力的一次验证。
  - 服务器文字压 zone 边框线：同样不该由渲染器自己悄悄对账 `ZONE_PAD` 常量和文字实际占用的高度，而是把重叠量算出来作为 finding 暴露给 agent，让它自己判断怎么改（加大 zone pad？缩小字号？把某些设备挪到别的 zone？）——决定权在 agent，不在渲染器。
- **DRC 的边界画对了，没有漏判也没有越界**：这张图从头到尾 DRC 都是 100 分零发现，5 个问题里没有一条该由现有 DRC 抓（3 个是实现/建模问题，2 个正好是本文档已经规划、但还没实现的新几何检查——zone-containment 需要扩展到"含文字的完整占用范围"，以及一条尚未命名的新检查"边是否穿过非自身端点的设备方框"，语义上类似 box-overlap，见下）。

### 挖出的新问题

1. **`deviceRoles[role].w/h` 不该继续同时决定"占地大小"和"长宽比"**——在图标功能出现之前，`w`/`h` 就是设备唯一的视觉表示（一个纯色矩形），这时候"占多大地方"和"长什么形状"是同一件事，独立作者化两个数字完全合理。图标功能上线之后，这两件事被悄悄拆开了，但字段没有跟着拆：一旦某个角色设了 `icon`，长宽比这部分完全由图标决定了，`w`/`h` 这时候只是"图标被塞进去的容器"——容器长宽比跟图标原生长宽比不一致时，`preserveAspectRatio="xMidYMid meet"` 会在非约束维度（fit 的时候没被撑满的那个方向）留出空白，导致那个方向上的连接端口视觉上"悬空"，看起来没接到设备上。这是本次案例最有价值的发现——比"加一条检测两者比例是否匹配的 DRC 规则"更好的修法是**从根上让这类 bug 不可能发生**：占地大小（比如只保留一个 `h` 或一个缩放系数）仍然合理保留作者化，用于表达视觉层级（比如核心设备画大一点）；长宽比一旦设了 `icon` 就不该再是一个能选错的自由变量，应该跟着图标的原生比例走。新增到"图标大小"概念表格行，以及下方问题清单。
2. **`buildLegend()` 从没跟着图标渲染功能一起升级**——设备图例目前永远画纯色 `<rect>` swatch，完全不读 `role.icon`，图上画的是真图标、图例里却是色块，两者对不上。这是 Task 4（图标渲染）落地时只改了 `drawNodes()`、漏改了 `buildLegend()` 留下的不完整实现，是纯粹的实现 bug，不涉及任何设计决策，直接修。
3. **图例面板必须真正参与④层布局，不能是浮动 HTML 覆盖层**——这次案例直接复现了这个问题（较宽的图例面板挡住了 FW-2）。已经更新到上面"内置 zone""Layer（图层合成）"和新增的"图例面板的完整分层表达"三处的描述里。**DRC 诊断面板则确认根本不该出现在渲染结果里**（下一轮讨论修正，见"图例面板的完整分层表达"开头），不是"要不要参与④层布局"的问题，是直接从渲染代码里删除。

## 检查（Check）体系原则

### DRC 的边界（本次讨论修正过一次）

**初版原则（讨论中被否定）**："DRC 检查所有可结构化验证的声明"——这个原则太宽。用户举了反例：两台设备允许显示相同的 label（人类设计者可能就是想这样），或者允许图纸完全不显示图例——这些都是合法的风格选择，不该被 DRC 判定成问题，即使它们"可以被结构化验证"。

**修正后的原则**：**DRC 只检查会真正破坏/污染渲染结果、或违反明确结构化指令的东西——不检查任何"虽然不常见但依然合法"的内容/风格选择。**

判断测试：违反这条规则，是否会让渲染结果本身出错、损坏、或产生引用歧义？如果只是"不寻常但没错"，就不是 DRC 的职责。这跟 DRC 从"Design Rule Check"改名成"Drawing Rule Check"时定下的原意（"这里画的是抽象拓扑，同一种网络结构有很多种同样合法的画法"）是同一条线的延伸，只是这次把它应用到了①②层以外的场景。

### 具体分类

**DRC 应该检查（真正的结构性缺陷）：**

| 规则 | 为什么是缺陷（不是风格） |
|---|---|
| `legend.*-missing` | 引用的编码没有定义，渲染没有东西可画——已有 |
| `naming.duplicate-id` | id 是引用的唯一凭据，重复会让所有引用（links/zones/satelliteOf/haPair）变得歧义——已有 |
| `naming.missing-label` | `render.js` 里 `lbl.textContent = n.label`，`label` 为 `undefined` 时会在图上渲染出字面量 `"undefined"`——真实的可见缺陷，不是风格——已有 |
| zone-containment（新，案例验证后细化） | 设备包围盒超出所属 zone 边界，虚框失去了"圈住成员"的意义——视觉上明显是错的。**细化**：案例中发现设备本身在 zone 内、但设备下方的文字标签超出了 zone 边界（文字压线），所以这条检查要圈的不是"成员的方框"，是"成员的完整可视范围（方框+文字）"，前提是文字大小/位置已经挪进④层（见开放问题 4） |
| box-overlap（新） | 两个设备包围盒重叠，是真实的渲染缺陷，不是审美问题 |
| route-blocked-by-device（新，案例验证中发现） | 一条边的直线路径穿过了非其自身端点的另一台设备的包围盒——线被设备挡住、视觉上看不出连接关系，比"线交叉"更严重（交叉线依然可辨认，被挡住的线完全不可见）。可以用线段-矩形相交检测直接算，`computeLayout()` 的坐标数据已经够用，不需要新的派生数据。案例中 `{link: "FW1-FW2", blockedBy: "BR1"}` 就是这条检查该输出的 finding 形态 |
| alignment-hint-satisfaction（新，待④层对齐字段设计完成后） | 一旦有了作者化的对齐提示，检查派生出的坐标是否真的满足这个提示——这是"派生结果有没有忠实执行明确指令"，不是判断指令本身好不好 |
| 复合图标引用的模板 key / 基础图标 key 必须存在（暂缓，复合图标本身还没引入） | 跟 `legend.*-missing` 同类——引用不存在的东西，渲染没法画 |

**DRC 不应该检查（本次讨论纠正，属于合法的风格选择）：**

| 规则 | 现状 | 为什么不该是 DRC |
|---|---|---|
| `naming.duplicate-label` | 目前是 `warn` | label 只是显示文本，不参与任何引用解析，重复不影响渲染正确性——用户举的原始反例。**建议移除** |
| `legend.*-empty` | 目前是 `warn` | 图例文案为空是合法选择（用户可能就是不想显示这条图例的文案），不影响渲染正确性。**建议移除** |

**不属于 DRC，属于 agent/reviewer 的语义判断：**

- 拓扑是否真的体现了用户需求（如"要双活防火墙"）——`ROLE.md` 的 reviewer 角色已经在做，只覆盖①层。
- 图标/模板选择是否恰当——`topology-icon-picker` 技能里已经明确是语义判断，允许 agent 拒绝勉强匹配。
- 整体"好不好看"——从来不是 DRC 的职责，跟"抽象拓扑，一种网络结构有很多种同样合法画法"的原始结论一致。

### 悬而未决

**④层新检查（zone-containment / box-overlap / route-blocked-by-device / alignment-satisfaction）应该合并进现有 `observe_topology`/DRC 报告，还是做成独立工具？** `drc.js` 的 `runDRC(model, layout)` 从函数签名建立起就一直带着一个 `layout` 参数，但所有调用点（`cli.js`/`render.js`/`index.html`）都只传 `runDRC(model)`——这个参数是死代码，从没被用来做任何坐标检查。这正好是本次讨论发现的问题（"agent 只看布局结果就说 ok，因为压根没有坐标层面的检查"）的技术根源：接口早就预留了，只是没人接上。是把这个参数真正接上、让 `observe_topology` 的报告里多出④层 findings，还是拆成新工具（如 `observe_layout`），本次讨论没有定论。

## Agent / Skill 层面的设计含义

以上都是数据模型/检查体系层面的结论。下面是这些结论对 `topology-agent` 本身（`resources/agents/topology-agent/SOUL.md`、`ROLE.md`、技能、工具）的影响——这部分是本次讨论衍生出的推论，还没有跟用户逐条确认，需要作为下一轮讨论的起点，不是已拍板的设计。

### SOUL.md 工作流的影响

现有工作流（简化）：① 构造/读取 `.topo.json`（可选用 `topology-icon-picker` 选图标）→ ② 调 `observe_topology` 拿 DRC 报告 → ③ 修 `error`、重新 `observe_topology` 直到清零 → ④ 调 `render_html` 落盘、`finish_task`。

在新模型下，可能需要的变化：

- **步骤①扩展**：遇到"对齐""放在哪个下面"这类请求，需要路由到（尚未设计的）④层对齐提示字段，而不是像此前发生过的那样误用 `satelliteOf`（`satelliteOf` 语义是"同层旁挂"，跟"跨层对齐"完全是两回事，此前已经在实际使用中踩过这个坑）。（复合图标技能暂缓，见文末，"这几台设备是一对/一组"这类请求近期仍按现状——两个独立设备+虚线 HA 链路——处理）
- **步骤②③扩展**：如果④层检查最终并入同一份 DRC 报告，agent 需要能读懂新增的 finding 类型（zone-containment/box-overlap/alignment），并且知道怎么修。这里有一条核心约束必须保持：**agent 永远不能自己写坐标**（`SOUL.md` 现有的"绝不写任何坐标字段"铁律不能因为新增④层检查就被打破）——agent 只能通过调整①②③层的声明（比如把设备挪到别的 zone、调整 tier、缩小 role 的 w/h）去间接影响④层的派生结果，然后重新检查，形成"改声明 → 重新派生 → 重新检查"的闭环，而不是"直接改坐标去满足检查"。

### ROLE.md（reviewer）的影响

目前 reviewer 只读 DRC 报告 + JSON 语义，判断①层的用户需求是否体现。如果④层检查并入同一份报告，reviewer 的"评估要点"需要新增一条：新的④层 findings（如果存在）是否已清零，用跟现有"error 级别是否清零"一致的门槛逻辑判断，不需要额外发明新规则。

### 技能（Skills）清单

- **已有**：`topology-icon-picker`——给一个设备角色选基础图标 key，语义匹配、允许拒绝。
- **暂缓**：复合图标选择技能——给一组设备选"模板+基础图标"，模式跟 `topology-icon-picker` 类似（提供人类可读的模板参考表，agent 按语义判断，允许声明"这几台设备不该合并成复合图标"）。见文末"复合图标（暂缓）"一节。
- **待定**：④层对齐机制本身是否需要配套技能——取决于对齐字段最终的设计形态；如果只是一个简单字段（比如"对齐到某个 id"），可能不需要技能，"要不要对齐"是语义判断（agent 自己拿捏），"怎么声明对齐"只是填一个字段，不需要"选择"。

### 工具（Tools）的影响

- `topology:observe_topology`——待决：是否扩展纳入④层检查（需要真的把 `layout` 传进 `runDRC`）。
- `topology:render_html`——内部实现需要重构（把 `labelSize`/`labelY`/`roleY` 这类派生从 `render.js`（⑥）挪到 `topo.js` 的 `computeLayout()`（④））。**对外输入契约不需要新增任何图例相关参数**——`showLegend`/`legendPosition`/`legendGroups` 讨论到最后全部收敛成 `meta` 下的④层作者化字段（详见"图例面板的完整分层表达"），跟 `layoutDirection` 一样写在 `.topo.json` 里，`render_html` 只读 model，不需要额外调用参数。**也不需要 `showDrc` 之类的参数**——DRC 诊断面板确认不进渲染，`buildDRC()`/`#drc` 直接从代码里删除，不是一个可开关的展示选项。
- 可能新增：`topology:observe_layout`（如果最终决定跟 `observe_topology` 分开）。

12. **硬编码常量审查——哪些渲染/布局常量该开放成 `meta` 下的作者化字段，哪些不该**：起因是讨论"用户中途要求调整某个具体细节（比如缩短纵向间距），这个调整能不能被记住、下次重新生成还在"时发现，`topo.js`/`render.js` 里有一整批这样的常量——不是"该存在哪层"的问题，是"压根没有字段可以存"，不管后面持久化架构怎么设计，这些请求都没地方落笔。判断标准沿用今天已经用过的"这是用户大概率会主动提的调整，还是纯审美选择，不该预判性地字段化"（跟"设备端口默认样式该不该②层化"是同一把尺子）。审查结果按优先级分三档：
   - ~~**高优先级（大概率被直接问到，应尽快补成 `meta` 字段）**~~——**已落地**（2026-07-24）：`meta.rowGap`/`meta.hGap`/`meta.zonePad` 三个作者化字段已生效（`regions.js` 的 `metaLayoutOverrides()` 统一提供给两个引擎），同时行距语义从**中心距改成净空距**（内容多高都吃不掉留白），`tier` 随之变成纯序数；另加了 `CFG.SATELLITE_GAP`（旁挂贴靠，从 `H_GAP` 独立出来）和 per-zone 的 `rowGap`/`hGap` 覆盖。见 `2026-07-24-topology-layout-vocabulary-and-geometry-observe-design.md`。原文记录：`CFG.ROW_GAP`（相邻 tier 行距）、`CFG.H_GAP`（同 tier 内设备间距）、`CFG.ZONE_PAD`（zone 虚框外扩距离）——三者都跟 `layoutDirection` 同类，`computeLayout(model, opts)` 已经支持 `opts` 覆盖 `CFG`，只需要在 `serve.js`/`cli.js`/`render.js` 三处调用点把对应的 `meta.rowGap`/`meta.hGap`/`meta.zonePad` 塞进 `opts`。
   - **中优先级（可能被提到，且有的现在连"耦合关系该不该解开"都还没讨论过，不只是缺字段）**：
     - **设备文字大小没有独立开关**——`render.js` 里 `labelSize = Math.max(7, Math.min(12.5, n.h * 0.27))`，字号完全是 `n.h` 的比例函数，"字体大一点、但设备框别跟着变大"这类请求现在做不到，字号跟设备大小耦合在一起，比"缺一个字段"更深一层。
     - `LEGEND_CFG.PANEL_W`（图例竖列宽度，今天刚加的，"图例太宽/太窄"是合理的后续请求）。
     - trunk 双线偏移量 `off = 2.4`（`render.js drawEdges`）、connType 标记半径 `r=3.6`、基础端口点半径 `r=2.1`（`render.js drawConn`/`drawPort`，后两者也是"未分类接口该有自己的编码"这条待办的一部分）。
   - **低优先级（纯审美常量，不建议现在开放，除非以后有真实反馈）**：zone 边框圆角 `rx:12`/虚线 `"7,5"`、设备框圆角 `rx:7`、图例内部除 `PANEL_W` 外的行高/间距细节（`TITLE_H`/`ROW_H`/`GROUP_GAP` 等）。

## 复合图标（compound icon，暂缓）

这次讨论确定的方向，但**明确决定暂不引入**——先把上面这套架构落地跑稳，再回来做这个。放在文档最后，标记为暂缓，不代表设计不成立，只是排在后面：

- 预先设计一个**组合模板目录**（如 `pair-overlap`、`pool-stack-3`），每个模板定义固定的组合结构（多份图标之间的偏移量、缩放比例、层叠顺序），模板本身不含具体图标内容，是纯结构。
- Agent 需要做两个选择：(a) 一个模板 key，(b) 一个已有的基础图标 key（复用现有 35 个图标目录的 key，不新增）。渲染时把基础图标按模板结构组合，agent 不手绘/生成 SVG——这跟基础图标目录"只能从策展好的集合里选，不允许模糊匹配/自由发挥"的信任边界完全一致，只是多了一层组合。
- 具体例子（讨论中给出）：`pair-overlap` 模板 + `agg-switch` 图标 = "汇聚交换机对"复合图标；同一个模板换成 `firewall` 图标 = "防火墙对"复合图标——模板结构不变，只换皮肤。
- **待设计**（暂缓，不是当前阻塞项）：具体需要哪些模板、每个模板的组合参数、以及选择模板+图标的技能（类比 `topology-icon-picker`）的设计细节，本次讨论只定了方向，没有定细节。
- 连带暂缓的："设备组/配对"（①层声明"这几台设备是一组"）本身也一起推迟——单独声明分组、却没有任何渲染能力去表达它，意义不大，两者一起做。
