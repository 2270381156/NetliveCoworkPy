# 自定义增量更新设计

## 0. 一句话

首次安装继续用 NSIS 向导（可选目录）；**更新**改为**自研的应用内增量更新模块**——只下载变化的文件、进度完全自控、不弹选目录、原地替换、自动重启。

---

## 1. 背景与目标

### 1.1 现状痛点
- 现用 `electron-updater` + NSIS 全量安装器。`disableDifferentialDownload = true`，每次更新**全量下载整个 Setup.exe** → 慢。
- 更新即"重新跑一遍安装器"：`quitAndInstall(false)` 会弹出**完整向导（含选目录页）**；`quitAndInstall(true)` 静默但**无任何进度**、干等。
- NSIS 的"是否一键 / 是否可选目录"是**打进安装包的**，首装与更新共用同一安装器，**无法**用标准配置做到"首装可选目录、更新只显示进度且不选目录"。

### 1.2 目标
1. **首次安装**：保留 NSIS 向导，可选安装目录。**（不改）**
2. **更新**：
   - 只下载**变化的文件**（真增量），显著减小下载量。
   - 进度**完全自控**（应用内进度条），不再干等。
   - **不弹选目录**、**原地更新**、装完自动重启。
3. **可靠**：完整性校验、失败可回滚、正确处理运行中文件锁。
4. **内网可用**：走系统证书库，兼容内网 https + 内网 CA。

### 1.3 非目标
- 不追求"零停机热更"——更新仍需退出应用、由助手替换文件后重启（Windows 运行中文件不可覆盖，这是硬约束）。
- 不改首次安装体验。
- 暂不做 P2P / 断点续传的复杂优化（可后续增强）。

### 1.4 关键事实（决定方案可行性）
- **后端是 PyInstaller onedir**（`resources/backend/` 下几百个文件）。版本间绝大多数文件（Python 运行时、DLL、依赖）**不变** → 按文件粒度增量，命中率极高，每次更新通常只下载少量变化文件。
- 应用数据在 `AppData`（`%APPDATA%` / `NLC_DATA_DIR` 等），**在安装目录之外**，更新不动它。
- 安装目录结构（NSIS 装出来的）大致：
  ```
  <installDir>/
    IPMaster-Cowork.exe        # electron 主程序
    *.dll, resources/app.asar, locales/ ...   # electron 运行时
    resources/backend/         # onedir 后端（ipmaster-cowork.exe + 一堆 DLL/py/data）
    resources/default_data/    # 随包默认数据
  ```

## 2. 总体架构

```
                         ┌───────────────────────────┐
   首次安装              │  NSIS 向导安装器（不变）    │  → 选目录、写注册表、建快捷方式
                         └───────────────────────────┘

                         ┌───────────────────────────────────────────────┐
   更新（自研）          │  Electron 主进程内的 Updater 模块               │
                         │   check → diff → download → verify → stage     │
                         │        → 退出+停后端 → 助手替换 → 重启          │
                         └───────────────────────────────────────────────┘
                                    │ net.fetch（系统证书库）
                                    ▼
                         ┌───────────────────────────────────────────────┐
   更新服务器            │  /update/<channel>/                            │
                         │    manifest.json     （版本 + 文件清单 + 签名）│
                         │    blobs/<sha256>    （按内容寻址的文件块）    │
                         └───────────────────────────────────────────────┘
```

- **首装**与**更新**彻底解耦：首装走 NSIS，更新走自研模块，互不影响。
- 更新模块只在 electron 主进程运行；渲染层只负责显示状态/进度、点"立即更新"。

## 3. 服务端布局与发布产物

### 3.1 目录布局（按渠道）
```
/update/latest/
  manifest.json
  blobs/
    3f2a...e91   # 每个唯一文件内容一份，文件名 = 该内容的 sha256（十六进制）
    a17c...44b
    ...
/update/beta/
  manifest.json
  blobs/ ...
```

**按内容寻址（content-addressed）的好处**：
- 跨版本天然去重——两个版本里没变的文件 sha256 相同、共用同一个 blob，服务器只存一份，客户端只下没有的。
- 客户端逻辑极简：本地缺哪个 sha256 就下哪个。
- 任意版本跨级更新都成立（不依赖 vX→vY 的差分链）。

### 3.2 manifest 格式
```jsonc
{
  "schema": 1,
  "channel": "latest",
  "version": "0.5.0",
  "releasedAt": "2026-07-20T08:00:00Z",
  "minCompatVersion": "0.3.0",     // 低于此版本不能增量，须走全量/重装（见 §11）
  "files": [
    { "path": "IPMaster-Cowork.exe",                 "sha256": "3f2a...e91", "size": 145203200 },
    { "path": "resources/backend/ipmaster-cowork.exe","sha256": "a17c...44b", "size": 5320192 },
    { "path": "resources/backend/python311.dll",      "sha256": "9d0b...c22", "size": 5619712 }
    // ... 覆盖安装目录内【所有】应随更新管理的文件
  ],
  "signature": "base64(ed25519_sig(sha256(canonical(files+version+...))))"
}
```

- `files` 覆盖 **win-unpacked 应用目录里的所有文件**（相对安装目录、正斜杠）。manifest **只描述应用自身文件**，不含 NSIS 装出来的东西（卸载器等）和运行时生成物（`__pycache__`/日志）。**删除退役文件靠"上一版 manifest − 新 manifest"，绝不按"清单里没有就删"（会误删卸载器），见 §4.3。**
- `path` 一律用正斜杠、相对安装目录。
- `signature`：用**发布私钥**对 manifest 关键内容签名；客户端内置**公钥**校验（见 §8）。

### 3.3 构建/发布流水线要做的
1. electron-builder 照常打出未打包的应用目录（`--dir`，即 `win-unpacked/` 那种），或直接对安装目录内容取文件清单。
2. 一个发布脚本：
   - 遍历应用目录所有文件 → 算 sha256 → 生成 `files` 列表。
   - 把每个文件按 `blobs/<sha256>` 传到服务器（已存在的可跳过，实现增量存储）。
   - 生成并**签名** manifest.json，上传。
3. **仍然照常产出 NSIS Setup.exe**（供首次安装/全量兜底下载用）。

> 服务器只需能静态托管 `manifest.json` 和 `blobs/*`（普通静态文件服务即可）。**这是本方案对外部的主要依赖，需与运维确认。**

## 4. 客户端更新流程

```
1. 检查      GET manifest.json（net.fetch）→ 校验签名 → 比版本号
2. 计算差异  对【新 manifest 列出的每个文件】，比本地同路径文件的 sha256：
               - 要下载 = 新 manifest 里有、但本地该路径文件不存在 / hash 不一致
               - 要删除 = 【上一版 manifest 有、新 manifest 没有】的文件（= 本更新器自己装过、现被移除的）
                          ★ 绝不是"本地有、新 manifest 没有就删"——见 §4.3
3. 下载      只下"要下载"集合里各文件对应的 blob → 暂存区（进度=已下/总下字节）
4. 校验      每个下完的 blob 再算一次 sha256，与文件名/清单一致才算通过
5. 落盘暂存  在暂存区按目标相对路径摆好"本次要写入的新文件"
6. 应用      退出应用 + 停后端 → 助手进程按计划替换/删除 → 重启（见 §6）
```

### 4.1 本地哈希缓存（优化）
- 每次成功更新/首装后，把"当前版本的文件→sha256"写一份 `installed-manifest.json` 到 AppData。
- 下次检查时，只对 **mtime/size 变了的文件**重算 sha256，其余用缓存 → 避免每次全盘哈希。
- 缓存缺失（如首装后第一次）或对不上时，退化为全量哈希一次（可接受，几百 MB 顺序读，秒级）。

### 4.2 下载策略
- 并发下载少量 blob（如 4 并发），带重试（指数退避）。
- 失败的 blob 重下即可（内容寻址，无副作用）。
- 断点/续传：第一版可不做（失败重下整个 blob）；后续可加 Range。

### 4.3 删除规则的坑（重要 —— 别用"本地有、清单没有就删"）

安装目录里有一批**不是应用自身、也不该被更新器碰**的文件，manifest（由 win-unpacked 生成）里天然没有它们：
- **NSIS 装出来的**：卸载器 `Uninstall *.exe`、NSIS 的注册/记录文件；
- **运行时生成的**：日志、后端可能产生的 `__pycache__`、临时文件等；
- 用户手动放进目录的东西（少见但可能）。

若按"本地有、新 manifest 没有 → 删"来处理，会**误删卸载器等文件、破坏安装**。正确规则：

> **要删除的 = （上一版 manifest 的文件集合）−（新 manifest 的文件集合）**，即"**本更新器上一版自己装过、这一版被移除**"的文件。
> **更新器只增删自己管过的文件；清单里从没出现过的文件（卸载器、pycache、日志、外来文件）一律不碰。**

- 这要求手里有**上一版 manifest**：用 §4.1 缓存的 `installed-manifest.json` 当"上一版"。
- **首次没有上一版**（刚从 NSIS 装完、或缓存缺失）→ **本次不做任何删除**，只做"下载+替换"；把新 manifest 存为 `installed-manifest.json` 当基线，删除能力从**下一次**更新起生效。漏删一两个退役文件无害，误删卸载器才致命。
- 好处顺带解决"运行时生成物"问题：这些文件更新器从不认识 → 从不删 → 也不影响下载 diff（下载只看"新清单里我缺的"，外来文件不产生下载）。

## 5. 传输与网络（内网 CA）

- **一律用 Electron `net.fetch`（Chromium 网络栈 = 系统证书库）**，不用 Node 的 `fetch`/`https`。
- 原因与之前 auth、云端上报同：Node 自带 CA 不认内网 CA（HWBPIT Enterprise CA），内网 https 会 `fetch failed`；`net.fetch` 与浏览器同源信任，浏览器能开的它就能连。
- **这正是当前 `electron-updater` 的一个隐患**：它用 Node https，内网 CA 环境下自动更新可能证书报错。自研模块用 net.fetch 从根上避开。

## 6. 应用替换机制（核心难点）

### 6.1 约束
- Windows 上**运行中的 exe/DLL 无法被覆盖/删除**（文件锁）。electron 主程序、其 DLL、以及**运行中的后端 exe** 都被锁。
- 所以替换必须：**先退出应用 + 停后端（释放锁）→ 由一个独立进程完成替换 → 再重启**。这与安装器做的事一致。

### 6.2 助手进程（applier）
点击"立即更新"后：
1. 主进程 `stopBackend()`（按 PID 杀掉后端，释放其 exe 锁；复用现有逻辑）。
2. 生成一份**替换计划** `apply-plan.json`（要覆盖的文件列表：`暂存路径 → 安装目录相对路径`；要删除的文件列表；主进程 PID；安装目录；重启命令）。
3. 把 applier 放到**安装目录之外**（如 `%LOCALAPPDATA%\<app>\updater\`，避免它自己被替换）。applier 方案二选一（见 §6.4）。
4. 以 detached 方式拉起 applier，主进程随即退出。
5. applier：
   - 轮询等待主进程 PID 退出（`tasklist`/句柄）。
   - **逐文件替换（带备份）**：对每个要写入的文件 `f`：
     - 若安装目录已有 `f` → 先移动到 `backup/f`（备份）。
     - 把暂存的新 `f` 移到安装目录（同卷 move，近似原子）。
   - **删除**清单标记要删除的文件（同样先备份）。
   - 全部成功 → 删除 `backup/` 与暂存区 → 启动应用 → applier 自删。
   - **任一步失败 → 回滚**：把 `backup/` 里的文件全部还原 → 启动**旧版本** → 记录失败原因（写日志/落一个 flag，供应用下次读取上报）。

> 采用"逐文件 + 备份"而非"整目录拷贝再交换"：后端 onedir 有几百 MB，整目录复制一遍太重；只动变化文件、只备份被替换的那批，I/O 最小且能回滚。

### 6.3 原子性与半更新防护
- 逐文件替换不是全局原子。用两道防护：
  1. **备份 + 失败即回滚**（上面）。
  2. **版本标记最后写**：所有文件替换成功后，才更新 `installed-manifest.json` 的版本号。若中途崩溃，下次启动发现"文件状态与已记录版本不一致" → 触发**自愈**（重新拉起 applier 用残留 backup 回滚，或重新走一次更新）。
- applier 自身要幂等、可重入（崩了重跑不出乱）。

### 6.4 applier 的两种实现（取舍）
| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 生成脚本 + 系统工具** | 生成 `.cmd`/`.ps1`，用 `robocopy`/`move` 干活，`cmd.exe` 跑 | 不用额外打包/签名二进制 | 脚本脆（路径含空格/中文、错误处理弱）；杀软可能拦 `.bat`/`.ps1`；PowerShell 执行策略可能拦 |
| **B. 随包一个小 applier.exe** | 打包一个**已签名**的小可执行（可用 Node SEA / Go / Rust 写），更新时先拷到安装目录外再运行 | 健壮、可做进度/日志/回滚、可签名过杀软 | 需额外构建+签名一个二进制 |

**建议**：第一版可先用 A 快速跑通，但**目标是 B**（自研更新最容易在"替换"这步翻车，一个签名的小 applier 值得投入）。

### 6.5 后端 exe 的特殊处理
- 更新前 `stopBackend()` 释放后端 exe 锁。
- 若后端 onedir 里**某些文件没变**（大概率），它们不在下载/替换集合里，applier 不动 → 天然增量。
- 若后端整体大改（如 Python 版本升级），变化文件多 → 下载量大，但仍只下"变了的"。

## 7. 增量策略小结

- **粒度**：文件级（按 sha256）。得益于 onedir，命中率高。
- **下载量** ≈ 本次真正变化的文件总大小（+ manifest 极小）。相比现在全量 Setup.exe，通常小一到两个数量级。
- **安装量** ≈ 只替换变化文件（不是整包重装）——这是当前 NSIS 做不到的"增量安装"。

## 8. 完整性与安全（威胁模型）

| 威胁 | 防护 |
|---|---|
| 传输被篡改 / 中间人 | ① https + net.fetch（系统证书库）② 每个 blob 下载后按 sha256 校验 ③ manifest **签名**校验（内置公钥） |
| 服务器被投毒发假 manifest | manifest 签名——没有私钥签不出合法 manifest，客户端拒绝 |
| 单个文件内容不符 | blob 内容寻址 + 下载后重算 sha256，不符即弃 |
| 本地暂存被本机攻击者改 | 属"本机已被攻破"威胁，超出更新模块职责；但可在**应用前**对暂存文件再校验一次 sha256（廉价，建议做） |
| 降级攻击（诱导装旧版） | 校验 `version > 当前`，拒绝装更旧版本 |

- **签名算法**：建议 ed25519（小、快、库成熟）。私钥离线保管，只在发布时用。公钥硬编码进应用（随版本可轮换，见遗留问题）。
- **代码签名**：若应用本身有代码签名证书，替换进去的 exe/dll 也应是**已签名**的产物，否则可能触发 SmartScreen/杀软。签名在**构建时**完成（blob 就是签好名的文件），更新模块不额外签。

## 9. UX 与前端

状态机（复用并扩展现有更新 UI）：
```
idle → checking → (up-to-date | available{version} )
available → downloading{percent, downloaded/total} → verifying → ready
ready →（用户点“立即更新”）→ applying → 重启
任意阶段 → error{message}（可重试）
```
- **下载进度**：`downloading` 全程显示百分比（分母=本次要下的总字节）——这是解决"干等"的关键。
- **应用阶段**：退出应用后由 applier 接管，应用内已无 UI；applier 用方案 B 时可弹一个极简原生进度窗（可选），A 则无（但替换很快）。
- 文案走 i18n（`update.*` 已有一批，按状态补齐）。
- 保留"稍后提醒 / 立即更新"选择，不强制打断。

## 10. 与现有 electron-updater 的取舍

- **更新路径完全替换** electron-updater，移除 `initUpdater`/`quitAndInstall` 那套。
- **NSIS 首装保持不变**（`oneClick:false` + 可选目录）。
- `latest.yml`/`.blockmap` 不再被客户端使用（可留给"全量兜底下载"，见 §11）。
- 好处：摆脱 Node-https 的内网 CA 隐患、拿到完全可控的增量+进度。

## 11. 版本、渠道、兜底（一次性上线的安全网）

- **渠道**：`latest`/`beta`，来自 app-config（沿用现逻辑），对应不同 manifest 路径。
- **首次接入**：老版本（用 electron-updater 的）升级到"第一个带自研更新的版本"时，仍由 electron-updater/NSIS 完成这一跳；此后进入自研更新轨道。

### 11.1 全量重装兜底 —— 不灰度也能安全铺给所有人的关键

因为**不做灰度、一次性铺给全量用户**，必须保证"更新永不把用户装坏"。做法：**增量为主，完整 Setup.exe 重装为硬兜底**。

- 更新链路的**任一步失败都回退到全量兜底**：下载 blob 失败、sha256 校验失败、磁盘不足、applier 替换失败且回滚成功、`当前版本 < minCompatVersion`（目录结构大改，增量不安全）……统统触发：
  ```
  下载完整 Setup.exe（manifest 里带其 url + sha256）→ 校验 → 运行它 → 由它完成安装
  ```
  这条兜底路径 ≈ **今天的更新行为**（NSIS 全量），成熟可靠。
- 兜底运行 Setup.exe 时用 `/S` 静默 + 指向现有安装目录（不弹选目录），或必要时退回向导——总之**能装上**优先。
- 结果：最坏情况只是"部分用户走了慢的全量重装"，**没有人会卡在装坏/打不开**。这就是"不灰度、一次性上线"的底气。
- manifest 里附带兜底所需字段：
  ```jsonc
  "fullPackage": { "url": ".../IPMaster-Cowork-Setup-0.5.0.exe", "sha256": "…", "size": 180000000 }
  ```

## 12. 失败与边界

| 场景 | 处理 |
|---|---|
| 下载中断/网络差 | 重试；仍失败 → 报错、保留已下 blob 下次续用（内容寻址可复用） |
| 磁盘空间不足 | 应用前预估所需空间（要下 blob 总量 + 备份量），不足则报错不动手 |
| 替换时文件仍被锁（杀软扫描/残留进程） | applier 重试若干次；仍失败 → 回滚、装旧版、上报 |
| applier 崩溃/断电 | §6.3 版本标记 + backup 自愈 |
| 杀软拦截 applier | 方案 B 签名可缓解；A 风险较高 |
| 安装在 Program Files（需管理员） | 替换需提权 → applier 触发 UAC；**建议首装默认装每用户目录 `%LOCALAPPDATA%`**，更新无需提权、无 UAC（见遗留问题） |
| 多实例同时更新 | electron 单实例锁；更新过程加互斥 |
| **更新时正有 agent 会话在跑 / 后端在忙**（本应用特有） | 更新必须退应用+停后端 → 会**打断进行中的会话/工具执行**。策略：应用点"立即更新"前，**检测是否有运行中的会话**——有则提示"更新会中断当前任务，是否继续"或等其结束；确保退出前后端**优雅关闭**（会话是事件溯源持久化的，可恢复，但要避免写到一半被硬杀）。 |
| **NSIS 卸载器与文件清单失步** | NSIS 卸载器记的是"安装时"的文件清单；自研更新**新增/删除**的文件它不知道 → 卸载可能残留孤儿文件。缓解：electron-builder 的 NSIS 卸载器通常**整目录删**安装夹，问题不大；但需**实测卸载**确认干净（尤其更新新增了文件后）。 |
| **首次更新（刚从 NSIS 装完）无本地哈希缓存** | 无 `installed-manifest.json` → 首次 diff 要**全盘算一次 sha256**（几百 MB 顺序读，秒级，可接受）。优化：让 NSIS 包里**随包带上该版本的 installed-manifest.json**，首更即增量、免全盘哈希。 |
| **切换到自研更新的那次更新（仍由 electron-updater 完成）** | 存量用户从"当前用 electron-updater 的线上版本"升到"第一个内置自研更新模块的版本"的这一次更新，机器上还没有自研代码，**只能由旧的 electron-updater/NSIS 全量完成**。装上之后才有自研模块、之后才走增量。这是**全量用户切到自研更新的唯一入口**，不灰度尤其要先确认它在内网 https + CA 环境下**真能装上**，否则用户切不过来。 |
| **代理环境** | `net.fetch` 走 Chromium，**自动遵循系统代理**（Node https 不一定）——内网代理下更省心，算一个额外好处。 |
| **更新装成功、但新版本一启动就崩**（坏构建） | §11.1 兜底只管"更新过程失败"，管不了"更新成功但应用是坏的"。不灰度时这会让全量用户一起崩。建议做**崩溃自愈**：替换成功后**保留备份**若干次启动；启动加"哨兵"——若新版在 X 秒内连崩 N 次，applier 自动**回滚到备份的旧版**并提示。属健壮化项，但一次性上线**强烈建议带上**。 |

## 13. 实施计划（一次性交付，不灰度）

> 不做灰度 = 一版就要健壮、且给全量用户。因此**一开始就上健壮实现**（签名小助手 + 备份回滚 + 全量兜底），不走"先脆弱脚本试水"的路子。工作项按依赖排序，但**同一个版本一起发**。

**必做（阻塞发布，缺一不可）**
1. 服务端 + 发布流水线：manifest（含 `fullPackage` 兜底字段）+ blobs + **签名**；服务器静态托管；仍产出 Setup.exe。
2. 客户端更新链路：检查 → 签名校验 → 逐文件 diff → net.fetch 下载变化 blob（进度）→ sha256 校验 → 暂存。
3. **applier 方案 B（签名小助手 exe）**：等主进程退出 → 逐文件"备份+替换"→ 删除清单标记文件 → 重启；**失败即回滚**。
4. **半更新自愈**：版本标记最后写；启动时检测不一致 → 回滚或重跑。
5. **全量重装兜底（§11.1）**：任一步失败 → 下载并运行完整 Setup.exe。这是"不灰度也安全"的命门，**必须随首版一起上**。
6. 磁盘/空间预检、本地哈希缓存、错误上报、单实例互斥、i18n 状态文案。

**上线前测试矩阵（代替灰度的把关手段）**
- 全新装 → 更新；同版本重复更新（无变化）；跨多版本更新。
- 应用运行中/后端运行中触发更新（文件锁）。
- 中途断网、磁盘满、校验失败、applier 被杀软拦 → 应回滚或走全量兜底，**绝不装坏**。
- 每用户目录 与 Program Files 两种安装位置。
- 内网 https + 内网 CA 环境实测下载。
- 断电/杀进程模拟半更新 → 下次启动自愈。

**后续增强（可不阻塞首版，但不属于"灰度"）**
- 断点续传、并发调优、公钥轮换。

## 14. 待确认的遗留问题（需要你/运维拍板）

1. **服务器**：内网更新服务器能否托管 `manifest.json` + `blobs/*`（普通静态文件）？发布流水线能否加"切块+签名+上传"这一步？——这是最大外部依赖。
2. **代码签名**：应用及其 exe/dll 现在有没有代码签名证书？（决定替换后会不会被 SmartScreen/杀软拦、以及 applier 方案 B 能否签名。）
3. **安装位置**：首装默认装**每用户目录**（`%LOCALAPPDATA%`，更新免提权、免 UAC）还是 **Program Files**（需管理员，更新要提权）？强烈建议前者。
4. **签名密钥**：ed25519 私钥谁保管、怎么用于发布；公钥轮换策略（是否需要支持多公钥过渡）。
5. **兜底**：不兼容/增量失败时，是"自动下 Setup.exe 重装"还是"提示用户手动下载"？
6. **applier 落地**：第一版接受方案 A（脚本）先跑通，还是直接上方案 B（签名小助手）？

## 15. 风险提示（诚实说）

- 自研更新最容易翻车的是**"替换运行中文件"这一步**：涉及进程时序、文件锁、杀软、权限、回滚。这块必须做扎实（方案 B + 备份回滚 + 自愈），否则一次失败可能让用户装成"半个应用"打不开。
- 相比 electron-updater（成熟、被广泛验证），自研意味着**这些边界都要自己趟**，维护成本更高。收益是：真增量、进度可控、首装/更新解耦、避开内网 CA 隐患。
- **不灰度、一次性上线的安全底线 = §11.1 全量重装兜底**：只要兜底做对，增量出任何问题都退回"今天的全量重装"，没有人被装坏。所以**兜底是首版必须项，不能省**。上线前用 §13 的测试矩阵替代灰度做把关。

## 16. 可测性设计（不灰度 → 靠它把关，等同验收标准）

### 16.1 分层可测
| 层 | 覆盖 | 手段 |
|---|---|---|
| **纯逻辑** | diff（本地清单 vs 服务器清单 → 下载集/删除集）、manifest 解析、**签名校验**、sha256 校验、版本比较、**兜底决策**（何时退全量） | 单元测（纯函数，快、无需打包） |
| **下载/暂存** | 检查→下载→校验→暂存 全流程 | 本地静态服务托 `manifest+blobs`，updater 指过去；不需真内网服务器 |
| **applier（替换/回滚）** | 备份、替换、删除、**失败回滚**、半更新自愈 | 对**临时的"假安装目录"**跑（不绑真实安装路径）；注入"文件锁/缺文件/写失败"断言回滚 |
| **端到端** | 真装 vN → 更新 vN+1；坏一个 blob → 退全量 Setup.exe | Windows 真机/VM，手动，慢——用 §13 矩阵 |

### 16.2 为可测性必须做的设计
1. **纯逻辑与 I/O 解耦**：diff/校验/决策是纯函数；`net.fetch`/`fs`/`spawn` 藏在薄适配层后可 mock。→ 单元+本地 mock 覆盖绝大部分。
2. **applier 独立成组件**：签名 `(计划, 安装目录, 暂存目录, 备份目录) → 结果`，对任意目录工作 → 可在临时目录里反复测替换与回滚。
3. **故障注入开关**（关键）：留 env/flag 强制"在第 X 步失败"——下载失败 / 校验失败 / applier 替换到一半失败 / 主进程未退出 …… QA 据此**主动触发每条失败路径**，断言"要么回滚成旧版、要么退全量重装，绝不装坏"。**不灰度就靠这个替代灰度试错。**

### 16.3 相比 electron-updater
electron-updater 是黑盒、基本只能端到端测；自研代码在手，**单元/集成层反而更可测**，只有"替换运行中文件+重启"这层两者一样要真机。

## 17. 开工前置条件 checklist（一次性上线，缺项别开工）

### A. 阻塞级：不落实就没法做 / 会白做
- [ ] **当前 electron-updater 更新在内网 https + CA 环境下今天到底能不能用？** ← **最先验证**。若现在自动更新本身就因内网 CA 证书报错而不工作，则"切换到自研更新的那次更新"根本发不出去，整个迁移无从谈起（需先修好 feedUrl 的 CA 信任，或改用 net.fetch 做那一跳）。
- [ ] **服务器能托管** `manifest.json` + 一个含**上千个小文件**的 `blobs/` 目录 + 兜底 `Setup.exe`（纯静态、供 GET）；并确认多小文件下的**列举/下载性能**没问题。
- [ ] **发布流水线能加"切块+签名+增量上传"这步**，且能**只上传服务器上还没有的 blob**（需要能查已存在的 blob 列表）。
- [ ] **代码签名证书**有没有？替换进去的 exe/dll 是否已签名（否则杀软/SmartScreen 可能拦）；applier（签名小助手）能否用同证书签。
- [ ] **首装安装位置**拍板：每用户 `%LOCALAPPDATA%`（更新免提权、强烈建议）还是 Program Files（更新要 UAC 提权）。
- [ ] **签名密钥**：ed25519 私钥谁生成/保管/怎么在发布时用；公钥硬编码进应用；**轮换方案**（是否需支持多公钥过渡）。

### B. 真机/环境验证（代替灰度的把关，写代码期间逐项过）
- [ ] **切换到自研更新的那次更新**（旧 electron-updater 全量）在内网真机真能装上。
- [ ] **net.fetch 从内网 https 服务器能正常 GET**（manifest + blob），系统证书库信任内网 CA。
- [ ] **替换运行中文件**：真装一版 → 停后端 → applier 覆盖 electron/后端文件 → 重启，全程 OK；模拟文件锁/杀软拦 → 回滚或退全量兜底，**绝不装坏**。
- [ ] **杀软/企业环境**：applier 与下载的 blob 不被拦/隔离。
- [ ] 两种安装位置各测一遍（提权/免提权路径）。
- [ ] **断电/杀进程**模拟半更新 → 下次启动自愈；**坏构建**模拟启动即崩 → 崩溃哨兵回滚。
- [ ] **卸载**：自研更新增/删过文件后，NSIS 卸载器仍能干净卸载（无残留、不报错）。

### C. 构建侧一致性（决定增量是否真省、diff 是否准）
- [ ] electron-builder 是否**产出并保留 win-unpacked**（blob 生成的输入）。
- [ ] **安装到磁盘的文件 == win-unpacked 的文件（逐字节一致）== blob** —— 否则客户端算的 hash 对不上、误判"变了"。NSIS 只是解压、不改字节；签名在构建时完成，签好的 exe 就是要发的那份，需确认这条链一致。
- [ ] **构建可复现性**：同一版本重复构建，"没改的文件"字节是否稳定？若 exe 头/资源里嵌了**构建时间戳**，每次构建 hash 都变 → 即使没改也会被下载（增量打折，不致命但要知道）。能固定则固定。
- [ ] 摸清 **NSIS 往安装目录额外放了什么**（卸载器名、其它记录文件），确保删除规则（§4.3）把它们排除、且 `installed-manifest` 基线不含它们。

### D. 应用行为
- [ ] 确认**运行时没有往安装目录写关键文件**（日志/数据都在 AppData；后端 onedir 里若会生成 `__pycache__` 等，靠 §4.3"不碰未知文件"兜住）。
- [ ] 更新前**优雅停后端**（复用 stopBackend）+ **检测有无运行中的 agent 会话**，有则提示"更新会中断当前任务"。
- [ ] 单实例锁 + 更新过程互斥。

### E. 安全
- [ ] **canonical JSON**（确定性序列化：key 排序、无空白差异）规范定死，客户端/发布脚本用同一套，验签才可复现。
- [ ] 威胁模型（§8）走查签字：传输、假 manifest、单文件篡改、降级、本机篡改。
