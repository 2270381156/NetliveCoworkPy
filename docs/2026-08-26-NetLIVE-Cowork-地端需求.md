# NetLIVE Cowork 地端 —— 需求文档

> 状态：初稿，待评审 · 日期 2026-08-26 · 分支 `netlive-cowork`
> 范围：**仅地端**。云地协同（云端会话、一人一实例）不在本文范围内。
> 参考实现：`demo/experimental` 分支已有一套可工作的实现，本文写的是**要什么**，不是**怎么搬**。

---

## 1. 背景

今天这个产品把「有哪几个 cowork」写死在交付物里：名字颜色在 `electron/branding.json`，提示词在
`resources/agents/<id>/`，MCP 连接在全局 `mcp.json`，skill 市场地址在两个环境变量，LLM 账号在一份
全局清单。后果有两条：

**① 阵容是构建期常量。** 换一批 cowork 要重新出包，而不同用户该看到不同的几个。

**② 能力装配层没有「这个能力属于谁」这个维度。** 所有 provider 都是启动时注册一次的全局单例，
七个 cowork 共用同一套 skill 与 MCP。多 cowork 一上线即串台，**而串台不报错**——只是模型手里多了
不该有的工具。

同时，本期还伴随一次**应用身份更换**（IPMaster-Cowork → NetLIVE Cowork）：两版在同一台机器上
完全并存、数据目录互不可见。代价是存量用户的会话与配置不再自动继承，因此**存量导入是本期
必须交付的一部分**，否则老用户装上新版等于从零开始。

本需求要建立的是一条完整的链：**登录取得身份 → 云端按权限决定阵容 → 地端验签下载并加载 →
运行时按 cowork 隔离能力**，外加**一条把老用户带过来的路**。

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 达成的标志 |
|---|---|---|
| G1 | 一个 cowork 的全部可定制内容集中成一件可下发的东西 | 新增/修改一个 cowork 只改一处，不再动四个地方 |
| G2 | 用户看到的阵容由**云端权限**决定，不由安装包决定 | 同一个安装包，两个人打开看到不同的 cowork |
| G3 | 权限是**执行边界**，不只是展示 | 绕过界面直接调接口，也拿不到没权限的 cowork |
| G4 | 能力按 cowork 隔离 | 在 A 的会话里，模型看不到也调不动 B 的 skill 与 MCP |
| G5 | 权限收回后历史记录仍可查 | 被收回 cowork 的会话能打开、能读，但不能继续 |
| G6 | 装进来的套件确实是我们发布的那一份 | 被替换或损坏的包装不上，且会明确告警 |
| G7 | 存量用户能带着自己的会话与配置迁过来 | 导入后历史会话、LLM 账号、自建 skill 都还在 |

### 2.2 非目标（本期明确不做）

- **云地协同**：云端会话、一人一实例、云端实例自己拉套件、云地两端的套件版本一致性比对。
  > 注意：**与云端管理服务的通信与鉴权在本期范围内**（§B）——没有它整条链跑不起来。
  > 不做的只是"会话跑在云上"这件事。
- **套件的可视化管理台**。谁能用哪个由云端管理服务决定，本产品只消费结果。
- **套件的差量更新**。整包替换即可，个位数量级、体积不大。

## 3. 名词

| 词 | 含义 |
|---|---|
| **cowork** | 一个面向特定领域的智能体形态。用户在界面上切换的就是它 |
| **套件（suite）** | 一个 cowork 的全部可定制内容打成的一个 zip：清单 + 提示词 |
| **清单（manifest）** | 套件里的 `cowork.json`，声明这个 cowork 是什么、拥有哪些能力 |
| **母版（default）** | 模板继承的来源。**不是 cowork**：不下发、不进阵容、不能用来建会话 |
| **云端管理服务** | 持有授权与制品的服务端（现有 substrate）。本产品只消费它，不改它 |
| **授权（entitlement）** | 云端持有的「这个人能用哪几个 cowork」 |
| **对账（recheck）** | 拿云端的授权清单与本机已装的比对，补齐差的、删掉多的 |
| **归属（ownership）** | 一个 skill 属于哪些 cowork。`*` 表示所有 |
| **存量应用** | 换身份之前的 IPMaster-Cowork 安装，与新版并存 |

应用跑起来其实是**三个各自独立的进程**，本文多处按它们分工，先说清：

| 叫法 | 是什么 | 在这个仓里 | 能做什么 |
|---|---|---|---|
| **主进程** | 应用的外壳。开窗口、启后端、读写文件、访问系统密钥库 | `electron/main.js` + `electron/lib/` | 有完整系统权限。**登录令牌只存在这里**（系统密钥库的接口只有它能调） |
| **界面** | 那个窗口本身，跑前端页面 | `frontend-desktop/src/` | 在沙箱里，**碰不到文件系统与密钥库** |
| **后端** | Python 服务，由主进程拉起 | 打包后是一个 exe | 干活的那个；没有用户令牌 |

> 需求 B2「令牌只在主进程」与 C3「取套件由主进程做、装由后端做」都是这张表的直接结果，
> 不是分工偏好。

## 4. 角色与外部依赖

```
                     ┌─ (1) 登录 → 用户令牌
用户 ── 客户端主进程 ─┼─ (2) 我能用哪几个、各是哪一版 ──→ 云端管理服务
        （持令牌）    └─ (3) 给我这个套件的 zip + 签名 ──→ （授权 + 制品）
             │
             ├─ (4) 验签、摆进暂存目录
             ↓
           后端 ── (5) 装/删 → 数据目录 ── (6) 阵容 → 前端
```

**外部契约（已由运维给定，本产品只消费）：**

```
GET  <base>/api/me/agents               → [{"agentId": "ipmaster", "version": 3}]
GET  <base>/api/me/agents/<id>/package  → zip 原文 + 响应头 X-Package-Sha256
```

两个端点都用**用户令牌**（与登录态同一个）。

三条要点，写进需求是因为每一条错了都不报错：

- `version` 是云端**递增的整数**，不是语义化版本号。管理员回滚时它会**变小**。
- 不存在的 agentId 返回 **400**，不是 404。
- 云端**没有办法主动通知地端**权限变了，只能由地端定期去问。

**签名如何搭进这条链见 §D**——现有契约里只有内容哈希，签名的承载方式需要与运维确认（OQ-5）。

## 5. 功能需求

> 措辞约定：**必须** = 不满足即不可上线；**应当** = 有强理由才可不做；**可以** = 可选。

### A. 套件：交付物的形状

**A1 · 一个 cowork 的全部可定制内容必须能打成一个 zip，解开是一个以 cowork id 命名的目录。**
目录内含清单 `cowork.json` 与提示词文件。
> 提示词不进 json：正文数千字，做成 json 字符串后换行全变 `\n`，改一个字 git 上显示"整段都变了"，
> 也没法在编辑器里正常写。

**A2 · 清单必须声明：** 结构版本、id、版本、展示次序、品牌（名称/副标题/色标）、拥有的 MCP、
skill 市场地址、允许的 LLM 账号。字段全表见附录 A。

**A3 · 展示次序必须是套件自己的属性**，不能依赖一份全量清单的数组次序。
> 下发之后每个用户拿到的是**子集**，他没权限的那些根本不在他机器上，全量清单无从谈起。
> 退化成按 id 字典序的话，界面排列与产品意图无关，而且没人会察觉这是个错误。

**A4 · MCP 声明必须分成「用哪几个」与「怎么连」两半。**
> 多数 cowork 只需要引用平台已有的服务器；只有下发一个平台没有的新 MCP 时才需要给连接定义。
> 合成一个的话，每个套件都要把公共服务器的连接信息抄一遍，改一次要改七处。

**A5 · 套件必须自带全部四个提示词 facet**（act / observe / compact / recognize_intent），
不依赖母版补齐。
> 运行期本来就有"缺了从母版取"的能力。利用它的代价是：套件看着装成功、跑起来也正常，
> 实际用的却是母版那份，而你以为是它自带的。⇒ 见 A6，必须在装之前挡住。

**A6 · 必须有构建期校验，且校验不通过不许出包。** 至少挡住：
四个 facet 缺任何一个 · id 与目录名不一致 · 两个套件 id 相同 · 展示次序缺失或重复
（含把布尔值当数字用）· 引用了没有定义的 MCP · 清单里出现形如密钥的字段（见 NFR-4）。

**A7 · 构建期校验与运行期读取必须是两套代码，不共用。**
> 构建期面向"改套件的人"，做完整校验、报错要具体。运行期面向"已经装上的东西"，**容忍缺字段
> 而不是拒绝启动**——装都装上了才发现清单少个字段，此时拒绝启动的代价远大于按缺省值继续。

**A8 · 母版必须保留，但不得以 cowork 的身份出现**：不下发、不进阵容、不能被选来建会话。
> 它仍要参与 facet 兜底与"建会话未指定模板"的回落，所以必须和套件装在同一个目录下被扫到。

### B. 与云端管理服务的通信与鉴权

**B1 · 必须复用登录态的用户令牌，不得为套件下发另立一套凭据。**
> 另立一套就有两处要维护过期、两处要处理失效，而它们必然在某个分支上不同步。

**B2 · 令牌必须只保存在客户端主进程的安全存储中**，不得落到后端可读的明文位置，
**不得进日志、不得进遥测、不得进错误上报**。
> 这也是"取套件由主进程做"（C3）的根本原因，不只是分工方便。

**B3 · 云端管理服务的地址必须可配置，且随品牌走。**
> 不同环境、不同交付形态的地址不同，写死会让每换一个环境就出一次包。
> ⚠ 配置项没写时必须保持出厂模板原值，**不得覆盖成空**——这个坑刚踩过一次：
> 品牌文件里缺一个键，把出厂模板里的正确地址抹成了空字符串，新装机器整块功能失效。

**B4 · 未登录时必须不对账、不装、不删**，界面说的是"请先登录"。
> 说成"尚未开通任何 Cowork"会把人送去找管理员，而他只需要登录一下。

**B5 · 令牌失效或过期必须能被识别并明确提示**，不得表现为"你没有任何 cowork"。
> 这两件事在数据上长得一样（拿不到清单），但用户该做的事完全相反。

**B6 · 切换账号后必须立刻重新对账**，不能等到下一次定时对账。
> 阵容跟人走。不重新对账的话，换了账号还看着上一个人的 cowork，
> 而且**能用**——那是一次实打实的越权。

**B7 · 必须支持内网自签证书的部署环境**，证书校验策略可配。
> 默认值要与实际部署环境一致，否则出厂即连不上，而现象是"一直在获取中"。

**B8 · 必须有明确的超时、重试次数与退避策略**，全部重试都失败才算这次对账失败。
> 一次抖动不该触发 §C7 的"一动不动"分支——那会让权限更新平白晚一天。

**B9 · 云端返回的错误必须分类呈现，至少区分：**
未登录 / 无此授权 / 授权被停用 / 请求不合法。云端返回的说明原样展示。
> 四种的下一步完全不同——重新登录 / 去申请 / 等管理员 / 删本地残留。
> 合并成"无权限"会让用户去做完全错误的事。
> ⚠ 现有契约里**不存在的 id 返回 400 而不是 404**，按状态码分支的要注意。

**B10 · 「整个人被停用」与「少了某个 cowork」必须在界面上分开。**
> 一个该找管理员，一个可能只是权限调整。混为一谈会让用户找错人。

**B11 · 通信必须可审计**：日志要能回答去了哪个地址、拿到几个、失败原因。
> 但**令牌本身不得出现在日志里**（B2）。

### C. 授权对账与下发

**C1 · 安装包里必须一个套件都不预置。**
> 预置了的话，用户装完先看到全部七个，云端再来"收走"没权限的——中间那一下很难看。
> 第一次启动必然在线（人刚下载完安装包），没有预置的必要。

**C2 · 必须在启动时对账一次，之后每天对账一次。**
> 云端改了权限没法通知地端，这个间隔就是「收回多久之后真的生效」的上限。
> 更频繁与否见 OQ-1。

**C3 · 取套件必须由客户端主进程完成**（它持有用户令牌，见 B2），**装必须由后端完成**。
两者之间以一个暂存目录交接。
> 分这一刀是因为解包、验签、版本比对的逻辑在后端且要被复用；搬到主进程那边就得各写一份。

**C4 · 暂存目录里除 zip 外必须有一份「该有哪几个」的凭据文件。**
> 不能让后端直接看目录里有几个 zip：**版本没变的根本不会下载**，那个 zip 不在目录里——按目录判
> 会把它当成被收回而删掉，于是每次启动都得重下一遍全部套件才能不被误删。

**C5 · 没有那份凭据时必须一个都不删。**
> 覆盖两种情形：手工摆目录的开发态，以及这次对账没成功。

**C6 · 判断"要不要重装"必须用版本**相等比较**，不得写成"变大才装"。**
> 版本是云端递增整数，管理员回滚时会变小。写错的现象是"我明明回滚了他还在用新版"，不报错。

**C7 · 对账失败必须一动不动**：不装、不删，也**不回落到开发期的本地包目录**。
> "没拿到清单"与"拿到了一张空清单"必须区分。把网络故障当成权限被收回，后果是把用户的套件
> 连同他改过的提示词删掉，**且不可逆**；反过来（该删没删）只是晚一天生效。
> **两个方向的错不对称，所以往安全的一侧偏。**
> 回落到本地目录则会让"下发挂了"表现成"用着开发期那份"，更难发现。

**C8 · 单个套件下载完必须当场校验内容哈希**（从响应头取）。
> 这一层防的是传输损坏与截断。**防篡改是签名的事**（§D）——哈希与包走同一条通道，
> 能改包的人也能改哈希，单靠它证明不了来源。

**C9 · 某个套件下载失败不得被当成"被收回"**，它仍要计入"该有哪几个"。
> 一次 403 不该等于替对方做了收回决定。

**C10 · 算差集必须用 zip 自己报的 id，不是清单里的 agentId。**
> 两者一旦不一致（对面写成 `cowork-ipmaster`），拿清单字段算差集会**装完立刻删掉**，
> 日志还理直气壮写"权限收回"。

**C11 · 连不上云端时不得增加任何闸门。** 应用照常打开，历史会话照常查看。
> 真要对话时网络不通自然就失败了，不需要再造一道门去拦。

**C12 · 开发期必须能用一个本地目录当"假云端"**，且**走的是与真下发完全相同的安装代码**。
> 否则等真接云端才发现问题。想试"某人只有两个 cowork"，就让那个目录里只放两个 zip，重启即可。

**C13 · 未配置假云端时必须一个 cowork 都没有，不得有全量兜底。**
> 任何"没配就给你全量"的兜底都会让权限失去意义，本地也就验不出"某人只有两个"这种场景。

**C14 · 单个套件必须有大小上限。**

### D. 套件的完整性与来源校验

> 本组是本期新增的硬要求。没有它，**能往托管处放文件的人，就能让所有装了该套件的机器
> 去连任意地址、按任意提示词行动**——套件里带着 MCP 连接定义和全部提示词。

**D1 · 每个套件必须带发布方签名，安装前必须验签，验不过一律不装。**

**D2 · 验签公钥必须随应用交付（内置），不得从下发通道取。**
> 从同一条通道取公钥等于没验：能改包的人也能改公钥。

**D3 · 签名必须覆盖整个 zip**，不能只签清单。
> 只签清单的话，提示词可以被随意替换而验签照过——而提示词就是这个 agent 的全部行为。

**D4 · 必须支持多把内置公钥，任一把验过即通过。**
> 否则轮换密钥要求所有客户端同时升级，实际做不到。密钥一旦不能轮换，泄露时就只剩重出包一条路。

**D5 · 一旦启用验签，未带签名的套件必须一律拒绝，不得为兼容而放行。**
> 留一个"没签名就放行"的口子等于没签名——攻击者只需把签名去掉。

**D6 · 验签失败必须与"下载失败"分开报，且必须显著告警。**
> 验签失败可能是发布流程出错，也可能是包被替换了。静默跳过的现象是"改了没生效"，
> 与一次攻击**完全无法区分**。

**D7 · 验签失败时不得删除已装的旧版本。**
> 保住"还能用旧的"这个状态；把旧的删了会让一次发布事故升级成不可用。

**D8 · 开发期的绕过手段（若有）必须不可能出现在发布构建里。**
> 这是最容易漏的一条：为本地方便加一个"跳过验签"的开关，然后它留在了发布版里。
> 要么开发期用开发密钥真签，要么该开关由构建类型决定而非运行期配置。

**D9 · 即便有了签名，套件仍不得携带明文凭据**（见 NFR-4）。
> 签名保证的是"这份东西是我们发的"，**不保证它落到用户磁盘上之后没人读得到**——
> 套件会解包到用户数据目录，本机任何进程都能打开。这是另一件事，签名解决不了。

### E. 安装、更新与收回

**E1 · 解包必须防路径穿越。**

**E2 · 同一个 cowork 在暂存目录里有多个版本时，必须显式取最新，不得依赖文件名排序。**
> `1.9.0` 排在 `1.10.0` 后面，于是装上旧版本，现象只是"改了没生效"。

**E3 · 播种必须「只增不覆盖」**，用户改过的提示词不动；覆盖只能由版本变化显式驱动。

**E4 · 权限被收回时必须删除该套件的文件**，包括用户在本地改过的提示词；
**删除前必须显式告知用户**，不得静默删。
> 播种尊重用户、收回执行权限，两者语义相反是有意的。但这一步不可逆，必须说清楚。

**E5 · 权限被收回时必须保留对应的历史会话**，只是不能再继续（见 I4）。
> 删掉的是**能力**，留下的是**记录**。

**E6 · 套件必须装在用户数据目录下**，与用户的 skill、agent 并列。

**E7 · 改了套件内容却没改版本时，必须能被发现。**
> 安装判据是版本相等就跳过，所以内容改了不动版本的话重启后还是旧的，**且不报任何错**。
> 至少要在日志里能看出"这次跳过了"。

### F. 加载与运行

**F1 · 模板必须从「已装套件」目录加载**，出厂资源目录退化为播种源。
> 于是"装了哪几个"既决定界面列什么，**也决定实际能跑什么**——这是 G3 的落点。

**F2 · 模板 id 必须来自目录名**，不得取自提示词文件的 frontmatter。
> 两处不一致时，以 frontmatter 为准会让 id 与目录、与前端拼出来的标识对不上，
> 表现是"这个 cowork 建不了会话"。

**F3 · 交给内核的模板标识与 host 内部使用的标识必须有一处唯一的转换点，且必须有往返测试。**
> 实测教训：可用性校验忘了剥前缀，结果**四个 cowork 全被拒**，而错误信息说的是"未安装或
> 你没有权限"——**一个前缀 bug 被伪装成了权限问题**。

**F4 · 用没装的 cowork 建会话必须返回明确的「不可用」错误，不得是 500。**
> 500 看起来像"系统坏了"，与真实原因（没权限、或套件没装上）完全不搭边，
> 用户会去重试、去报故障，而不是去申请权限。

**F5 · 套件在运行期发生变化时，模板、能力归属、市场路由必须一并重建。**
> 只重建其中一样会出现"阵容更新了但能力还是旧的"这种半生不熟的状态。
> 已知限制与触发语义见 OQ-2、OQ-3。

### G. 能力隔离

> 这一组是本需求的核心，也是今天完全没有的那个维度。

**G1 · 能力必须属于 cowork，不属于会话。** 会话只表明身份。
> 像工牌不拥有门禁权限、是部门拥有；工牌只用来查你属于哪个部门。
> 归属已经在套件里声明过一次，**不得再造一套归属表**——否则有两个真值源。

**G2 · 必须有一张「会话 → cowork」的登记表，且它只回答归属、不承载任何能力语义。**

**G3 · 登记必须是会话粒度，不得按「界面上的当前 cowork」取。**
> 否则：用户在 A 下开了条会话跑长任务，切到 B 去干别的 → 后台那条 A 会话下一轮取工具时
> 拿到 B 的 skill 与 MCP。**它会中途换一套能力，而用户什么都没做**，会话记录里写的还是 A。

**G4 · 登记必须带注销**，会话结束时一并清掉。

**G5 · MCP 必须按 cowork 过滤：** 只有套件声明拥有的那几个可见、可调。

**G6 · 客户端自带的 MCP 不受套件声明约束。**
> 它随包发布、不需要云端配置，云端管理台里根本不会列出它。
> 拿套件声明去卡它的结果是：所有 cowork 都失去这个工具。

**G7 · 过滤必须覆盖「模型实际看到的那条路径」，不能只过滤列表接口。**
> 实测教训：只改了列表方法，而喂给模型的是另一个方法，于是**两个 cowork 都说自己有全部
> 三个 MCP**。验证时必须验模型实际拿到的工具集，不是接口返回值。

**G8 · 包装 provider 必须是内核抽象基类的真子类。**
> 内核用 `isinstance` 挑 provider 建路由索引。包一层却不继承的话，**该类能力会整个从索引里
> 消失**——表现是按名字调用报"找不到"，而列表里明明还在。实测出现过所有 MCP 工具全部
> `no provider found`。

**G9 · skill 必须按 cowork 过滤，且「按名字直接取内容/执行」这条路径也必须拦。**
> 那条路径不经过列表，而是按名字走一张**全局建一次、跨会话复用**的索引。
> 只拦列表的话，A 会话先把索引建起来，B 会话就能按名字读到 A 那个 skill 的文件。

**G10 · cowork 变化时必须让上述索引失效。**
> 反方向的故障：换了 cowork 之后索引还停在旧快照，表现是"这个 skill 不存在"。

**G11 · 运行期的能力清单必须按名字去重**，cowork 专属的压过通用的。
> 同名两条的后果：清单里出现两条一模一样的条目，模型无从选择；而按名字取内容只会命中
> 其中一条，另一条永远取不到——**"看得见调不动"最难查**。

**G12 · LLM 账号必须按 cowork 声明过滤；声明为空表示不限制。**
> 与 MCP 的空语义**刻意相反**：MCP 是能力，"给了才有"；LLM 是资源，"没说就是都能用"。
> 这条差异要写进代码注释，否则下一个人会来"统一"它。

**G13 · LLM 过滤后一个账号都不剩时，必须在日志里说明真实原因。**
> 界面上只会显示"没有可用模型"，而真实原因是套件里写了不存在的账号名。

### H. 技能市场与归属

**H1 · 每个 cowork 的 skill 市场地址必须写在它自己的套件里，不得放环境变量。**
> 一个用户可能同时开通好几个 cowork，每个各有各的市场；放变量则每新开通一个就要改一次
> 部署配置，改漏一处就是阵容不同。

**H2 · 市场页必须按作用域分页签**：一个固定的通用页签 + 每个有独立市场的已开通 cowork 一个。
**地址相同的必须合并成一个页签。**
> 否则用户看到两个一模一样的页签。

**H3 · 一个 cowork 配了市场之后，不得再为它回落到通用市场。** 两个源都没配才整体回落。
> 回落的话通用市场的内容会在那个 cowork 的页签里重复出现一遍，而且从那里引用会被记成
> "只归它"——用户以为引的是专属 skill，实际是通用那一份。

**H4 · 归属必须支持「所有 cowork」这个通配值，且它是缺省值。**
> 用通配而不是把当前所有 cowork 枚举进去：将来新增一个 cowork 时通用 skill 应当**自动**对它
> 可用；枚举的话得回头补每一条，漏补的表现是"新 cowork 少了几个通用 skill"，没人会立刻发现。
> 存量记录没有归属字段，读成"谁都能用"才是它们此前的实际行为；读成"谁都不能用"会让用户
> 已有的 skill 在升级后一夜之间全部消失。
> ⚠ **从存量应用导入进来的那批是例外**：它们按一张固定名单判归属，不套用这里的缺省（见 J10）。
> 缺省管的是"字段缺失怎么读"，导入管的是"这一批东西本来属于谁"——两件事。

**H5 · 从市场引用时，归属由「从哪个页签引的」决定，不得再弹框追问。**
> 用户点的那个页签已经表达了意图，再问一次只会让人对着两处描述同一件事。

**H6 · 本地导入 skill 时必须询问归属，默认「通用」，且必须是可多选的勾选清单。**
> 导入没有页签这个上下文，所以必须问。默认收窄会让人在别的 cowork 里找不到刚导入的
> skill，而这个现象与 bug 无法区分。
> 多选是因为归属本来就是一组；下拉只能选一个，逼着用户为"给两个 cowork 用"导入两次。
> 「通用」与具体项互斥——通配已涵盖所有 cowork，再叠一个具体的会显示成"通用 / MBB"这种
> 自相矛盾的样子。

**H7 · 归属必须在界面上可见，通用的也要显示。**
> 用户手里多数是通用 skill，通用不占位的话整个"归属"概念在界面上根本不存在，
> 人就无从判断自己刚才的选择有没有生效。

**H8 · 同一条 skill 被多处引用时，归属取并集，不得覆盖。**
> 覆盖的话用户做的是"再给一个 cowork 也加上"，得到的却是"换了个 cowork"，
> 先引的那个静默失去这条 skill。

**H9 · 上传回市场必须传到它归属的那个市场。**
> 否则用户在归属上花的心思在上传这一步就丢了。

**H10 · 权限收回时，只清「仅被它引用」的市场 skill；本地导入的 skill 一律不删。**
> 本地 skill 是用户**自己的东西**，只是暂时没有任何 cowork 认领它因而不可见，
> 权限恢复后自己回来——与只读会话同一个道理：**可见性是推导的，不写状态**。

### I. 界面与状态呈现

**I1 · 阵容是运行期异步到达的数据，不得在模块加载时捕获成常量。**
> 实测教训：模块顶层那一行拿到的永远是空数组，**且不报错**，只表现为"界面一个 cowork 都没有"。
> ⇒ 对外暴露取值函数而不是常量，让编译器把每个调用点都逼出来。

**I2 · 「一个 cowork 都没有」必须区分成五种状态，各给各的说法：**

| 状态 | 判据 | 界面 | 能新建会话 |
|---|---|---|---|
| 本构建没有这一层 | 构建期就没有 cowork | 通用文案，一切正常 | 是 |
| 未登录 | 没有令牌 | "请先登录" | 否 |
| 还没拉到 | 对账未完成 | "正在获取可用的 Cowork…" | 否 |
| 拉取失败 | 对账失败 | "暂时获取不到…稍后重试" | 否 |
| 拉到了但为空 | 对账成功、清单为空 | "尚未开通…请联系管理员" | 否 |

> 判据必须是**构建期有没有这一层**，不是运行期清单——运行期清单为空正是要区分的那件事本身，
> 拿它当判据是循环的。五种数据上长得一模一样，但该让用户做的事完全相反。

**I3 · 零 cowork 时不得提供「新建会话」，且拦截必须收在一个口子上。**
> 点下去会建出一条跑母版的会话，它不属于任何 cowork、界面上无名无姓，
> 而用户以为自己在正常使用产品。新建有好几个入口，逐个记得加判断迟早漏一个。

**I4 · 「只读」必须是推导出来的，不得写进会话记录。**

```
只读  ≡  这条会话的 cowork 此刻不在已装清单里
```
> 加字段就得在权限恢复时把它清掉，而"该清没清"是个静默故障——用户权限回来了，
> 会话却永远停在只读。推导式没有这个状态要维护：套件装回来，会话自己就活了。

**I5 · 只读会话必须真的读得了**：历史消息、任务、导出都要正常。
> 如果只读实现成"打开就报错"，等于变相删除——用户会认为记录丢了。

**I6 · 继续/恢复只读会话必须返回明确的「权限已收回」，且不得是 404、不得是 500。**
> 会话在、也读得了，缺的是**继续**它的权限；404 会让人以为记录没了，
> 500 会让人去报故障而不是去申请权限。

**I7 · 被收回 cowork 的会话不得受「当前 cowork」过滤，必须仍有入口。**
> 部分收回时，被收回的 cowork 没法成为"当前 cowork"（它不在阵容里），
> 于是那些会话**彻底没有入口**——这比"打开就报错"更彻底地违反 I5。
> ⇒ 应当收进一个可折叠的归档区。

**I8 · 归档同样必须是推导的，不写标记，且不给「取消归档」按钮。**
> 按了也回不去，一个按下去没反应的按钮比没有这个按钮更糟。

**I9 · 只有在阵容确知时才判只读。** "还没拉到"和"拉取失败"是"不知道"，不是"没有"。
> 否则一次网络抖动会显示成"你的权限被收回了"，而后端其实好好的。

**I10 · 前端必须有顶层错误兜底。**
> 渲染层任何一处抛异常，用户拿到的就是一块纯白——没有提示、没有重试入口，
> 也看不出是崩了还是在加载。

### J. 存量 IPMaster-Cowork 导入

> 本期换应用身份，新旧两版在同一台机器上完全并存、数据目录互不可见。
> 没有这条路，存量用户装上新版等于从零开始，而旧数据一直躺在那儿没人管。

**J1 · 导入必须由用户主动触发，不得在启动时自动进行。**
> 自动搬会在用户还没决定要不要用新版时就改变两边的状态。

**J2 · 「自动继承旧数据目录」的机制必须保持关闭。**
> 现有代码里有一条启动时自动把旧数据糊过来的路径。它一旦生效会**抢在本功能之前破坏隔离**，
> 而且是静默的——用户不会知道自己的新版里混进了旧数据。

**J3 · 导入必须是选择性的**，逐项决定搬与不搬（清单见附录 B），不得整目录拷贝。

**J4 · 会话库必须先做 WAL 检查点再拷贝。**
> 不做的话最近一段写入还在 WAL 里没落盘，拷过去就丢了——而现象是"最近几条会话不见了"，
> 用户会以为是导入功能坏了。

**J5 · 后端配置文件必须重写而不是照搬。**
> 里面是指向**旧目录的绝对路径**（数据目录、日志目录、资源目录）。照搬的结果是新版跑起来
> 读写的还是旧目录——两个应用共用一份数据，问题会以极其难查的方式浮现。

**J6 · 依赖虚拟环境必须不搬，由新版重建。**
> 里面写死了绝对路径，搬过去是坏的。

**J7 · 各类状态标记必须不搬**（安装版本、配置规整标记、播种标记、遥测安装 id）。
> 搬了的后果各不相同且都静默：跳过新版的配置规整、误判"已播种"从而跳过出厂数据初始化、
> 两个安装共用同一个遥测 id 导致数据无法区分。

**J8 · MCP 配置必须与新版出厂播种的同名项合并，不得直接覆盖。**
> 直接覆盖会丢掉新版新增的随包 MCP；反过来直接跳过则丢掉用户自己加的。

**J9 · 导入完成后必须留标记，避免重复导入。**

**J10 · 存量带过来的 skill 没有归属字段，必须按一张固定名单判定归属，不得一律判成「通用」。**

```
下列按名字判为「通用」（*）：
    docx · pptx · pdf · xlsx · skill-creator · skill-edit · huawei-intranet-search
其余一律归 ipmaster
```

> **为什么不能一律通用**：存量装机里除了上面那几个文档处理与 skill 编辑工具，其余都是 IP 网络
> 领域的东西（拓扑绘图、L2VPN 拓扑、SDN 迁移调研）。判成通用会让它们出现在**所有** cowork 的
> 能力清单里——模型手里多出一堆不该有的工具，而这正是本需求要消灭的那种串台（§G）。
>
> **为什么不能一律归 ipmaster**：那几个是所有 cowork 都要用的基础工具。判给 ipmaster 会让别的
> cowork 连读个 docx 都不行，而现象是"这个 agent 好像变笨了"，没人会联想到是导入时归属判错。

**J10.1 · 这张名单必须集中在一处、可枚举、有测试。**
> 它是一次性迁移规则，**不是运行期回落**——写成运行期兜底的话，用户事后改了归属会被下次
> 启动重新覆盖回去。

**J10.2 · 归属按记录写入，与当前是否有该 cowork 的权限无关。**
> 用户此刻没有 ipmaster 权限时，那些 skill 归属仍写 ipmaster，只是**暂时不可见**（不删，见 H10）；
> 权限到位后自动出现。可见性是推导的，归属是数据——两件事不能混。

**J10.3 · 名单按 skill 名匹配，比较必须与 skill 名的既有规则一致**（大小写、去空白）。
> 匹配不上的静默后果是"这个通用工具被判给了 ipmaster"，别的 cowork 里就少了它。

**J11 · 导入进来的会话可能指向新阵容里没有的 cowork，必须走只读路径，不得报错。**
> 这正是 I4「只读是推导的」天然覆盖的情形——但必须实测确认，否则表现是导入后一打开就 500。

**J12 · 部分失败必须可诊断，且不得留下半个状态。**
> 要么这一项搬成功，要么这一项没搬且说得出为什么。半个数据库比没有数据库更糟。

**J13 · 导入只在「本机第一次装 NetLIVE Cowork」时主动提示，且这个判定必须在应用写出
任何自己的数据之前取。**

判据：**业务数据目录里没有安装版本标记**（首启时应用自己写的那个）。

> **顺序是这条的全部难点。** 那个标记在首启的播种末尾就会被写出去，判定晚一步就**永远
> 判成"不是第一次"**，而且不报错——用户再也看不到导入引导。
> 同一个文件里已经因为同样的理由踩过两次：一次是升级判定（代码里已有注释"必须在播种
> 之前取"），一次是配置规整跑在配置生成之前、导致新装机器永远不规整。
>
> ⚠ **不能用浏览器侧那个目录判**：它在应用就绪之前就被创建了，永远"存在"。
> 要判的是业务数据目录（放会话库、配置的那个）。
>
> ⚠ **卸载重装不算第一次**：卸载默认不删数据目录，标记还在。这是对的——数据还在，
> 本来就不需要导入。

**J14 · 「能不能导入」必须由推导得出，不得写成"只有首启那一次能点"。**

```
可导入  ≡  新版的会话库里一条会话都没有（且没导过）
```

> **为什么不能严格锁死在首启**：用户首启时手头忙，点了"以后再说"，就再也导不了了——
> 这会直接变成支持工单。
>
> **为什么判据是"没有自己的会话"而不是"没用过"**：会话正是会与导入数据冲突的东西。
> 用户还没建过会话时导入是安全的；一旦建了，入口自动灰掉并说明原因。
> 与只读会话（I4）同一个套路：**可见性/可用性是推导的，不写状态**。

**J15 · 限定「新版为空时才能导入」是有意的，它同时消掉了「合并还是覆盖」这个问题。**
> 新版必然是空的 ⇒ 不存在冲突 ⇒ 不需要回答"已经用过一阵怎么办"。
> **这是一条用约束换掉一整块复杂度的取舍，实现时不要为了"更灵活"把它放开**——
> 放开就要重新面对合并语义，而那是一整套没人测得全的分支。

### K. 活动日志与可追溯

> **这一组的存在理由：本需求里绝大多数失败都是静默的。** 对账失败不动、版本相等跳过、
> 某家市场没配跳过、能力被拦、导入某项没搬——每一条正确的行为都长得像"什么都没发生"。
> 没有日志，"它没生效"与"它生效了只是结果如此"根本无法区分。

**K1 · 下列活动必须留日志，每条都要说清「做了什么 + 为什么」：**

| 活动 | 至少要能看出 |
|---|---|
| 授权对账 | 去了哪个地址 · 拿到哪几个 · 各是哪一版 · 失败时的分类（B9） |
| 验签 | 通过 / 失败及原因 · 用的哪把公钥 |
| 安装 | 装了哪个、从哪一版到哪一版 |
| **跳过安装** | **哪个、因为版本相等**（C7 的静默面：改了内容没改版本时，这是唯一线索） |
| 收回 | 删了哪个 · 连带删了用户改过的哪些文件（C4 不可逆，必须留证） |
| 会话归属 | 建会话登记了哪个 cowork · 结束时注销 |
| **能力被拦** | **哪条会话、想用哪个能力、属于哪个 cowork**（见 K4） |
| 市场作用域 | 算出了哪几个页签、各挂了哪些源 |
| 归属判定 | 引用/导入时定了什么归属 · 存量导入按名单判成了什么（J10） |
| 存量导入 | 每一项搬了/跳过了/失败了，逐项（J12 要求可诊断） |
| 登录态变化 | 登录 · 切账号 · 令牌失效（B5/B6） |

**K2 · 「什么都不做」的分支必须留日志，且要写明是哪一种"不做"。**
> 这是本组最要紧的一条。`对账失败 → 一动不动`（C7）与`对账成功但清单为空 → 全删`
> 在文件系统上的差别是天壤之别，而**在没有日志时它们看起来一模一样**（都是"我的
> cowork 不见了"或"没变化"）。

**K3 · 日志的验收标准是：能回答「这台机器此刻为什么是这个状态」。**
> 不是"记得越多越好"。拿这个标准去删：一条日志如果无助于回答这个问题，就是噪声，
> 会淹掉有用的那几条。

**K4 · 能力被拦必须留日志，且这是排查串台的唯一线索。**
> 隔离做对时，用户侧完全无感——模型只是"没有那个工具"。做错时（该有的没有），
> 用户报上来的现象是"这个 agent 变笨了"。**两种情况在界面上无法区分，只有日志能分。**
> 拦下来的那条要记：哪条会话、属于哪个 cowork、想用哪个能力。

**K5 · 复用现有日志设施，不得新建一套。**
> 仓里已有结构化日志、轮转、打包、上传（`observability/logging.py`、
> `electron/lib/log-rotate.js` / `log-bundler.js` / `log-uploader.js`）。
> 新建一套的后果是用户报障时提供的日志包里**恰好没有新功能那部分**。

**K6 · 日志与运营打点是两件事，不得混用。**

| | 日志 | 运营打点 |
|---|---|---|
| 给谁看 | 排查问题的人 | 运营/分账 |
| 去哪 | 留在本机，用户报障时才打包上传 | 主动上报到云端 |
| 内容 | 越具体越好（路径、版本、原因） | 只要口径统一的那几个字段 |

> 混用的两个方向都难受：往打点里塞排查细节会让**上报量爆掉且含本机路径**；
> 把日志当打点上报则可能**把用户环境信息传出去**。

**K7 · 令牌、密钥、用户凭据不得进日志**（与 NFR-8 同）。
> 日志会被用户打包上传，**它比打点更容易外流**。

## 6. 非功能需求

**NFR-1 · 权限必须在服务端闭环，不得由客户端自证。**
> 客户端说"我有 MBB"云端就给 MBB，等于没有权限。

**NFR-2 · 强制边界必须落在能力提供层，不能只在界面。**
> 界面拦得住人，拦不住模型。

**NFR-3 · 套件的真实性必须由签名保证，不得依赖"托管处在内网"这一环境假设。**
> 环境假设会随部署变化而失效，而失效时没有任何信号。

**NFR-4 · 套件清单不得携带任何明文凭据**，连接定义只允许地址与超时一类。
> 签名保证"这份东西是我们发的"，**不保证它落到用户磁盘之后没人读得到**。
> 套件会解包到用户数据目录，本机任何进程都能打开。要带凭据得另想办法（OQ-6）。

**NFR-5 · 对账必须不阻塞界面**，失败只给一条不打断的提示。

**NFR-6 · 对账频率必须可配**，且默认值要考虑云端的承受能力。
> 一人一实例的形态下，一千个人就是一千个客户端在问。

**NFR-7 · 日志必须能回答四个问题：** 这次对账拿到了什么、验签结果、装了/删了什么、为什么跳过。
> 本需求里绝大多数故障都是静默的，日志是唯一的排查入口。

**NFR-8 · 令牌、密钥、用户凭据不得出现在日志、遥测与错误上报中。**

## 7. 验收标准

> 每条都是可实测的场景。括号里是失败时的典型现象，用于确认测的是对的东西。

| # | 场景 | 期望 |
|---|---|---|
| AC-1 | 云端只授权两个 cowork，启动应用 | 界面恰好两个；数据目录里恰好两个 |
| AC-2 | 直接调接口，用没授权的 cowork 建会话 | 明确的"不可用"错误，不是 500（G3 的落点） |
| AC-3 | 在 A 的会话里问模型有哪些工具 | 只有 A 声明的 MCP + 客户端自带的；**要看模型实际拿到的工具集** |
| AC-4 | 在 A 的会话里按名字调 B 的 skill 文件 | 拒绝（只拦列表的话这里会成功） |
| AC-5 | 断开云端后重启 | 应用照常开、历史照常看；套件不增不删 |
| AC-6 | 云端把某个 cowork 收回后对账 | 套件文件消失；该 cowork 的历史会话仍可打开、可读 |
| AC-7 | 继续 AC-6 的那条会话 | 明确的"权限已收回"，不是 404、不是 500 |
| AC-8 | 把套件放回去重启 | 同一条会话直接能继续，**无需任何数据迁移** |
| AC-9 | 部分收回后看会话列表 | 被收回那些 cowork 的会话仍有入口（在归档区），不是消失 |
| AC-10 | 云端把版本从 5 回滚到 3 | 客户端装回 3（写成"变大才装"的话这里不会变） |
| AC-11 | 授权清单请求超时 | 不装不删，提示说的是"没核对上"而不是"你没权限" |
| AC-12 | 未登录直接启动 | 说的是"请先登录"，不是"尚未开通" |
| AC-13 | 换一个账号登录 | **立刻**重新对账；阵容随之改变；上一个账号的专属 skill 不可见 |
| AC-14 | 令牌过期后触发对账 | 明确提示重新登录，不表现为"没有 cowork" |
| AC-15 | 改动 zip 内容后重新签名之外的任何一个字节 | 验签失败、不安装、显著告警；已装的旧版本仍在 |
| AC-16 | 用一个未签名的包 | 拒绝安装（有"兼容放行"口子的话这里会装上） |
| AC-17 | 发布构建里查找验签绕过开关 | 不存在（D8） |
| AC-18 | 从某 cowork 页签引用一个 skill | 归属自动是那个 cowork，未弹框追问 |
| AC-19 | 本地导入一个 skill 不做选择 | 归属为通用，且界面上看得到"通用"这个标签 |
| AC-20 | 一个 cowork 都没授权 | 说的是"尚未开通…请联系管理员"，且不能新建会话 |
| AC-21 | 存量应用里有会话与 LLM 账号，执行导入 | 历史会话、账号、自建 skill 都在；旧目录未被破坏 |
| AC-22 | 导入后检查新版的后端配置 | 其中的路径全部指向**新**数据目录（照搬的话会指向旧的） |
| AC-23 | 导入前先在存量应用里产生几条会话，立刻导入 | 最近那几条也在（没做 WAL 检查点的话会缺） |
| AC-24 | 导入的会话属于新阵容里没有的 cowork | 能打开、只读，不报 500 |
| AC-24a | 导入后查 `docx` 的归属 | 通用；且在**非 ipmaster** 的 cowork 会话里模型能用它 |
| AC-24b | 导入后查 `huawei-l2vpn-topology` 一类的归属 | 归 ipmaster；在别的 cowork 会话里模型**看不到也调不动** |
| AC-24c | 导入后手工把某条归属改掉，重启 | 改动保留（写成运行期回落的话会被覆盖回去，J10.1） |
| AC-25 | 重复执行导入 | 有标记拦住，不产生重复数据 |
| AC-26 | 全新机器首次装新版，旧版数据在 | 主动弹出导入引导 |
| AC-27 | 首启点了"以后再说"，重启应用 | **不再主动弹**，但设置页入口仍可用（J14） |
| AC-28 | 在新版里建一条会话，再看导入入口 | 已灰掉，并说明原因（J14 的推导判据生效） |
| AC-29 | 卸载新版后重装（数据目录仍在） | **不当作第一次**，不主动弹 |
| AC-30 | 在首启播种之后才取首次判定 | 这是实现错误：**必然判成"不是第一次"**，用测试钉住取值时机（J13） |
| AC-31 | 断网启动后翻日志 | 看得出"对账没成功、本地未改动"，而不是一片空白（K2） |
| AC-32 | 改了套件内容但没改版本，重启后翻日志 | 看得出"版本相等、已跳过"（否则"改了没生效"无从查起） |
| AC-33 | 在 A 的会话里调 B 的能力后翻日志 | 有一条拦截记录：哪条会话、属于谁、想用什么（K4） |
| AC-34 | 用户报障打包日志 | 上面这些都在包里（K5：没新建第二套日志） |
| AC-35 | 通篇搜日志与打点内容 | 无令牌、无密钥（K7 / NFR-8） |

## 8. 待定事项

> 这些必须先有结论才好写，不是实现细节。

**OQ-1 · 对账频率。** 每天一次意味着"权限收回最长一天后才生效"。要更快是产品决定，
也取决于云端扛不扛得住。

**OQ-2 · 热更新的触发语义。** 权限在**会话跑到一半**时被收回，怎么办？
立刻生效 / 等当前任务跑完 / 等会话结束。三选一。
> 已定的"收回 → 转只读"讲的是重启后的状态，没讲跑到一半怎么办。

**OQ-3 · 套件带来的新 MCP 服务器能否热更。** MCP 连接在启动时建好，
所以"只用平台已有 MCP 的 cowork"热更是完整的，带自定义连接定义的仍要重启。
是否要做到不重启，取决于下发的频率。

**OQ-4 · 零授权时是否连母版会话也一并拒绝。**
母版要留给历史会话与内部任务，所以它是唯一放行的。判据是现成的
（本构建有 cowork 这一层、而已装为空 ⇒ 就是"没开通"）。
这把"界面上看不到"升级成"接口上也不给"，属于权限策略而非展示，宜单独确认。

**OQ-5 · 签名怎么随包走。** 现有下发契约只给了内容哈希响应头，没有签名字段。
三条路：塞进 zip 内（如 `cowork.sig`）· 加一个响应头 · 单独一个端点取。
**需要与运维确认**，且这决定了 §D 的实现形状。

**OQ-6 · 套件将来要带凭据时怎么办。** 本期禁止（NFR-4）。真要带的话，
签名解决不了"解包后本机可读"这一半，需要另外的方案（运行期换取短期凭据等）。

**OQ-7 · ~~导入时新版已经用过一阵怎么办~~ —— 已由 J14/J15 定掉，不再是待定。**
结论：**新版一旦有了自己的会话就不给导**，因此不存在"合并还是覆盖"。
用一条约束换掉了一整块合并语义。

**OQ-8 · 导入入口放哪。** 首启引导（J13 的主动提示），加设置页里一个入口（J14 的推导可用性）——
两处都要，还是只要一处？以及导入后是否提示用户卸载旧版、旧数据是否保留。
以及导入后是否提示用户卸载旧版、旧数据是否保留。

**OQ-9 · 通用市场的正式地址。**

**OQ-10 · 母版改进的下发方式。** 四个 facet 全自带 ⇒ 母版一改，所有套件都要重新生成、
**重新签名**并重新下发。这不是"待定"，是**已知的运维负担**，需要把
"重新生成→打包→签名→发布"串成一条命令，否则实际会漏掉几个。

## 附录 C — 与 skill 包的异同

| | skill 包 | cowork 套件 |
|---|---|---|
| 形状 | 目录打 zip | 同 |
| 谁能装 | 用户手动导入 / 从市场引用 | **平台按权限下发** |
| 是否验签 | 否 | **是**（§D） |
| 数量级 | 几十个，用户自由增删 | 个位数，平台统一管 |
| 收回时 | 不删（用户自己的东西） | 删（平台发的许可） |

**可以复用**：解包与路径穿越防护、播种的"只增不覆盖"。
**不该复用**：市场拉取链路——套件是平台下发，不走用户市场。
**形状像、性质相反**，不要因为像就复用那条链路。
