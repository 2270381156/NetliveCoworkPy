## 0. 一分钟版

**业务侧只认识一个函数：**

```python
from netlivecowork.reporting.record import record

record("skill_usage", {"function_name": "docx", "duration": 2.5}, session_id=sid)
```

它不认识出口、不认识重试、不认识"要发给哪个云"。那些全在**路由表**和**出口**里。

**加一种统计** = 写一个订阅者把内核事件翻译成 `record(...)` + 路由表加一行（§5.1）。
**加一个平台** = 写一个出口类 + 路由表加一行（§5.3）——
**已有的统计一行都不用改**，比如"skill 用量再发一份给别处"就是加一条路由的事。
两件事都**不用碰**对方，也不用碰已有的任何统计。

⚠ 两个最容易踩的：`install_routes` 是**覆盖不是追加**（不带 `DEFAULT_ROUTES`
会让现有上报全部静默消失）；出口名**拼错的表现是数据消失**，不是报错。

## 1. 名词

| 词 | 意思 |
|---|---|
| **主进程** | 应用外壳（`electron/main.js`）。**登录令牌只在这里**——系统密钥库的接口只有它能调 |
| **后端** | Python 服务，由主进程拉起。有这个部署自己的凭据（AK/SK），没有用户令牌 |
| **内核** | `ctx_weft`，跑 agent 的引擎。以只读 wheel 交付，**绝不修改** |
| **事件总线** | 内核里的事件流。skill 调用、LLM 响应完成这些都从它出来 |
| **记录类型** | 一种统计。今天有 `skill_usage` / `token_usage` / `step_failed` / `task_failed` |
| **出口** | 数据"往外发"的那一段：发给谁、用什么凭据、失败怎么重试 |
| **归属** | 一条数据属于哪个 cowork / 哪个账号。**今天恒为空**，等 cowork 那块接上 |
| **扇出** | 一条数据要发给几个平台时，**复制成几条各走各的**，而不是一条发几次 |
| **投影** | 从统一记录里挑出某个平台要的那几个字段（顺带脱敏），各平台各一份 |

## 2. 架构

### 2.1 四段

```
① 产生       领域语义。"一次 skill 调用发生了" / "这一轮用了多少 token"
   │         ← 不知道要发给谁，也不知道怎么发
   ▼
② 路由+扇出   按「记录类型 × 归属」查出要发给**哪几个**平台（可能不止一个）
   │         每个平台复制出一条独立待发项，各带各的字段投影
   ▼
③ 本地队列   队列里的一条 = **一条记录发给一个平台**
   │         取走 → 落盘 → 确认，崩了不丢
   ▼
④ 发送       各平台自己实现：Datalink（后端直发）· 主进程代发 · 将来的第 N 个
```

### 2.2 代码

```
src/netlivecowork/reporting/
  record.py      117 行   统一入口 + 路由表的装载
  routing.py     107 行   Route / Delivery / resolve（匹配 + 扇出 + 投影）
  spool.py       158 行   本地队列：append / claim / ack / drain
  labels.py       42 行   归属（今天恒为空）
  defaults.py     48 行   出厂出口与路由 —— **它就是重构前的行为**
  sinks/
    base.py       32 行   出口契约
    __init__.py   33 行   出口注册表
    relay.py      38 行   主进程代发
    datalink.py  744 行   后端直发（配置·签名·HTTP·重试·队列·死信）
```

**产生那一段不在这里**，它属于各自的领域：

```
skill 调用    providers/capability/skills/runtime/usage.py
token 用量    observability/token_usage_subscriber.py
失败事件      observability/telemetry_subscriber.py
```

### 2.3 今天的三条数据流

| 记录类型 | 谁产生 | 出口 | 用什么凭据 | 谁发 |
|---|---|---|---|---|
| `skill_usage` | 内核事件（任务创建/开始/能力结束） | Datalink | 部署的 AK/SK | **后端** |
| `token_usage` | 会话处理 LLM 响应时同步调 | 主进程代发 | **用户令牌** | Electron |
| `step_failed` / `task_failed` | 内核事件 | 主进程代发 | **用户令牌** | Electron |

**两类出口的差别不是历史包袱**：用户令牌只存在主进程的安全存储里，后端拿不到。
任何"统一成后端直发"的方案都会撞上它，而撞上之后的常见做法是把令牌递给后端——
那正好破坏"令牌不出主进程"这条安全要求。

⇒ **不要合并出口。要合并的是出口以外的东西**，那正是这次做的。

## 3. 设计意图：每条规矩都对着一种"不报错的故障"

> 本模块几乎所有故障都是静默的：数据没发出去，本地看起来与发出去了一模一样，
> 要等运营那边发现数据缺了才知道。下面每一条都是冲着某一种静默故障去的。

### 3.1 出厂默认就是重构前的行为

**没做成"装配期必须记得装路由表"。** 那样任何没走到那步的路径（测试、单跑脚本、
将来新加的入口）都会静默地不再上报。

⇒ `defaults.py` 内置了与重构前一一对应的路由，**不配置也照常工作**。
装配期可以用 `install_routes()` 覆盖。

判断"装没装过"用的是**标记**而不是"表是不是空的"——否则"我确实不要任何路由"
这个意图表达不出来，每次都会被默认值顶回去。

### 3.2 扇出发生在入队之前

一条记录按路由复制成 N 条待发项，此后各走各的。**不能"一条记录发给多个平台"再统一记状态**：

```
发给 A 成功、发给 B 失败  →  整条重试  →  A 收到重复
```

代价是存储放大 N 倍——打点数据量小，可接受。

每条待发项带两个 id：`record_id`（扇出的几条共享，跨平台对账时认出"同一件事"）
与 `delivery_id`（各自独有，下游去重用）。

### 3.3 字段投影是脱敏点，不是性能优化

同一条数据发给不同平台，可见字段可能不同（比如某个平台不该看到用户名）。
**写在路由表里，不靠出口自觉**——自觉的失效方式是"多发了一个字段"，而它不报错。

缺失的字段直接不出现，**不补空值**：补了下游就分不清"没有"和"是空的"。

### 3.4 归属未知 ≠ 属于所有人

空归属**不匹配**具名 cowork 的路由。否则在 cowork 那块接通之前，
数据就会流向本不该去的平台，而那不可撤销。

反过来也能表达："归属未知的发到某个兜底平台"——写 `cowork=""` 的路由即可。

### 3.5 归属参数从第一天就在签名里

今天恒返回空（`labels.py`），但 `record()` 的签名已经带着它。
等 cowork 的会话归属表建好，**只改 `labels.py` 一个文件**，调用点一个都不用动。

反过来（先不带、以后再补）要回头改每一处打点，而打点散在事件订阅、会话处理等
好几条路径上，漏一处不报错——只是那类数据永远没有归属。

### 3.6 静默消失的两条路都必须留日志

```
没有任何路由匹配        routing.resolve 记 WARNING
路由指向不存在的出口     record._enqueue 记 WARNING（出口名拼错时）
```

这两种在本地都表现为"什么都没发生"，与"正常发走了"无法区分。

### 3.7 打点绝不能影响业务

`record()` 整个兜住异常，各出口内部再各自兜一道。
**分层之后风险反而变大**：多了路由与多个出口，任何一处抛出来都会污染调用点。

### 3.8 全进程只有一把队列锁

追加与"重命名接管"必须互斥。两把锁的失效方式是**偶发的半行 JSON**：
取走的那批里会有写了一半的行。量小时几乎撞不到，上线后才出现。

⇒ 锁与队列在同一个模块里，别处不许再定义。用测试钉住，不靠约定。

### 3.9 队列用「取走 → 落盘 → 确认」

```
取走即删     后端把批次交出去 → 主进程还没落盘就崩了 → 这批没了
取走-确认    重命名后的批次在确认之前一直保留，崩了下次照样取到
```

确认时校验批次哈希，对不上就拒绝——那批不是调用方拿到的那批，删掉等于丢数。

## 4. 迁移记录

### 4.1 之前是什么样

一个 903 行的 `persistence/skill_reporter.py`，里面塞着六件事：

```
① Datalink 配置读取（环境变量）
② AK/SK 签名
③ 用户身份（从系统 PWD 取 / 从会话表取）
④ 领域语义：内核事件 → "一次 skill 调用"        ← 只有这件是 skill 的
⑤ HTTP 发送 + 重试 + 退避 + 状态码分类
⑥ 本地队列：重试文件 + 死信文件 + 定时清空
```

**①②③⑤⑥ 与 skill 毫无关系**，是任何一种打点都要的。接第二个平台就得再抄一遍。

另外两处问题：它放在 `persistence/`（存储层），位置本身在误导人；
重试与队列有**两套实现**（后端一套、主进程一套），丢数语义不同，
于是"这条数据到底丢没丢"要先问"它走了哪条路"。

### 4.3 那次自查值得记下来

第 1–4 步做完之后自查"是不是真的只剩一套"，发现**没有**：

- `api/spool.py` 里还有一份完整的取走/确认/解析，与 `reporting/spool.py` 重复；
- `observability/events.py` 的 `emit()` 生产代码已 0 处调用，只剩测试在用。

两份队列实现的危险在于：**一边改了另一边没改，表现是"主进程偶尔取不到数据"，
而两边各自的测试都是绿的**。

⇒ `api/spool.py` 收成三行转发（190+ → 109 行），`observability/events.py` 整个删掉。
并加了两条测试直接钉死：

```python
assert not hasattr(api_spool, "_parse_spool_bytes")   # 接口层不许再自己解析
assert not hasattr(api_spool, "_spool_lock")          # 也不许再持有一把锁
```

### 4.4 怎么保证"功能一致"的

**① 测试跟着代码走，断言一个字不改。** 出口那 9 条搬去新文件时只换了模块名——
搬完全绿就是行为没变的证据。领域那些留在原处，只把拦截点从"出口函数"换成 `record()`。

**② 基准是旧实现的真实产物，不是"我觉得应该长这样"。** 切换时旧的 `emit` 还在，
直接拿它比对。旧实现删除后改成钉住当时比对出来的形状，并在文件头记了出处。

**③ 端到端不 mock 中间层。** 拆完之后中间多了路由这一层，就多了三处会静默断掉的地方
（路由没匹配、出口没注册、默认没生效），三种在本地都表现为"什么都没发生"，
而重构前那是不可能的——那时是直接 await 一个 HTTP 调用。

**④ 运行时追踪确认主链路。** 真跑一次上报，看调用栈实际经过哪些模块：

```
token_usage_subscriber.report_token_usage
  → reporting/record.py:record
  → reporting/labels.py:labels_for_session
  → reporting/routing.py:resolve → _matches → _project
  → reporting/record.py:_enqueue
  → reporting/sinks/relay.py:enqueue
  → reporting/spool.py:append
```

一处旧代码都没经过。

**⑤ 打包产物两个方向都验。** 新模块在包里、**已删的旧模块不在包里**——
PyInstaller 是静态分析找依赖的，只要还有一处 import 引着旧模块，它就会被一起打进来。

## 5. 开发指南

### 5.1 加一种统计（例：MCP 调用）

**要写的只有"产生"那一段。** 路由、扇出、队列、重试、脱敏、多平台都是现成的。

**第一步 · 写一个订阅者**，把内核事件翻译成一条记录：

```python
# 放在这类能力自己的领域目录下，不要放进 reporting/
class MCPUsageReporter:
    async def on_event(self, event):
        if event.type == EventType.CAPABILITY_INVOKED:
            记下开始时间
        if event.type == EventType.CAPABILITY_FINISHED:
            record("mcp_usage", {...}, session_id=event.session_id)
```

内核已经给足了数据：`CAPABILITY_FINISHED` 的载荷里有 `capability_name`、`outcome`、
`arguments`、`result_length`，配上 `CAPABILITY_INVOKED` 就能算耗时。

**第二步 · 路由表加一行**（或者先只加进 `defaults.py` 试跑）：

```python
Route(kind="mcp_usage", sink="datalink", fields=("tool_name", "duration", "outcome"))
```

**第三步 · 在 `lifecycle.py` 里订阅它。**

完了。**不用碰** `reporting/` 里的任何文件。

### 5.2 加一种统计时必须先想清楚的三件事

**① 怎么认出"这是我要的那种调用"。**
`capability_name` 里既有 MCP 工具，也有文件系统、skill 执行器那些内置工具。
判据要**问对应的 provider"这个名字是不是我的"**，不要靠字符串前缀猜。

**② 量级。**
skill 一次会话跑几次，MCP 工具可能跑几十上百次。直接一条一条报的话，
上报量和对端存储都要重新估。**大概率需要先聚合再报**，而聚合逻辑今天一点都没有。

**③ 载荷里有没有敏感内容。**
比如 MCP 调用参数带着用户的真实输入（查询词、设备名、文件路径）。
**绝对不能整个塞进去。** 路由表的字段投影就是干这个的，但要**明确列出只报哪几个**，
而不是"顺手都带上"。

### 5.3 加一个平台（例：skill 用量再发一份给别处）

三步，**产生数据的地方一行都不用改** —— `skill_usage` 已经在走 `record()`。

#### 第 0 步：先定它属于哪一类

这一步决定了后面怎么写，选错了要推倒重来：

| | 凭据 | 谁发 | 怎么写 |
|---|---|---|---|
| **后端直发** | 这个部署自己的 AK/SK | 后端 | 参照 `sinks/datalink.py`：自己攒队列 + 重试 |
| **主进程代发** | **用户令牌** | Electron | 直接用 `RelaySink(名字, "xxx-spool.jsonl")`，再让主进程去取 |

⚠ 这一刀不是历史包袱：**用户令牌只存在主进程的安全存储里，后端拿不到**。
任何"统一成后端直发"的方案最后都会变成把令牌递给后端，而那正好破坏
"令牌不出主进程"这条安全要求（需求 B2）。

#### 第 1 步：写出口

```python
# reporting/sinks/myplatform.py
from ..routing import Delivery
from .base import Sink


class MyPlatformSink(Sink):
    name = "myplatform"          # 路由表里就用这个名字指代它

    def enqueue(self, delivery: Delivery) -> bool:
        """**绝不抛** —— 打点不能影响业务。返回值只供上层记日志/计数。

        要发网络请求就先入队、异步发，别让调用方等在这儿：
        record() 是在业务线程上被调的。
        """
        ...
```

出口只管"把这一条送出去"，不管它怎么来的、归属是谁、要不要同时发给别人 ——
那些是路由的事。

主进程代发那一类连出口都不用写：

```python
sinks.register(RelaySink("relay:myplatform", "myplatform-spool.jsonl"))
```

#### 第 2 步：注册

`sinks/__init__.py` 是张表，加一行；或在装配期 `sinks.register(MyPlatformSink())`。

#### 第 3 步：加路由

```python
from netlivecowork.reporting import record
from netlivecowork.reporting.defaults import DEFAULT_ROUTES
from netlivecowork.reporting.routing import Route

record.install_routes(DEFAULT_ROUTES + (
    Route(kind="skill_usage", sink="myplatform"),
))
```

⚠ **`install_routes` 是覆盖不是追加。** 不带上 `DEFAULT_ROUTES` 的话，原来发去
Datalink 的 skill_usage、发去主进程的 token_usage **全部静默消失** ——
本地看起来和"正常上报"一模一样。

装配点放 `bootstrap/host_runtime.py`（`reporting_labels.install_resolver` 附近）：
要赶在第一条数据产生之前。`record()` 有惰性兜底（没人装过就套出厂默认），
所以装晚了不会报错，只会有一段时间按默认走。

#### 只发一部分字段 / 只发某个 cowork 的

```python
Route(kind="skill_usage", sink="myplatform",
      cowork="ipmaster",                          # 只发这个 cowork 的
      fields=("skill_name", "ts", "count"))       # 只有列出来的发得出去
```

`fields` **是脱敏点，不是性能优化**（§3.3）：写在路由表里而不是靠各出口自觉 ——
自觉的失效方式是"多发了一个字段"，而它不报错。

`cowork` 的三种值不一样：`"*"` 匹配全部、`"ipmaster"` 匹配那一个、
**空串只匹配"归属为空"**。

#### 加完之后自查

- 出口名**拼错的表现是这条数据消失**，不是报错 —— 看日志里 `不存在的出口` 那行，
  它会把已注册的名字列出来
- 发给两个平台之后，**A 的成功不会因为 B 的失败而重发**（扇出在入队之前，§3.2）。
  这条是整个设计的理由，值得在测试里钉一遍
- 测试抄 `tests/test_reporting_routing.py` 的形状。最该钉的两条：扇出后互不影响、
  `fields` 真的挡住了没列的字段

### 5.4 排查"数据为什么没上报"

按这个顺序看日志（`%APPDATA%\<品牌>\logs\backend.log`）：

| 现象 | 搜什么 | 说明 |
|---|---|---|
| 完全没有上报痕迹 | `没有路由匹配` | 路由表里没有这个记录类型 |
| 同上 | `不存在的出口` | 路由里的出口名拼错了 |
| skill 的没有 | `has own reporting` | **这个 skill 自带埋码，后端主动跳过**，见 §6 |
| 有发送但失败 | `[Datalink]` | 看状态码分类与是否进了重试队列 |
| 用量不涨 | `claim` / `ack` | 主进程有没有来取走 |

### 5.5 改动时的红线

- **`record()` 与各出口的 `enqueue()` 绝不能抛。**
- **写出的文件名与形状不能改**：主进程正在读 `token-usage-spool.jsonl` /
  `telemetry-spool.jsonl`，一行一个 `{event_type, ts, …}`。两边不是一起发布的，
  改了这边，装着旧主进程的机器就再也上报不了，**且不报错**。
- **归属取自 cowork 那边，不得在打点代码里现拼。** 现拼就有两套判断，
  而它们必然在某个分支上不一致——现象是"权限对了但账算错了"。
- **打点只收运营字段，排查细节走日志。** 往打点里塞排查细节会让上报量爆掉、
  且把本机路径带出去；把日志当打点上报则可能把用户环境信息传出去。

## 6. 一个重构期间发现的事实：skill 用量有两条上报路径

**这不是我们代码里的分支，是 skill 自己带的。**

云端引用的 skill 在物化时会被扫一遍源码文件；发现里面有 Datalink 的服务地址、
签名头或配置项名，就判定"它自己会报"，**后端主动跳过**，避免一次调用被算两遍。

```
后端报了     [Datalink] skill report request params: ...
后端跳过了   SkillReporter CAPABILITY_FINISHED: skill X has own reporting, skipped
```

⚠ **注意第二行里没有 "Datalink" 这个词**，搜 `Datalink` 是搜不到的——
排查时很容易误判成"没上报"。

### 实测观察（2026-08-27）

- **netcowork 市场引来的 skill** → 后端报，日志里有 `[Datalink]`；
- **mythos 市场引来的 skill** → 后端跳过，日志里只有那行 `has own reporting`。

代码路径不按市场分（只看这个 skill 自己带不带埋码），但**实际结果按市场分开了**。

### 三个后果

**① mythos 那批的上报我们看不见也控制不了。** 它是在 skill 自己的脚本进程里发出去的，
不经过后端。发没发、发了什么，只有 Datalink 那边的数据能确认。

**② 按 cowork 分账时那批数据不在我们手里。** 归属标签只对后端报的那部分有效。

**③ 检测是启发式的，误判就是静默丢数。**
后端只检测"看起来像会报"，**不验证"真的报了"**。一旦误判（比如某个脚本只在注释里
提了一句 Datalink 配置项名，或者复制了一段不执行的模板），后端跳过而 skill 也没报,
**这次调用谁都没报，且不报错**。

> 检测有意排除了 `SKILL.md` 与 `references/`，只扫可执行源码，误判概率已降低，
> 但仍是启发式判断。

**建议**：那行日志加上命中依据（哪个文件、命中了哪条规则），
把一个不可见的故障变成可查的。成本很小。

## 7. 已知欠账

### 7.1 凭据硬编码（**最要紧的一条**）

`sinks/datalink.py` 的 `_get_datalink_config()` 里，AK/SK 等有**硬编码默认值**，
且随包发出去。⇒ **拿到仓库或 exe 的人就有了往那张表写数据的凭据。**

拆除顺序（**反了会断一批人**）：

1. 先把 `DATALINK_*` 加进 `env-reconcile` 的 force 名单，老用户升级时自动补齐；
2. 再去掉源码里的默认值（此时已经没人依赖它）；
3. dev 与云端各自在自己的配置里补上。

> 为什么顺序要紧：那三个键 2026-07-17 才进随包模板，**在那之前首装的用户今天完全靠
> 源码默认值在上报**——用户 `.env` 只在首启生成一次，且 `DATALINK_*` 不在 reconcile
> 名单里，升级也补不上。

**更根本的**：客户端持有能往共享上报表写数据的凭据 = 任何拿到 exe 的人都能伪造上报。
真正的解法是**上报走服务端中转，客户端不持有写凭据**——那是另一个改动。

### 7.2 发不出去的数据（死信）没人看

重试用尽的记录会被挪进 `skill-usage-dead-letter.jsonl`（挪走是对的，
不挪它会卡在队头把后面全堵住）。但**全仓没有任何地方读它**：没有界面、没有统计、
没有告警，只是在用户磁盘上默默变大。

> 一个没人看的文件与直接丢弃的区别，仅仅是磁盘上多了个文件。

建议：

- **按原因分类**：4xx（我们发错了，重投也没用）→ 永久丢弃 + 显眼告警；
  5xx / 网络耗尽 → 可接受的丢失，计数即可。今天两类塞在同一个文件里，而行动完全相反。
- **计数要捎出去**：下次成功上报时带一个"上次以来丢了 N 条"。
  **运营数据的可信度取决于知不知道它缺了多少**——一份缺了 5% 却不知道缺的报表，
  比标着"缺 5%"的危险得多。
- **默认不自动重投**：云端恢复后涌入一批旧数据，时间戳全是过去的，
  报表会出现"昨天的量今天到"。
- **文件要有大小上限与保留期**：今天是无限追加。

### 7.3 归属还没接上

`labels.py` 恒返回空。等 cowork 的会话归属表建好后接上，**只改这一个文件**。

### 7.4 LLM 统计只有 token 数

现在报的是输入/输出 token、账号、模型。缺**调用次数、耗时、失败率、重试次数**——
内核事件（`LLM_REQUEST_STARTED` / `LLM_RESPONSE_FINISHED` / `LLM_RETRY_TRIGGERED`）
都在，数据是现成的，按 §5.1 补一个订阅者即可。
